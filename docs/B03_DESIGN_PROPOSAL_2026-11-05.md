# B03：审批修复与中断恢复设计提案

日期：2026-11-05。状态：**用户已确认方案与草图，进入实现**。正式要求已同步至 PROFILES/INSTALL/ARCHITECTURE/UI；下文为此次确认的设计依据。

本提案细化 `PRODUCT_REVIEW_PROPOSAL_2026-11-04.md` 的 B03 开工闸门。补上 PRODUCT.md 第 4 节中“新手需要自己运维”的缺口：从已核实的 Bypass 发现进入“改为执行前询问”，明确行为变化、服务中断、备份与实际结果。B02 已完成；本提案不扩展到自定义备份范围或通用任务编排。

## 1. 推荐决定

1. **保持活动目录只通过交换修改的规则。**配置命令仅对暂存副本执行；验证通过后，由 porter 用持久交换日志发布。不把“审批修复”作为直接写活动目录的例外。
2. **固定步骤 + 固定服务恢复规则。**profile 只增加有序 argv 列表与暂存重定向声明；停服、交换和恢复原运行状态由通用代码执行，不加入条件表达式、循环或任意 cleanup 脚本。
3. **先记录，再修改。**原服务状态、步骤开始/结束、目录交换和恢复服务均持久化。断连或崩溃后，不自动重跑结果不明的配置命令。
4. **中断恢复由用户发起。**没有发布新目录时，推荐“放弃本次配置修改并恢复原服务状态”；已经发布时，推荐“保留已发布配置并恢复原服务状态”。只有全部配置步骤已确定成功且暂存验证通过时，才允许“继续发布”。
5. **风险为 config。**沿用管理登录、现有异地备份前提、默认先备份及确认；不为 B03 新增权限等级或额外口令。
6. **逐版本核实后开放。**只有当前 profile/harness 版本下已验证的审批读法、暂存重定向和修改动作才提供入口。先验证隔离 fixture，再验证真实 harness 的隔离实例；不对正在使用的 agent 注入故障。

## 2. 为什么需要暂存

当前规范禁止直接写活动状态目录。原提案的“停止网关 → exec-policy preset → 恢复网关”若直接针对活动目录执行，不符合这条规则。

只读检查了 debian-vm 上已安装的 OpenClaw 2026.10.9：`exec-policy preset --help` 与安装包中的 `exec-policy-cli-HynY5Vun.mjs`。其 preset 同时更新请求配置和 approvals，写入配置失败时还会尝试回退 approvals；因此不能把它当成一个原子的单文件写入。`cautious` 的值为 allowlist / on-miss / deny fallback。**本轮只读 CLI 帮助与程序源码，没有运行 preset，没有读取用户配置内容或修改审批状态。**

暂存重定向必须另行实测，不能据此宣称已验证。环境变量、实际文件路径、版本和具体命令只写在 profile 中，Go 代码保持通用。

## 3. 建议的 profile 扩展

下例为中性结构示例，`example` 不是待执行命令；schema 已实现，具体 harness 动作仍须单独完成验收：

```yaml
approval_check:
  # 保留现有 argv / each / bypass_when / ask_when 等字段
  repair_action: approval-ask
  repair_expect:
    security.effective: allowlist
    ask.effective: on-miss

actions:
  - id: approval-ask
    name: 改为执行前询问
    explain: "改为白名单命令可直接执行，其余命令先询问；原本运行的服务会短暂停止"
    undo: "恢复服务不撤销审批设置；如需撤销，单独选择本次修改前的备份进行恢复"
    risk: config
    output: none
    steps:
      - id: set-policy
        argv: [example, exec-policy, preset, cautious]
    transaction:
      root: state
      env:
        EXAMPLE_STATE_DIR: "${STAGE_DIR}"
      writes:
        - config.json
        - approvals.json
    verification:
      versions: ["1.2.3"]
      env: "已实测的系统、架构与安装方式"
      date: 2026-11-05
```

字段语义与 lint：

- `argv` 与 `steps` 必须且只能出现一个。现有单 argv 动作保持兼容。
- `steps` 是 1～16 个固定 argv 步骤，id 唯一；顺序执行，任一步非零、超时或执行失败即停止后续普通步骤。每步采用现有非交互动作超时上限，不增加表达式、跳转、条件、循环或 shell 字符串。
- B03 的多步骤动作只允许 `risk: config`、`output: none`、非 terminal，且必须写 `undo` 和 `transaction`。步骤输出不写日志或持久操作记录；结果报告步骤 id、退出码、脱敏错误。
- 首版 `transaction.root` 固定为 `state`。`env` 的值只能为 `${STAGE_DIR}` 或其安全相对路径；键名来自 profile，必须逐版本核实能将全部配置写入重定向到暂存目录。它覆盖实例选择变量中的对应项，不记录登录环境或任何凭据值。
- `writes` 为 state 内明确的相对文件/目录路径，不接受 glob、绝对路径、`..` 或用户运行时输入。包括该命令会写的备份、锁和附属文件；可写目标及父路径不能通过链接指回活动目录或外部。核实重定向失败或存在无法隔离的写入时，不支持此动作。
- 新 `verification` 只用于 B03 事务动作，列出完整流程已通过的 harness 版本、环境与日期；缺少证据时必须标 `verify: pending`，不得关联到 `approval_check.repair_action` 或显示为可执行动作。首版按精确 harness 版本匹配，不用版本范围推测兼容。
- `approval_check.repair_action` 只能引用本 profile 的上述已核实 config 事务动作；审批读法本身也不能 pending。关联时必须同时声明 `repair_expect`：沿用现有字段路径与相等比较，所有被 `each` 选中的非空 scope 都必须满足全部目标值；缺字段、空 scope 或 unknown 均不得通过。这样不会把其他“需要批准”策略误认作本次要求的 allowlist/on-miss。命名实例使用 ForAgent 的有效 profile；服务作用域未核实的实例不开放 B03。
- 不允许客户端传入命令、env、writes 或路径。porter 从登记时的服务器 profile 生成计划。资料版本/定义有变化时停止并重新接入；已存在的未完成操作使用其冻结计划恢复，不从新 profile 重新解释旧步骤。

`writes` 是已核实命令的限定声明，不能把声明本身称作操作系统沙箱。执行前核实与隔离验收是开放能力的前提；对已存在的跨 root 自定义配置或未覆盖写入，明确拒绝自动处理。

## 4. 事务执行与服务状态

顺序固定如下：

1. 读取有效 profile、安装版本、活动 root、已声明服务及同一服务受影响的其他实例。检查资料一致、命令/依赖可用、重定向证据匹配、磁盘空间充足、目录可交换、无未完成冲突操作。
2. 展示计划：真实动作名、行为变化、实际 argv、原服务状态、受影响实例、暂存复制量与停机影响、默认备份与撤销边界。沿用现有备份前提和用户确认。
3. 用户确认后，按默认勾选建立标准逃生舱；用户取消勾选沿用既有后果说明。备份或前置检查失败时，不停服务、不运行配置命令。
4. 获取与封存/复活共享的修改互斥，再核对计划中关键事实；变化则要求重新确认。先原子写入并 fsync 事务记录，保存每个服务的原状态。只接受稳定的 active/inactive；failed、activating、未知或服务身份不符时先停止执行并解释。
5. 仅停止原本 active 的服务，逐个确认已停止；原本 inactive 的服务保持停止。停止失败，不运行配置步骤，并尝试恢复此前已被本操作停止的服务。
6. 再检查活动 root 是否仍被非服务进程使用；不能擅自结束用户进程。复制完整 state 到同文件系统的私有暂存目录，保留数据和权限，不与活动文件共享可写 inode。首版遇 root 符号链接、其他已登记实例嵌套或无法安全复制的文件类型时拒绝；不得静默漏文件。运行时、身体和工作区也计入复制空间估算，不因备份分档而漏复制。
7. 在暂存环境执行 `steps`，逐步写入开始/结束记录。命令只能写暂存目标；检查写入边界，并在暂存环境重跑审批检查。配置步骤失败或暂存复核仍 Bypass/unknown，不发布，恢复原服务状态。
8. 步骤与暂存复核均成功后，以 intent → rename → fsync → completed 的交换日志发布：活动目录保留为 prev，暂存目录成为活动目录。只复用既有交换机制的底层能力，不能调用会重建身体或无条件启动服务的完整 revive 流程。
9. 恢复服务：只启动本操作开始前 active 的服务；原本 inactive 的保持停止。分别核对恢复结果，重跑活动目录的审批检查，以及原本运行服务的健康检查。
10. 分别报告配置发布、审批复核和服务状态恢复结果，追加审计。审批仍为 Bypass、无法复核或服务恢复失败均不能显示整体成功。已经发布的配置不因服务启动失败而自动撤销；旧目录与备份仍可供用户另行恢复。

原本停止的服务保持停止也可以是“已恢复原运行状态”。界面应同时写明“当前服务未运行”，不得显示“服务健康”。白名单语义必须明确，不能将 cautious 宣称为“所有命令都询问”或“绝对安全”。

## 5. 持久记录、断连与恢复

建议独立存储于 `~/.local/state/valise/action-journal/`，格式 `valise-action-operation/1`，目录 0700、文件 0600；终态记录移入 `done/`，不混入现有 revive journal 的 JSON 类型。金库格式不变。

记录包括：操作 id、实例/安装/受影响实例、profile 与动作定义摘要、冻结的固定执行计划、前置备份 id、原服务身份与 active/inactive、live/stage/prev 的受限路径与目录身份、当前阶段、每一步 started/completed/exit、交换 intent 与结果、审批复核结论、服务恢复结论、时间与脱敏错误。**不记录文件内容、原始 stdout/stderr、登录环境、令牌或口令。**冻结计划不含运行时秘密。

每次外部副作用前先保存 intent，完成后保存结果；rename 窗口通过记录的目录身份与现场核对，不能只凭路径存在推断。记录损坏、目录身份冲突或未知版本时停止，给出保留现场与人工检查建议。

| 中断位置 | 重连后的处理 |
| --- | --- |
| 尚未停服 | 明确结束或重新发起，不推进配置 |
| 已停服、配置未完成或某一步只有 started | 不重跑该步骤；允许放弃暂存修改并恢复原服务状态 |
| 所有步骤 completed 且暂存复核通过、尚未发布 | 用户可继续发布，或放弃暂存修改并恢复原服务状态；继续前重新核实现场 |
| 交换过程中 | 依据 intent 和目录身份先完成一个可辨认的目录状态；不能猜测或删除冲突目录 |
| 已发布新目录、尚未恢复服务或复核 | 明确配置已经发布；只恢复原服务状态并重新复核，不再运行配置步骤 |
| 恢复服务失败 | 保留可重试记录，独立展示配置与服务结果 |

普通错误或捕获到断连时，可在本次操作授权范围内用有时限的清理路径尝试恢复原服务状态；原错误和清理错误分别保留。porter 被强制终止时不承诺服务自动恢复：项目不新增守护进程，下一次连接必须提示未完成操作，由用户确认后处理。

每次运行的配置子进程使用独立进程组，取消时只结束本次创建且身份核实的进程。重连后若原执行者或子命令仍存活，不允许并发恢复或重跑；不能根据旧 PID 杀进程。互斥锁覆盖执行期，未完成记录还阻止下一次冲突操作；封存、复活、重新接入和同安装其他修改入口必须采用相同的冲突检查。

原运行状态在恢复时不被当前探测结果覆盖。用户自行启动、改目录或变更相关服务后，显示现场变化并要求重新确认，不能悄悄覆盖用户的新操作。

## 6. 协议、权限与界面

推荐新增有界的 `action_plan`、`action_status`、`action_resume`、`action_cleanup` RPC；扩展 `action_run` 以接受计划摘要并返回 operation id。计划摘要仅用于发现确认前后的事实变化，不作为授权证明。

- `action_plan` / `action_status` 只返回脱敏计划与状态，属于日常只读；run/resume 的权限由服务器冻结动作决定，B03 为 config，即管理登录。cleanup 依据残留物与保留时间采用现有删除分级。
- 协议次版本从 1.2 升至 1.3，hello 增加明确的事务能力声明与 `pending_actions`；客户端同时确认服务器能力后才允许发送事务动作。旧 porter 不支持时提示先更新，不试图当作单 argv 执行。旧客户端忽略新增返回字段；未识别的新动作不得被旧执行路径执行，部署/重新接入前需做兼容检查。
- CLI 沿用 `valise action <服务器> <实例> <动作>`；新增范围明确的 `valise action status <服务器> <操作>`、`valise action resume <服务器> <操作> --continue|--restore-services`、`valise action cleanup <服务器> <操作>`。技术 id 不出现在日常健康摘要中。
- 健康页优先显示 `f 改为执行前询问`。进入现有动作确认与备份流程，展示白名单语义与服务中断；资料版本变化沿用 B02 重新接入入口。
- 结果页分列“配置”“审批检查”“服务”，另列备份与失败步骤。重新检查并刷新所有受同一服务影响的导航栈页面，过期响应不得覆盖新结果。
- 重连发现未完成操作时，入口说明当前配置是否发布、原本哪些服务在运行，提供上表允许的选择。退出提示不修改服务器；绝不自动推进。
- stage/prev 等残留只在用户显式清理时由 porter Go 代码删除；先列出影响并按既有删除等级确认，不自动清理或删除备份。审计与操作记录保留。
- TUI 草图见 `docs/sketches/B03-approval-repair.html`，包含确认、部分完成、重连恢复三种页面；用户已确认，页面已按方案实现。实现与验收进度见 [B03 验收报告](B03_ACCEPTANCE_2026-11-05.md)。

## 7. 验收范围

fake-ssh 覆盖：原本运行/停止；多服务停止部分失败；配置首步或后续步骤失败；退出 0 但暂存检查仍 Bypass；无法复核；前置备份失败；用户取消；越界/链接写入；旧 profile/porter；共享服务影响；进程仍活跃；重复请求；profile 更新后的冻结恢复；交换各窗口崩溃；操作记录损坏；清理确认与拒绝路径。故障必须检查活动内容及配置是否发布、实际启动次数、原始错误与恢复错误，不能仅断言返回状态。

真实 Debian 隔离实例覆盖：正常修复与取消；原本停止的不启动；停服后 SSH 断开、客户端退出、porter 中断；重连识别、放弃未发布修改并恢复服务；已发布后仅恢复服务；CLI/TUI/服务状态/审批读法/审计一致；定向清理。真实 harness 使用当前安装版本的隔离状态目录和独立服务，核实 preset 全部写入只在暂存范围，验证 allowlist/on-miss 的真实语义，记录原状态并按明确方案恢复，不在使用中的 agent 上注入故障。

交付前运行完整 `testbed/selfcheck.sh`（必须退出 0），并区分 fake-ssh 与实机结果。C 和 B03 之外的审批策略不进入本批。
