# 登录中继、管理页与本地页面转发

这一部分帮助系统管理能力有限的用户完成三件事：打开 agent 的管理页面、打开服务器上任意一个只在本机监听的页面，以及在无头服务器上完成登录授权。目标是让他们不必再临时搭建有头浏览器和 VNC。

> 2026-11-05：从零开始与接入已有共用这些客户端服务，GUI / TUI 适配与开发顺序见 DEV_PLAN.md N4。端口、来源校验和原生页面隔离规则不因改版放宽；访问级别按 ARCHITECTURE.md 2.2 的现行三级规则执行。

## 1. 两类转发必须严格区分

| | 管理页（Web 入口）与本地页面转发 | 登录中继 |
| :--- | :--- | :--- |
| 用途 | 打开管理页面或服务器上的本地页面 | 完成 OAuth 等登录流程 |
| 本机端口 | **与远端端口相同**；被占用时说明原因，建议用户释放端口再试；harness 支持改端口时，还可以同意"两边一起改端口"（4.2 节）；绝不静默换端口（2026-11-01 用户决定） | **必须与远端端口相同，绝不递增**（回调端口由登录服务写死，无法改） |
| 生命周期 | 用户手动关闭，或空闲超时后关闭 | 登录完成或超时（默认 5 分钟）后自动关闭 |
| UI 状态 | 隧道已建立、端口在监听、健康检查通过三个状态 | 等待链接 → 已打开浏览器 → 已收到回调 → 登录命令已退出（附退出码） |
| 访问级别 | 隧道为日常；代取令牌为主人操作 | 主人操作；旧日常钥匙无 PTY 能力时按现有兼容路径使用管理登录 |

所有隧道都只绑定本机回环地址，绝不绑定 `0.0.0.0`。管理页将来如要支持不同的本机端口，必须作为单独的能力设计（页面常校验 Host、Origin 或回调地址）。

## 2. 为什么"转发了就失效"

无头服务器上的 CLI 登录，通常会在服务器的 `127.0.0.1:<port>` 上启动一个回调监听，然后把浏览器重定向到 `http://localhost:<port>/callback`。**同端口转发本身是可行的**：本机浏览器访问 `localhost:<port>` 时，请求会经隧道到达服务器上的监听器；从服务器那一侧看，这个连接也来自回环地址。

转发失效的常见原因有以下几种：

1. **本机端口与远端端口不一致。**例如某些工具在端口冲突时会自动递增，而 redirect_uri 中已经写死了原来的端口号。
2. **端口在运行时随机选择**，用户事先不知道应该转发哪个端口。
3. **CLI 尝试在服务器上打开浏览器**（调用 xdg-open），在无头环境下失败，用户根本看不到授权链接。
4. **地址族不一致。**服务只监听 `[::1]`，转发却指向 `127.0.0.1`；或者本机浏览器把 `localhost` 解析成 `::1`，而本机只绑定了 IPv4。
5. **服务校验 Host 或 Origin 请求头。**
6. **流程确实需要一个真实的浏览器会话**，例如 agent 工具需要在浏览器里登录某个网站并保存 cookie。

第 1 到第 5 种情况，都可以由代码自动处理。只有第 6 种情况，才真正需要远端浏览器。

## 3. 登录方式（在 profile 的 `login` 中声明）

```yaml
login:
  - id: provider
    display_name: "模型提供商登录"
    kind: loopback_oauth           # loopback_oauth | device_code | paste_code | remote_browser
    argv: [example, auth, login]
    url_pattern: null              # 可选：从输出中匹配授权链接的正则表达式
    timeout_seconds: 300
```

### 3.1 `loopback_oauth`（回环 OAuth）

1. 通过 `ssh -tt` 运行登录命令（分配 PTY），并设置环境变量 `BROWSER=<porter 路径> browser-shim`。CLI 一旦试图打开浏览器，shim 就会把链接写到一个 porter 能读取的位置，然后正常退出。
2. 同时扫描 PTY 输出中的 URL，作为第二条截获渠道，用来覆盖那些直接打印链接、而不调用 `BROWSER` 的 CLI。
3. 从链接中解析出 `redirect_uri`（或其中指向 localhost 的 URL）和端口号。在服务器上用 `ss -ltn` 确认这个端口实际监听的地址族。
4. 在本机检查该端口是否空闲。如果被占用，就明确报错，指出占用端口的进程，并给出下一步建议；**绝不更换端口**。
5. 建立隧道：本机同时绑定 `127.0.0.1:<port>` 和 `[::1]:<port>`，转发到服务器上实际监听的地址。
6. **在本机浏览器中打开链接之前，先向用户展示链接的域名**，帮助用户识别钓鱼链接。
7. 用户完成授权后，等待登录命令退出，关闭隧道，并展示退出码。整个过程中的 PTY 输出只展示给用户，不写入审计记录。

### 3.2 `device_code` 与 `paste_code`

如果 harness 支持这两种方式，优先使用，因为它们完全不需要转发。

- **device_code**：截获设备码和验证链接，在 UI 中展示，并帮用户在本机浏览器中打开链接。
- **paste_code**：把 PTY 交互转接到 UI，用户在本机浏览器中完成授权后，把授权码粘贴回 UI。

### 3.3 `remote_browser`（后期）

计划方案：在服务器上以无头模式启动 Chromium，把它的调试端口（CDP）经隧道转发到本机，用画面投射的方式让用户完成操作。这样可以避免让用户自己搭建 VNC，也符合"不做临时有头桌面"的铁律。在 M5 验收之前，不实现这种方式。

## 4. Web 入口

- 端口取自 profile 的 `entries`。本机使用同一端口；被占用时报告占用它的进程（5.1 节），建议关闭占用这个端口的程序后重试；harness 支持改端口时（4.2 节）另外提供"两边一起改端口"。不静默换端口。（M5 实现的"冲突时递增"在 M11 改为本规则。）
- 隧道建立后，分别检测三个状态：本机端口在监听、远端端口在监听、HTTP 健康检查通过。三个状态分开展示。
- 可以设置为"打开实例卡片时自动建立隧道"，默认关闭。
- **入口一律在系统浏览器中打开，绝不在 Valise 桌面应用的窗口中加载**（原因见 `docs/UI.md` 第 6 节）。
- 界面上称为"管理页"（PRODUCT.md 8.1）。

### 4.1 管理页令牌（2026-10-31 用户决定）

很多 harness 的管理页在打开后还要一个令牌或密码（例如 OpenClaw 的 Gateway 令牌）。处理分两种：

- **profile 声明了 `entries[].auth`**（已知 harness）：隧道和健康检查通过后，按 ARCHITECTURE.md 2.2 完成主人证明（用户也可以选择不代取、直接打开），porter 在服务器上以登录环境运行声明的 `url_argv` 或 `token_argv`（argv 来自经过审核的 profile，不来自网页或 LLM；超时 15 秒）。
  - `url_argv`：声明了 `url_field` 时把输出按 JSON 解析并取该字段；否则从输出中取第一个指向该入口端口的 URL。把它的协议、主机和端口换成本机隧道地址，保留路径、查询和片段。harness 同时提供长期令牌与一次性配对链接时，profile 应选一次性的那个。
  - `token_argv`：取输出的第一行非空文本作为令牌，拼成 `本机地址 + path + url_suffix`。
  - 得到的地址直接交给系统浏览器。令牌只在内存中经过：不写盘、不显示、不进日志与审计、不放进错误信息；命令失败时只报告退出码，并退回下一种方式。
- **没有声明，或自动取得失败**：界面显示 profile 的 `hint`（没有时显示通用说明："如果页面要求令牌或密码，请在服务器上运行 harness 自己的命令获取，再粘贴到页面中"），并提供"打开服务器终端"：暂停界面，用管理登录新开一条独立连接打开交互式登录 shell（INSTALL.md 第 2 节），用户自己运行命令、复制令牌，退出 shell 后回到界面，管理页的隧道保持打开。Valise 不读取这个终端里的任何内容。

### 4.2 两边一起改端口（2026-11-01 用户决定，M11 实现）

本机端口被占用时，经用户同意，把服务器上 harness 的监听端口和本机端口一起改成同一个空闲端口，两边仍然保持一致。

- **前提**：profile 在入口上声明了改端口的方法 `entries[].port_change`（PROFILES.md 第 2 节）：harness 自己的改端口命令（`steps`，一条或多条 argv，只能引用 `${PORT}` 与 `${HOME}`），以及是否还需要重启服务。**只在 harness 支持（profile 声明了 `port_change`）时提供**；不支持时依然只建议用户释放端口再尝试。
- **选端口**：Valise 推荐一个本机与服务器上都空闲的端口（从原端口加 1 开始查找，本机用绑定测试，服务器经 porter 读监听表），用户也可以自己填。
- **确认**：确认框写明"会把服务器上 <harness> 的管理页端口从 A 改成 B 并重启服务；本机也用 B；服务会中断约 N 秒；以后打开管理页都用新端口；改回的方法……"，并展示实际命令。
- **执行**：需要管理登录；先建立一个备份（配置会被改动；可以跳过，跳过时说明后果）→ 运行 harness 的改端口命令 → 按需重启服务 → 健康检查 → 把新端口写进实例记录的 `entry_ports`（之后打开管理页、健康检查都用它）→ 用新端口建立隧道。任一步失败时停止并说明当前状态；配置已经被改动的，提示可以从刚才的备份恢复当前实例。
- 此操作只调用已声明的 harness 命令。其他已核实的配置动作按 INSTALL.md 第 5 节执行，不能因本流程可改端口而扩大任意配置写入能力。
- 本地页面转发（第 6 节）没有 profile 知识，不提供这个选项；端口被占用时说明原因，建议用户释放端口再尝试。登录中继的回调端口由登录服务决定，不能改。

## 5. 实现细节（M5 确定）

### 5.1 隧道

- 两类隧道的实现相同：客户端自己在本机回环地址上监听（`127.0.0.1` 必须成功，`[::1]` 在本机支持 IPv6 时一并绑定），每个进入的连接经系统 OpenSSH 的 ControlMaster 运行一次 `ssh -W <远端地址>:<端口> <服务器>`，把字节原样转发。传输仍然只走系统 OpenSSH，Valise 不实现任何 SSH 协议。
- 这样做，端口冲突在客户端绑定时就能确定；登录中继能看到回调连接到达（只记录"有连接到达"，不读取请求内容）；Web 入口能按连接活动判断空闲。
- 本机端口被占用时，报告占用它的进程（macOS 与 Linux 上用 `lsof -nP -iTCP:<端口> -sTCP:LISTEN` 查询；查不到时只报告端口被占用）。
- 远端实际监听的地址族由 porter 读取 `/proc/net/tcp` 与 `/proc/net/tcp6` 判断（与 `ss -ltn` 等价，不依赖 `ss`）：只监听 `[::1]` 时转发到 `[::1]`，否则转发到 `127.0.0.1`；监听在 `0.0.0.0` 或 `[::]` 上也转发到回环地址。

### 5.2 登录中继的流程

1. 客户端调用 RPC `login_prepare`，传入登录条目（来自客户端内置或本地 profile 中与实例 `profile_id` 相同的 profile）。porter 用登录 shell 的 PATH 展开 argv，生成一个会话 id，把会话写到 `~/.local/state/valise/login/<会话>.json`（0600）。
2. 客户端运行 `ssh -tt <服务器> "<porter 路径> login-run <会话>"`。porter 读出会话，设置 `BROWSER="<porter 路径> browser-shim"` 与 `VALISE_LOGIN_SESSION=<会话>`，在 PTY 中执行登录命令。`browser-shim` 把收到的链接追加写入 `<会话>.url` 后以 0 退出。
3. 客户端把 PTY 输出原样显示给用户，同时去掉终端控制序列后扫描链接（profile 有 `url_pattern` 时优先用它）；另起一个 RPC 会话轮询 `login_urls` 读取 shim 截获的链接。两条渠道先到者为准。
4. `loopback_oauth`：从链接的 `redirect_uri`（或链接本身）中找出指向 `localhost`、`127.0.0.1`、`[::1]` 的地址和端口；向 porter 查询该端口的监听地址（最多等待 10 秒）；本机绑定同一端口，失败就报错并结束登录命令，**绝不换端口**。没有找到回环地址时，按 `device_code` 处理（只打开链接）。
5. 打开浏览器前，先显示链接的域名，用户按回车确认后才用系统浏览器打开（macOS 用 `open`，Linux 用 `xdg-open`）。确认期间暂停向远端转发键盘输入。
6. 状态依次为：等待链接 → 已打开浏览器 → 已收到回调（仅 `loopback_oauth`）→ 登录命令已退出（附退出码；被 Valise 结束时说明"已被结束"）。回调隧道建好时（打开浏览器之前）另行提示本机与服务器的地址。超时（默认 300 秒，profile 的 `timeout_seconds` 可改）后结束登录命令。
7. 结束时关闭监听，删除服务器上的会话文件。PTY 输出与链接不写入审计记录；审计只记录登录条目 id、开始与结束时间、退出码。
8. `paste_code` 与其他需要输入的情况：用户在同一个终端里直接输入，客户端原样转发给远端 PTY。

### 5.3 CLI

- `valise login <服务器> <实例> [--method <登录条目 id>]`：没有 `--method` 时列出 profile 中的登录方式。
- `valise open <服务器> <实例> [--entry <入口 id>] [--idle <时长>] [--no-browser]`：前台运行；依次检查并分别显示"隧道已建立""远端端口在监听""健康检查通过"三个状态，然后用系统浏览器打开本机地址。Ctrl-C 关闭；空闲（没有任何连接）满 `--idle`（默认 30 分钟，`0` 表示不自动关闭）后关闭。健康检查使用 profile 中针对该入口的 `http` 检查的 `expect_status`，没有时任何 HTTP 响应都算通过。

## 6. 打开服务器上的本地页面（2026-11-01 用户决定，M11 实现）

用户在原生界面或其他地方看到一个服务器上的回环地址（例如安装程序打印的 `http://127.0.0.1:18789/?token=…`），可以让 Valise 在本机打开它。

- **输入**：粘贴带明确端口的地址，或手动填写端口。只接受 `http`/`https`，主机只能是 `localhost`、`127.0.0.1`、`[::1]`（转发目的地址由客户端固定为服务器回环地址，不接受其他主机，避免成为任意网络访问入口）。保留完整的路径、查询与片段。
- **端口**：本机使用同一端口（第 1 节）；先检查本机端口占用，被占用时说明原因与占用进程，请用户处理（这里没有 profile 知识，不提供"两边一起改端口"）。
- **状态**：显示目标服务器、转发状态与三个状态（4 节）；提供"重新打开"与"结束转发"；连接中断与退出时说明状态。
- **敏感参数**：URL 中的查询与片段（常含令牌）不写入日志、审计、诊断材料与错误信息；界面上只显示协议、主机与端口，完整地址只交给系统浏览器。
- **局限**：同端口转发能覆盖许多管理页与回环登录场景，但不保证所有 OAuth 成功（监听方向、固定回调地址、设备码、授权服务要求、会话生命周期各不相同）。界面不宣称"任意登录都可完成"，失败时说明可能的原因并建议改用 profile 声明的登录方式或原生界面。
- 走日常钥匙（只允许转发到服务器回环地址）。

## 7. 云盘登录（N3，2026-11-07 用户决定）

云盘的“服务器登录”（ARCHITECTURE.md 7.3）复用本文的登录中继，登录条目由代码按 `kit-tools.yaml` 的 `clouds` 生成，不来自 harness profile：

1. 主人操作，新开管理连接，`ssh -tt` 下由 porter 运行固定 argv：`rclone config create valise-<名> <rclone_type> <固定参数…> config_is_local=true --config ~/.config/valise/rclone/rclone.conf`。
2. rclone 在服务器 `127.0.0.1:53682` 起回调并打印 `http://127.0.0.1:53682/auth?state=…`；按 5.2 节以 `loopback_oauth` 处理：截获链接、绑定本机同一端口、显示域名后打开本机浏览器，回调经隧道到达服务器。
3. **退回**：本机 53682 被占用（报告占用进程），或云盘条目声明不支持回环授权时，改为 `config_is_local=false`。rclone 打印一行 `rclone authorize "<类型>" "<参数>"`；Valise 展示这行命令，用户确认后用本机 rclone（ARCHITECTURE.md 7.3“这台电脑登录”的同一来源，没有时先按确认下载）在本机前台运行，输出只显示给用户；用户把结果复制、粘贴回服务器终端。Valise 不解析、不自动传递这段结果。
4. 结束后按 ARCHITECTURE.md 7.3 做连通测试并保存位置。审计只记录云盘条目 id、开始与结束时间、退出码。
