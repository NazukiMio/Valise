## 2. A：文案与健康状态

### A-T01 概览没有失效入口及重复提醒

构造一个 agent，只有一个 `p.check.Findings`，其他健康项正常，进入概览。

- 提醒仅在“需要处理”出现一次；备份行不追加检查提醒。
- 页面不出现“见体检”或“体检有”；跳转提示实际指向健康分栏。
- 对 `finding:<id>` 执行黄色忽略后：健康页保留灰色项，概览不继续显示问题，摘要显示 1 项已忽略。
- 取消忽略后恢复问题。分别开/关对话分栏并覆盖安装下 agent 子页，确认编号没有写死。
- 自动测试比对去 ANSI 后文本，并验证状态；不只断言出现“健康”二字。

### A-T02 初次检查失败与旧结果

分别让 `Checkup` 首次失败、成功后刷新失败、失败后成功。

- 首次失败显示检查未完成，无“一切正常”。
- 刷新失败保留旧结果时同时显示旧结果标记、错误及成功时间；旧结果不冒充本次检查。
- 恢复后清除错误并采用新发现。概览与健康结论一致。
- 注入延迟旧响应：后发刷新先成功，旧成功或旧失败随后到达，均不能覆盖新状态；页面/实例切换后不串数据。此项属于 A，不等到 B 才测试。
- 没有已知问题但仍有检查失败/加载时，显示检查未完成；不得用绿色正常结论覆盖未知状态。

逐个注入 `Instances`、`TimerStatus`、`KitStatus`、审批调用失败，检查 `HealthReport` 的失败信息和 TUI 呈现。其他成功检查仍可见；未声明能力不误报连接失败。错误内容脱敏。

### A-T03 文案逐项检查

逐一打开 rules、chat 快捷项、技能设置、备份向导、备份分组设置，执行 CLI 总帮助、checkup、health。

- 对照实施单 A03 的每一行验收；记录实际页面文本。
- `checkup` 人类输出是会话与记忆检查，`health` 是综合健康，不混淆覆盖范围。
- `valise-checkup` 技能 ID、现有 CLI 命令与 JSON 字段保持兼容。
- 备份向导不把轻装说成全部状态，选择说明可看出凭据/工作区是否包含。
- 原型验收尺寸为 80×24、110×34；缩小后提示清楚，放大后选择不丢。

## 3. B：修复入口

### B-T01 服务项接已有动作

fixture profile 用中性名称，声明服务、restart 管理动作和有效关联；不要在 Go 实现中写 harness 特例。

1. 服务异常，选中健康项，看到 `f 修复` 和动作名。
2. 按 f 进入已有动作确认页；取消：零动作、零配置变更。
3. 确认并执行；审计记录匹配动作 ID、权限和退出码。
4. 结果返回后自动复核，父页面和概览采用新状态，无需手动 r。
5. 命令 0 但服务仍停：保留问题，不能显示已修复。命令非 0、复核 RPC 失败分别显示。
6. profile 关联不存在时 lint 失败；资料版本不同引导重新接入；无关联项不给假修复按钮。

真实靶机：只操作隔离测试实例，记录停止前状态、修复后 systemd 状态及入口响应。固定命令的 fake 测试不算实机验收。

### B-T02 审批三步与失败恢复

仅在 B03 schema 获批和实现后执行。覆盖网关原本运行/停止两种状态，以及 stop 失败、配置失败、恢复运行失败、配置成功但审批复核仍 Bypass。

逐步检查实际执行顺序：失败后不继续普通步骤；清理按设计恢复原运行状态；原本停止的不擅自启动；原错误与清理错误均保留。取消或前置备份失败时不得修改审批设置。

停服后分别断开 SSH、退出客户端和中断 porter，核对持久操作记录、重连识别及设计规定的恢复路径。分别报告配置变更与服务恢复结果，不能把补偿启动等同撤销配置。

真实靶机先记录配置与服务状态，完成动作后重新读 `approval_check`，确认谨慎策略的真实含义。测试结束按明确方案恢复测试设置，不把一键修复直接等同“绝对安全”。

### B-T03 刷新和忽略

修复完成前后分别模拟延迟旧响应；结果不能被过期健康数据覆盖。被忽略的真实问题仍允许主动查看和处理；忽略操作自身不能触发修复，也不能记成已解决。CLI action 后再 health 的事实与 TUI 一致。

## 4. C：自定义范围 fixture 与结果

先确认实施提案 C02 的匹配/回滚语义和格式兼容方案，再冻结以下预期。fixture 位于现有 state root，另设一个 workspace root。

| 路径 | 原分类 | 基础 soul 是否包含 | 自定义选择 |
| --- | --- | --- | --- |
| memory/keep.txt | memory | 是 | 包含 |
| memory/private.txt | memory | 是 | 排除 |
| custom-memory/a.txt | 未分类 | 否 | 显式包含目录 custom-memory/ |
| auth.json | secrets | 否 | 排除 |
| workspace/result.txt | workspace | 否 | 显式包含该文件 |
| cache/tmp.txt | cache | 否 | 不包含 |

每文件写不同合成内容，记录 SHA-256。预期自定义备份恰好含 keep、a、result；a 仍为敏感层，不能因为选中而成为 memory。凭据排除不改变 auth.json 的 secrets 分类。另建已声明 SQLite：选择主库时不能单独封存 WAL/SHM，复用一致性流程。

### C-T01 预览、保存、重入

- TUI 选上述范围，预览列出准确路径、类别、包含/排除原因与估计大小；不返回文件内容。
- 取消不写；保存后退出、重开、CLI 读取仍一致。
- 在 custom-memory 新增 b.txt，在 workspace 新增 other.txt。目录递归应包含 b；单文件选择不应包含 other。
- 两客户端基于同版本编辑：第一个保存后，第二个保存被明确识别为冲突，不能覆盖；读回版本与内容校验。
- 保存失败（权限或磁盘故障）不损坏旧方案。修改后不改变旧快照的范围事实。

### C-T02 实际封存与触发方式

手动执行、定时选择跟随方案分别备份，真正解密列出文件并逐一比哈希，不只看 UI 汇总。未改变设置的旧定时任务仍按原 soul；动作前备份使用明示的标准预设；MCP 仍用原预设。每种报告写出实际采用的预设/方案版本。

扫描中途修改方案：正在执行的备份用开始时固定的版本，下次才采用新版本。扫描中的文件变化、不可读文件须报告遗漏或不稳定，不能暗示完全覆盖。

### C-T03 回滚最重要的反例

快照后修改 keep、private、a、result；在 custom-memory 新增 b，在 cache 新增 live.txt。执行真实回滚后：

- keep/a/result 回到快照内容。
- private 保留当前版本；auth 与 cache 保留当前状态。
- b 位于当时包含的递归范围内，但快照时不存在，按已确认的回滚语义移除。
- 不在范围内的 workspace/other.txt 保留。

这条专门防止 `carry` 继续按整类判断：memory/private 不能因类别在 tier 内而被误删。分别制造暂存、交换失败，确认活动目录没有半写、可以按日志恢复。

另测父目录包含、子目录排除、孙文件包含的冲突，以及改名、文件与目录/链接互换。扫描遇到权限、I/O 或不稳定文件时，不得把未读到当作不存在，并据此删除当前数据；按定稿方案验证封存失败或不完整快照的恢复限制。

### C-T04 兼容与独立恢复

- 旧快照用新版本恢复，行为与旧预设一致。
- 新范围快照交给实际旧版本、不支持范围的客户端：交换前明确拒绝，不能忽略未知字段按旧 tier 回滚；记录旧版本和实际拒绝位置，不以新客户端模拟旧能力代替。
- 只剩异地副本、恢复套件与新本地配置：还原所选文件，不依赖原服务器方案记录。
- 独立恢复工具配合 age/zstd，不运行 Valise 二进制，输出所选文件并比哈希。
- 迁移/克隆后路径与范围继承可解释，排除内容不被宣称已迁移。
- profile 更新新增凭据分类时，已选路径仍按最新生效的敏感分类保护；用户选择变化在预览中可见，旧快照用旧范围与分类事实。

额外目录、陌生 harness 未实现时不验收为通过，不将手工目录备份称为自动重建支持。
