## 1. 产品定位

Valise 是自托管 Agent 的安装与管理入口。用户从一台可以通过 SSH 登录的服务器开始，使用 Valise 安装或接入 Harness，打开管理页面并完成日常管理；Valise 同时提供可靠的备份、恢复和迁移。

主要用户有服务器地址及登录凭据，但未必会配置 SSH 或使用终端。默认体验面向新手，同时保留 CLI、SSH 配置和高级功能供进阶用户使用。Valise 接手重复的服务器操作，不要求用户先掌握运维。

日常重心是安装、运行状态、管理入口、登录辅助、体检和其他管理能力。备份和恢复是重要的保障能力，但在正常状态下应安静运行，不持续抢占注意力；失败、长期未备份、异地副本缺失等需要处理的情况应清楚提示。

第一阶段只将 OpenClaw 从空服务器安装到日常管理的体验打磨透彻；形成成熟的方法和验证流程后再引入其他主流 Harness，稳定后才建设陌生 Harness 的通用接入方法。不要把单份 Profile 等同于已全面支持。

首次使用的目标结果：**用户成功连接服务器，安装或纳入管理一个 Harness，并在浏览器中看到它的管理页面。** 模型凭据配置不是完成该目标的强制步骤。

## 2. 新用户旅程

1. 首次启动建议用户设置 Valise 加密钥匙及备份，但允许暂时跳过；首次启用加密备份前必须完成相应设置与钥匙备份引导。
2. 首页没有服务器时，引导添加第一台服务器。支持从 SSH Config 发现，也提供明显的手动入口：地址、端口、用户名、登录方式及用户自选别名。
3. 验证连接和服务器身份；首次连接与身份变化时给出可理解的提示。优先使用操作系统钥匙串保护本机保存的 SSH 凭据；允许不保存、每次输入。具体平台回退策略待设计。
4. 新服务器没有 porter 时，提供“一键部署 Valise”：从官方发布源获取服务端，验证签名及 SHA-256，再安装。自动检查更新，用户确认后更新。不得将尚未建立的发布链描述为可用。
5. 部署完成后检测已安装的 Harness：已有实例可直接纳入管理；没有实例时引导安装第一个 Harness。两条路径都应可达，不强迫已有用户重新安装。
6. 第一阶段官方安装与管理只聚焦 OpenClaw。安装完成后发现实例、引导打开管理页；模型凭据由用户在 Harness 原生界面或管理页自行填写。
7. 可选引导安装 Valise 官方套件。首次安装或首次纳入 Valise 管理的实例，可选择“开始备份教程（有提示）”；确认后建立首个逃生舱并标记为教学或测试。成功后邀请用户尝试恢复，允许跳过；恢复演练应清楚说明目标与影响，优先研究隔离位置演练。
8. 向导引导用户选择是否开启定时备份，并允许自行修改配置。建议添加“空间站（异地备份）”，允许跳过。提供首次同步及后续从异地恢复的引导。
9. 提供“取回本地”：以“保存加密备份”或“导出可查看的文件”向用户表达。明确目的地、凭据是否包含、解密后文件的保护状态，以及恢复加密备份需要的钥匙。

初始教学备份只证明当时的流程和内容，不证明将来新增的配置、渠道凭据或工作区均已覆盖。用户完成重要配置后，应适时建议建立新的实际备份。

## 3. Harness 安装与原生引导

### 3.1 两种交互方式

- **简易引导**：官方 Profile 对已适配版本提供安装、环境检测和必要的页面转发引导。常见依赖可由 Valise 引导安装；需要管理员权限、系统配置变更或较大依赖时说明并取得确认。
- **原生安装界面**：向用户提供 Harness 自带的交互式 CLI，用户自行完成原生引导。Harness 管理页面的高级功能中应允许之后再次进入该原生界面。

官方方案默认展示通俗说明，允许展开查看实际命令、来源、权限和依赖。安装完成后检测实际结果，而非仅依据命令退出码判定实例已经可用。版本或流程不匹配时，如实提示并提供原生方式继续。

Valise 不提供 API Key 输入辅助，也不代用户提交、保存或管理模型凭据。用户在 Harness 原生 CLI 或管理页面自行填写。首次安装过程中需要填写 API Key 时，必须由用户在原生交互界面中输入；安装完成后也可通过 Harness 管理页自行配置。允许稍后配置。

交互式 CLI 经 Valise 转发时，输入字节仍会经过交互通道；不能声称凭据完全不经过 Valise。要求不主动解析、读取、持久化或向日志、诊断材料和普通输出记录凭据。终端录制、崩溃报告及敏感回显的处理须单独设计和测试。SSH 登录凭据、Valise 加密钥匙以及用户选择封存的 Harness 凭据属于不同用途，不与上述模型凭据输入边界混淆。

### 3.2 官方 Skill 套装

官方 Skill 与服务按使用方分为两类，职责和对接入口不得混淆：

- **受管方**：指被 Valise 管理的 Harness/Agent。其官方 Skill 主要与服务器上的 Valise 服务端（porter 及其受限接口）对接，帮助受管 Agent 使用获准的登记、体检、交接、封存等工作流。现有 agent-kit 属于这一侧；实际能力以现有实现和权限边界为准。
- **管理方**：指代表用户操作 Valise、管理服务器及 Harness 的 Agent。其官方 Skill 主要与用户侧 Valise 客户端对接，指导管理 Agent 完成已授权的连接、安装引导、管理、Profile 辅助与结果反馈，并遵守用户确认及凭据边界。**当前项目没有管理方 Skill；这是待设计和建设的新能力，不能描述为已有功能。**

两侧 Skill 可以组成官方套装，但不是同一套权限：管理方不得借 Skill 绕过客户端的确认、安装安全检查或凭据限制；受管方不得因安装 Skill 获得管理方权限。具体客户端接口、服务端接口、安装位置、身份与授权模型，以及两侧如何发现对方，须在架构和安全规则修订后设计；不得仅凭 Skill 文本替代代码强制的安全边界。未知 Harness/Profile 辅助 Skill 在主流 Harness 方法论成熟后建设，并明确其管理方角色。

## 4. 通用回环页面转发

提供“打开服务器上的本地页面”：用户在原生安装界面或其他流程中看到回环地址后，可粘贴带明确端口的地址，或手动填写端口。保留完整路径和参数，方便管理页和受支持的登录流程。

- 默认使用服务器端和用户本机**相同的端口**；检查本机端口占用。占用时解释原因并请用户处理，不得静默换端口。
- 隧道只绑定本机回环地址，显示目标服务器与转发状态，并提供重新打开和结束转发；连接中断和退出时说明状态。
- 限定输入与目的地址，避免成为任意网络访问入口；不得在普通日志或诊断材料中泄露 URL 中的令牌等敏感参数。
- 同端口转发可覆盖部分管理页和回环登录场景，但并不保证所有 OAuth 成功。需按实际监听方向、固定回调地址和端口、设备码、授权服务要求及会话生命周期逐项验证。显示进度和失败处理，不应宣称任意登录都可自动完成。
- 对普通管理页未来如要支持不同本地端口，必须作为单独能力明确设计；第一版采用同端口规则。

## 5. Profile 是适配知识核心

Profile 是 Valise 理解 Harness 的知识和操作规则：发现、路径与分类、来源、安装、服务、管理页、登录、健康检查、备份、体检、Agent Kit 和用户可操作的功能。通用引擎负责安全执行；Profile 的准确性决定具体 Harness 的体验和保护范围。

官方支持须按 Harness 版本、安装方式和能力真实验证，持续维护。官方列表区分“可安装”和“可管理”的能力，不因存在 YAML 就宣称全面支持。列表可用概览等级，详情按能力展示实际状态，例如“管理页连接测试通过”“备份已测试”“恢复尚未演练”，并注明适用版本与环境。

对于用户添加的 Profile，不用笼统的“未验证”制造压力，也不能隐藏风险或取消必要的恢复保护。将来源、已测试能力、未测试能力、失败项与具体影响清楚呈现；旧的 draft 恢复确认如何迁移，须在更新相关规范时明确。

### 5.1 后续：用户自建 Profile

主流 Harness 方法论成熟后，提供两条共享格式与测试流程的路径：

- 表单：用户参考官方文档填写路径、服务、端口、操作等，系统生成 Profile。
- 官方 Skill：用户提供文档链接，由 Agent 协助生成草稿，用户审阅并测试。

系统提供逐项测试，如程序和版本识别、路径存在、服务状态、管理页连接和备份覆盖预览。测试结果只陈述已验证内容，不推断其他能力已可靠。AI 生成结果是草稿，命令和路径应可查看；不擅自执行。

### 5.2 可登记动作与动态管理页面

用户可为 Profile 登记不同数量的动作，每项至少包含名称、对用户的解释、实际指令，以及执行结果展示信息。管理页面根据 Profile 动态生成按钮并能返回执行结果。普通用户界面默认隐藏复杂指令，但提供查看实际命令的入口；隐藏仅指视觉折叠，不得用于隐瞒内容。

动作应区分只读查询、常规管理、配置变更和高风险操作；按实际影响设计确认和权限。陌生命令先登记，不能因为登记或生成就自动执行。用户或 AI 提供的会改变状态或有风险的操作须在执行前展示实际内容并确认。结果区分命令退出状态与服务/功能的真实健康状态。具体 schema、权限和安全分类留待设计，不能借“动态按钮”引入无边界插件解释器。

## 6. 第三方工具

第一阶段优先支持接入用户已安装的工具：通过用户创建的 tool-profile 登记其服务、状态、端口、管理页面和动作。为后续用户提供安装命令的能力预留接口；不要宣称已实现工具安装。工具 Profile 可由表单或官方 Skill 协助创建，使用可解释的逐项测试；Valise 不为工具的安全性背书。

用户提到 Magpie 作为示例：其管理界面和端口可以作为将来接入的测试案例，是否适用特定部署方式须实际验证，不将示例视为已支持。

后续支持安装第三方工具和非列表 Harness 时，用户可提供命令，或让 Agent 根据用户提供的文档协助生成方案；均需展示实际命令、来源、脚本信息和基础风险检查结果，由用户明确发起和确认。高风险安装需要更明确、反复的用户确认，并显示“我知道自己可能会面临安全风险，确认”。Valise 不对第三方软件背书。

安装前可以建议用户备份 Agent，用户可选择跳过；必须说明 Agent 备份不等于服务器整机备份，不能保证撤销工具对系统、其他服务或外部资源的修改。

## 7. 安装命令与脚本的安全边界

Valise 只承担能够通过基础规则发现的疑点提示，不宣称完成安全审计。应考虑检测编码或混淆、隐藏下载来源、网络脚本直接执行、提权、敏感配置修改、明显删除覆盖及来源不一致等，并解释命中原因。“未发现基础疑点”不等于安全。

用户要求禁止一切隐藏信息的安装指令，包括通过 Base64 隐藏真实安装源等。对于明显编码、混淆或隐藏来源且不能向用户清楚展示实际内容的操作，不提供直接执行；用户可自行在 Valise 外处理后接入管理。检测能力有局限，不能声称能够识别所有隐藏行为。对于运行时动态下载等无法预先确定的内容，应明确说明未知范围，不得声称已看透所有后续行为。

用户确认不能取代技术边界。官方安装方案、用户提供的命令、Agent 生成的草稿须标明不同来源；Agent 不得绕过用户确认。未来“Valise 沙盒插件”是进阶规划，不作为现有隔离或安全能力描述。`curl | bash` 等旧禁令与新需求冲突，脚本获取、展示、后续下载与执行的具体规则尚需先定稿并修订旧文档；在此之前不得据本文直接绕过现有禁令。

## 8. 日常界面与备份体验

首页优先展示服务器和 Agent 的运行状态、异常、管理入口与需要处理的事情。正常备份以简短状态呈现，例如上次成功时间和异地副本状态；备份失败、空间不足、钥匙或异地副本问题应提升为提醒。避免把“建立逃生舱”作为所有页面的中心。

实例页优先提供管理页、原生界面、状态、登录辅助及体检，保留逃生舱、设置和恢复入口。“逃生舱”“着陆”等品牌用语可保留，但关键操作同时解释备份、回滚、迁移、克隆的实际含义。

逃生舱详情分别展示服务器、本地和空间站的副本状态；建立成功时清楚说明是否仅存在原服务器。加密取回和解密导出应展示各自结果与安全影响。保留可靠恢复、暂存校验、用户确认及失败回退，不因降低日常曝光而削弱保障。

80 列终端必须换行或可滚动展示恢复计划、停机和空间说明、结果路径及快捷键，不截断决策所需信息。长操作显示阶段和等待状态。体检结论应表述为“未检测到已知机制”等与证据一致的话，不把 Profile 未覆盖的情形断言为不存在。

### 8.1 TUI Harness 卡片与图标

当前各 Harness 官方 ASCII 图标大小不一致，会导致实例卡片尺寸不统一。TUI 须采用统一的卡片尺寸和固定图标占位区域：同一视图中，卡片宽高及图标区域一致，不能因为原始图标的行数或宽度改变卡片尺寸；实例名称、状态和操作信息也应保持稳定对齐。

Profile 中可以继续保存来源明确的原始图标；展示时统一适配图标区域，避免拉伸变形、破坏字符画或截断关键信息。无法在目标尺寸下清晰呈现时，使用统一占位图标或经过验证的简化版本，不得让卡片扩张。没有图标的 Harness 也使用相同尺寸的占位区域。

具体字符宽高、缩放和降级规则应结合终端字符宽度、Unicode 显示及可用空间设计，并在不同终端宽度、长名称、无图标和多种图标尺寸下验证；窄终端可以使用统一的紧凑布局，但同一视图内仍须保持一致，重要状态不得被截断。

## 9. 阶段与验收方向

1. **先修订规范**：明确新旧文档的优先关系、安装及凭据边界、确认规则和兼容策略，再开始实现。
2. **OpenClaw 端到端**：空服务器手动连接 → 部署 porter → 安装或接入 OpenClaw → 原生引导/受支持的页面转发 → 打开管理页；另测已安装实例接入。
3. **日常管理**：准确展示状态、管理入口、原生 CLI 高级入口、已验证的体检和清晰错误。验证不同安装方式和真实凭据/渠道，但不记录秘密。
4. **备份闭环**：首次教学标记、恢复引导、可配置定时、可选空间站、同步及恢复、本地加密保存与解密导出。演练需区分教学与实际业务备份。
5. **沉淀 Profile 方法**：按版本与能力建立测试矩阵，验证稳定后扩展其他主流 Harness；再做陌生 Harness 的表单与 Skill。
6. **工具管理**：先登记和管理已有工具；后续再启用用户提供安装命令。服务器健康、推荐记忆工具、工具仓库、沙盒插件等为后续规划，预留必要接口但不要将空页面呈现为已可用功能。

验收应包含真实无头服务器、无 SSH Config 的手动添加、端口占用、OAuth 成功与失败/断线、交互终端隐私、安装失败诊断、备份与恢复，以及新手独立操作观察。对未覆盖的操作系统、Harness 版本、渠道和安装方式如实标注，不作普适承诺。

## 10. 范围与保留原则

本方案扩展安装和管理，不自动变成 Harness 记忆引擎、托管平台、整机备份或第三方安全认证。公开金库格式、独立恢复、标准加密、只追加金库、最小暴露和不擅自改写活动状态等既有原则，除非未来另有明确决定，继续有效。恢复时仍应维护完整性检查、确认、日志和回退。

本文不是关于新功能已经实现、已安全或已完成靶机验收的声明。新建架构和协议前应先调查现有实现，沿用可用能力并标明差距。

## 12. 尚需定稿的问题

- 首次启动中所谓 Valise 登录密码是否确有独立用途，能否与钥匙口令避免重复；钥匙备份的具体完成判据。
- 各平台系统钥匙串的可用性、回退方案、SSH 密码与私钥处理、主机身份确认和变更流程。
- OpenClaw 具体版本和安装方式、管理员权限、依赖及各供应商 OAuth/设备码流程的真实验证矩阵。
- 官方方案与用户/AI 提供脚本的执行协议：脚本查看、混淆判定、动态下载、风险分级和多次确认的具体规则；不可将检测视为安全证明。
- 原生交互终端的 PTY、断线恢复、输入回显、日志、敏感信息及生命周期；高级入口的具体授权范围。
- 管理方 Skill 与客户端的接口、身份和授权方式，以及其与现有受管方 Skill/服务端接口的隔离和发现机制。
- 通用转发在不同监听方向、固定端口占用、浏览器回调失败和会话终止时的实现及体验。
- 教学快照元数据与格式兼容、标记命名，以及恢复演练如何隔离并避免误解为完整业务恢复。
- 定时任务默认周期、失败通知、空间站支持的协议和凭据边界、本地导出覆盖范围和文件权限。
- Profile 动作 schema、来源与信任、命令解释、权限/确认、执行输出和兼容版本；避免引入无约束解释器。
- 工具安装、推荐仓库及后续沙盒的范围、排序和风险边界。

这些问题需在对应阶段设计与验证，不应由开发 Agent 把未定事项当成已批准的实现细节自行扩大范围。

## 13. 2026-11-01 讨论后的决定（已写入规范）

- **安装脚本**：只执行签名资料包中的官方方案；来源锁定版本，脚本由客户端下载、核对 SHA-256、全文展示、确认后上传再执行，禁止管道直接执行（INSTALL.md 第 3 节、CLAUDE.md）。
- **SSH 接入**：不保存 SSH 密码，也不接系统钥匙串；引导时密码只用一次，换成 Valise 的日常钥匙；管理操作用可选的管理钥匙（单独的管理口令，默认不创建），或每次用服务器密码临时登录。Valise 自己的 `ssh_config` 交给系统 OpenSSH（ARCHITECTURE.md 第 2.1、3 节）。
- **第 12 节第 1 条（Valise 登录密码）**：不设独立登录密码；敏感操作必须出示管理登录（管理口令解锁管理钥匙，带时间窗口；或服务器密码）；工具安装、原生界面必须解锁且新开独立连接，不复用日常通道。限制由 OpenSSH 与 porter 代码执行（ARCHITECTURE.md 第 2.1 节）。
- **第 8.1 节卡片**：标准图标 24×12、紧凑 12×6，卡片统一尺寸、横向翻页；内置机器人图标由用户绘制（UI.md 8.1）。随 M12 的 TUI 改版实现，之前图标一律占位。
- **依赖安装**：默认只检测与说明；用户可以开启完全访问模式，由 Valise 代为安装运行时与依赖（含 sudo）。开启需要 Valise 口令与管理口令的挑战和免责确认，管理钥匙窗口到期后要重新验证；明显有害的命令一律不执行，用户坚持时只能自己去服务器执行（INSTALL.md 4.1）。
- **端口冲突**：说明占用原因；建议释放端口再试；harness 支持时，用户可以同意"两边一起改端口"，即用 harness 自己的命令改服务器端口，本机同步使用新端口（LOGIN_RELAY.md 4.2）。
- **里程碑**：M7a.2 冻结，M7b 暂停到 M12 之后，新增 M9–M15（DEV_PLAN.md）。
- **第 12 节其余条目**在对应里程碑开工时设计，届时先改规范再写代码。
