### 1.1 共享服务层的产品职责（2026-11-05）

GUI 为最终用户交付，TUI 为资源紧凑环境的交互入口，CLI 与管理方 MCP 服务自动化。各入口调用同一 Go 服务层；不解析 CLI 人类输出、不将认证与自动同步等业务只留在 TUI。保留 `client/ui/service` 作为现有边界，按职责扩展，不因名称含 ui 就重写或移动整个后端。

| 服务职责 | 提供的事实和操作 | 边界 |
| :--- | :--- | :--- |
| Agent 与接入 | 跨服务器列表、安装归属、原生入口、运行和保护摘要、发现及接入流程 | 服务器、安装和 Agent 关系保留；一个共享服务的影响范围由后端计算 |
| 保护计划与旅程 | 用户确认的默认保护、定时安排、实际覆盖、时间点与副本、恢复来源 | 计划不是文件分类；旅程索引不是备份权威数据 |
| 任务、授权与结果 | 冻结计划、权限要求、阶段进度、取消条件、断连后查询及分别复核的结果 | 复用恢复与 B03 各自日志，不构造通用脚本或工作流解释器 |
| 客户端核心与 porter | 钥匙、SSH、转发、解密、远端探测、安装、备份、暂存、校验和交换 | 保留按需执行与三级权限，不新增远端端口或常驻 Web 服务 |

现有 context、进度回调、`UserError` 和认证路由继续复用。返回交互子进程或需要 PTY 的方法须做入口适配，不能直接当作任意 JSON API。GUI 必须完成自己的认证、原生终端、任务生命周期和进度绑定。

## 2. 传输

- **控制面**：`ssh -T <host> "<porter_path> rpc"` 启动一个会话级子进程，通过 stdin/stdout 交换单行 JSON-RPC 2.0 消息。首个请求必须是 `hello`，返回 porter 版本、协议版本、架构、HOME 路径、可用工具（`systemctl --user`、`git`、`npm`、`uv`、`rsync`、`rclone`；按登录环境的 PATH 查找，与登记、复活一致），以及**未完成的交换日志**。协议主版本不一致时，客户端拒绝继续。耗时的调用（目前是建立备份）在返回之前，porter 可以发送没有 id 的 `progress` 通知（`{"id": 请求 id, "stage", "done", "total"}`），客户端用它显示进度；不认识的客户端按 JSON-RPC 规则忽略通知。交换日志的内容格式在 M4 定义；在此之前，`hello` 只按 `journal/` 目录中的 `<op_id>.json` 文件名列出 op_id。
- **数据面**：大数据流使用独立的一次性 SSH 调用，例如 `porter blob-read`（加密 blob 从服务器流向客户端）和 `porter stage-write --op <id>`（复活时，明文 tar 流从客户端流向服务器）。明文只会出现在客户端内存中，以及目标服务器的暂存目录里。
- **连接复用**：优先复用用户已有的 ControlMaster；没有时，使用 `-o ControlMaster=auto -o ControlPath=<客户端缓存目录>/cm-%C -o ControlPersist=60`。Unix 套接字路径有长度上限（macOS 为 104 字节，OpenSSH 建立 master 时还会追加约 17 字节的临时后缀），缓存目录过长时改用 `/tmp/valise-<uid>`（必须是本人所有、权限 0700 的真实目录）；仍不满足时不使用连接复用。
- **主连接按访问级别分开命名**：OpenSSH 只按主机、端口、用户区分主连接，复用时不看用的是哪把钥匙。日常钥匙的主连接套接字用 `cmd-%C`，你自己 SSH 设置的用 `cm-%C`，管理操作用一次性的 `op-<随机>`，三者绝不互相复用（M10 真机发现：两个配置目录都退回 `/tmp/valise-<uid>` 时，完整登录复用了日常钥匙的主连接）。
- **连接与保活超时**（2026-11-09，用户反馈：换网络后已有服务器全部读不到）：Valise 发起的每条 ssh 都带 `-o ConnectTimeout=15 -o ServerAliveInterval=10 -o ServerAliveCountMax=3`。连不上的服务器 15 秒内失败；网络变化后已经断掉、却还挂着的复用连接约 30 秒内被发现并结束，下次新开连接，而不是一直卡住。读取 Agent 清单时每台服务器单独限时 30 秒，一台不回应不影响其他服务器的结果，超时记为 `server_timeout`（界面算“离线”）。
- **只有日常钥匙使用持续的连接复用**：管理操作每次新开自己的连接（`-o IdentitiesOnly=yes`，不连到日常钥匙的 ControlMaster），需要时只为这一次操作开临时 ControlMaster，结束即关（第 2.1 节）。
- **协议版本**：格式为 `<主>.<次>`，当前为 `1.3`（1.1：M10 的访问级别；1.2：M11 的 `install_check`、`install_audit`、`entry_port_set`；1.3：B03 固定配置事务、操作状态与恢复）。主版本号不一致时客户端拒绝继续；次版本号只表示向后兼容的新增。
- **porter 部署**：客户端从 GitHub Release 下载目标架构的二进制，用随客户端发布的公钥校验 `SHA256SUMS` 的 minisign 签名，再核对哈希；或者由用户显式选择本地构建产物。上传时先执行 `cat > ~/.local/bin/valise-porter.tmp`，再 `chmod 0755`，最后 `mv` 原子替换。客户端按服务器记下所部署文件的 SHA-256（找回 Valise 口令时用来核对 porter，第 3.2 节；2026-11-09）。
  - Release 资产命名：`valise-porter_linux_amd64`、`valise-porter_linux_arm64`、`SHA256SUMS`（`sha256sum` 输出格式）、`SHA256SUMS.minisig`。远端架构由 `uname -s -m` 判定，只支持 Linux 的 `x86_64` / `aarch64`。
  - minisign 校验：同时接受预哈希（`ED`，BLAKE2b-512）与旧版（`Ed`）签名，并且必须校验 trusted comment 的全局签名。签名公钥随客户端发布；客户端尚未配置发布公钥时，拒绝从 Release 部署，只允许上传本地构建产物。
  - 在 `chmod` 与 `mv` 之间，执行 `valise-porter.tmp version --json`：确认它能在目标架构上运行，并且它自报的 SHA-256 与本地文件一致，才执行 `mv`。任何一步失败都不替换已有的 porter。
  - 部署目标固定为 `~/.local/bin/valise-porter`，全程不使用 sudo。首次部署在添加服务器的引导登录中完成（第 3 节），之后的更新是管理操作。
  - **检查更新**（`valise porter check`）：客户端经 GitHub API 列出 Release，取 tag 形如 `v<主>.<次>.<修订>` 的正式版（与资料包的 `profiles-*` 区分，草稿与预发布不算），按数字比较，发现比服务器上更新的 porter 时提示，用户确认后按上述流程更新；不自动更新。发布签名公钥尚未配置的开发构建，界面不显示"一键部署"，只提供"上传本地构建"，不把尚未建立的发布链描述为可用。

### 2.1 日常钥匙、管理登录与操作分级（2026-11-01 用户决定）

目的：打开 Valise 不等于拿到服务器的完整权限。敏感操作必须另外出示一个秘密（管理口令，或服务器密码），并且这一限制由 OpenSSH 与 porter 的代码执行，而不是只靠界面。

**日常钥匙**（每台 Valise 管理的服务器都有）：
- 生成：`ssh-keygen -t ed25519 -N ''`，存于 `<客户端数据目录>/keys/<服务器>/daily`（0600）。
- 服务器端：`authorized_keys` 中一行 `restrict,pty,port-forwarding,permitlisten="127.0.0.1:1",permitopen="127.0.0.1:*",permitopen="[::1]:*",command="$HOME/.local/bin/valise-porter serve --tier daily" <公钥> valise-daily@<本机名>`（注释里的本机名用来分辨是哪台电脑的钥匙；安装时按公钥本身去重，只替换同一把钥匙，别的电脑或别名装的 Valise 钥匙不受影响）。`port-forwarding` 会同时放开远程转发（`-R`），而 `authorized_keys` 的 `permitlisten` 不接受 `none`（写了整行钥匙失效），所以只允许监听特权端口 1：普通用户的 sshd 子进程绑定不了它，远程转发因此全部失败（M10 在 OpenSSH 10.2 / 10.5 / 10.0 上实测）。`pty`（2026-11-02 用户同意）让登录授权的 `login-run` 能在终端里运行，强制命令照样决定运行什么，拿不到 shell；此前装的钥匙没有 `pty`，客户端在 `servers.json` 中以 `daily_tty` 区分，旧格式的服务器登录授权仍走开发者模式，服务器设置里提示"按 K 重新装一次"。TrueNAS 默认 `AllowTcpForwarding no`，这时任何钥匙都不能转发，管理页与本地页面转发不可用（NAS 上通常也不跑 harness）。
- 能做什么：第 2.2 节的日常操作，以及转发到服务器本机回环端口；拿不到 shell。可以使用 ControlMaster 复用连接。
- **限制必须真正生效才用**（M10 在 InstaBox 上发现：它的 SSH 网关用 `none` 认证放行任何人，根本不看机器上的 `authorized_keys`，日常钥匙在那里等于完整登录，而且该用户有免密 sudo）。添加或迁移时：先试一次不带任何凭据的登录，能登进去就拒绝使用日常钥匙；装好日常钥匙后再用它执行一条普通 shell 命令，若被执行（强制命令没生效），立即从服务器撤掉刚装的钥匙、恢复原来的记录并拒绝。两种情况都提示用户继续用自己的 SSH 设置接入，并说明这台服务器本身的登录风险。
- porter 的日常模式：`serve --tier daily` 读取 `SSH_ORIGINAL_COMMAND`，只允许 `rpc`、`blob-read`、`vault-cat`、`version`，以及带一次性许可的 `stage-write`、`login-run`（2.2 节）；`rpc` 中的主人操作要先完成主人证明，开发者模式的方法一律返回"需要管理权限"。即使日常钥匙被盗，没有 Valise 口令也不能恢复、删除、改收件人或改同步目标。

**管理登录**（执行管理操作时出示，两种方式任选）：
- **管理钥匙（默认用 Valise 口令创建，2026-11-16 统管简化）**：添加服务器时若客户端已设置 Valise 口令，默认勾选一并创建管理钥匙并直接用当前 Valise 口令加密，无需再记忆第二套管理口令（若此时尚未设置 Valise 口令，保持可选创建或之后在服务器设置中一键补齐）。
  - 生成：`ssh-keygen -t ed25519 -N <口令>`，存于 `keys/<服务器>/admin`（0600）；服务器端是普通一行 `<公钥> valise-admin@<本机名>`。私钥加密由 OpenSSH 完成，Valise 不自研。
  - **口令统一与兼容（2026-11-16 用户决定）**：取消“管理口令必须与 Valise 口令不同”的限制；管理钥匙默认直接使用用户的 **Valise 口令**加密。早期版本已用独立管理口令创建的钥匙仍可正常解锁（输入原管理口令即放行），且在设置页提供一键同步/重办为 Valise 口令的入口；修改 Valise 口令时一并重加密使用统一口令的管理钥匙。
  - **联动解锁与时间窗口**：在未启用快捷解锁的模式下，输入一次 Valise 口令验证通过后，内存同时保留 `keystore.age` 解密身份，并顺带尝试将该口令加密的各台服务器管理钥匙加载进 **Valise 自己启动的 ssh-agent**；反之仅需管理钥匙且已同口令解锁时，同样不再重复索要口令。默认时间窗口为 **30 分钟**（设置中可改为 1–240 分钟）；到期自动清除，退出 Valise 时结束 ssh-agent 并清理内存。
  - **本机 6 位 PIN 码快捷解锁（2026-11-16 用户决定，Phase B2）**：`keystore.age` 与离线恢复套件始终使用标准 `age` 与完整 Valise 口令，保证脱离 Valise 可独立解密；用户可在设置页选择启用本机 6 位数字 PIN（默认关闭，不强迫启用），开启后客户端以随机盐 + 标准 `age/scrypt` 将解锁材料封装保存在本机 `pin-unlock.age`（0600，不随 `valise-config.json` 导出）。**触发频率规则**：未启用快捷解锁时沿用 **30 分钟**免输窗口；启用 6 位 PIN（或后续系统钥匙串/生物识别、1Password CLI 联动扩展）后，**每次触发主人操作或管理钥匙解锁均弹出 6 位 PIN 校验框**，操作结束后不保留长免输窗口；**防爆破**：连续输错 5 次立即销毁本机 `pin-unlock.age`，退回要求输入完整 Valise 口令。
  - **本机文件**：`pin-unlock.age` 用 age 自带随机盐的 scrypt 加密一把仅用于快捷解锁的本机身份。`pin-state.json` 记录失败计数、以该身份加密的 Valise 口令，以及用完整口令加密的本机公钥，供改口令时核对并更新。两个文件权限均为 0600，不纳入配置导出；修改完整口令时更新加密的口令，找回口令时关闭快捷解锁。5 次计数限制适用于通过 Valise 输入，无法限制对复制出去的本机文件进行离线尝试。
- **临时登录**（没有管理钥匙时）：每次管理操作都用服务器密码（或用户自己的私钥）新登录一次，密码只在 OpenSSH 自己的提示中输入（GUI 经 Valise 的 askpass 转交，只在内存中经过），不保存，没有时间窗口。
- **连接隔离**：每次管理操作新开自己的连接，绝不复用日常钥匙的连接或任何已有连接；一次操作需要多次调用（例如恢复）时，为这一次操作开一个临时 ControlMaster（套接字名 `op-<随机>`），操作结束立即关闭，万一没有关闭，闲置 120 秒后由 OpenSSH 自动结束。原生界面、harness 安装与工具安装都是一次操作一条独立连接。
- **客户端的实现细节**（M10 确定）：
  - 管理口令经 askpass 交给 OpenSSH 工具：`SSH_ASKPASS` 指向 Valise 自己的可执行文件，口令放在只传给这一个子进程的环境变量里（同一用户的进程才能读到，与钥匙文件的保护相同）；口令错误时 askpass 回答空，让 `ssh-add` 放弃而不是反复询问。
  - Valise 的 ssh-agent 属于一个 Valise 进程：TUI / GUI 在整个运行期间共享时间窗口；CLI 每条命令是一个进程，窗口只在这条命令内有效。
  - **GUI 的密码转交**（2026-11-08 用户决定，2026-11-16 补齐 `userTransport`）：桌面版在进程内开一个只属于本进程的本机通道（Unix 套接字，放在 0700 的临时目录里，另带一次性随机令牌）。需要服务器密码或私钥口令（passphrase）的 ssh 子进程——包括手动引导连接、管理钥匙/临时登录连接，以及**从 `~/.ssh/config` 导入的服务器连接（`userTransport`，当 GUI 可弹窗 `canPrompt` 时同样关闭 `BatchMode` 并挂载 `relayEnv()`）**——均带上 `SSH_ASKPASS`（Valise 自己的可执行文件，转交模式）、`SSH_ASKPASS_REQUIRE=force`、通道位置与令牌；OpenSSH 要密码或私钥口令时调用它，它把 OpenSSH 的原始提问经通道交给窗口，窗口弹框问用户（识别 `passphrase` 时提示输入私钥口令），答案原路交回 OpenSSH。密码只在内存里经过：不写文件、不进环境变量、不进日志；用户取消时转交程序以失败退出，OpenSSH 随之放弃。Valise 日常钥匙本身无口令，其连接仍保持 `BatchMode=yes`，从不询问。
  - TUI 运行时 OpenSSH 无法在终端里询问服务器密码：需要临时登录的管理操作在 TUI 中直接提示"创建管理钥匙或在命令行执行"；管理口令由 TUI 的掩码输入框询问。CLI 中由 OpenSSH 自己询问密码。
  - "自带钥匙"服务器的软限制只在界面（TUI / GUI）中实施，留到界面改版；CLI 用户本来就能直接 `ssh`，CLI 不加软限制。

**其他规则**：
- **Valise 主口令（2026-11-16 统一）**：用户只需维护一套 Valise 口令，同时保护加密钥匙（`keystore.age`）与默认随其加密的服务器管理钥匙；服务端权限隔离仍由日常钥匙 `authorized_keys` 强制命令、管理钥匙独立 SSH 连接及 porter 分级权限代码共同保证。Valise 不另设登录密码。
- **自带钥匙的服务器**：经用户自己的 `~/.ssh/config` 别名接入、未迁移到 Valise 日常钥匙的服务器，Valise 无法在服务器端设限。界面（不含 CLI）标明"软限制"：管理操作前要求输入管理口令（已创建时）或 Valise 口令（已设置时）确认，两者都没有时只做文字确认；并提供"迁移到 Valise 日常钥匙"。
- **如实说明的局限**：管理钥匙解锁期间，本机若已有恶意程序，它可以使用 ssh-agent 中的钥匙；这套分级防的是"别人打开你开着的 Valise"和"agent 借客户端越权"。Windows 上 ssh-agent 是系统服务，Valise 自启 agent 的方式 `verify: pending`，未核实前 Windows 版每次管理操作都直接要求管理口令、不提供时间窗口。

### 2.2 操作分级（2026-11-02 用户决定改为三级）

管理钥匙在概念上是**开发者模式钥匙**：只拦有安全风险的操作，不能成为基本功能的门槛。日常钥匙在本机没有口令保护，所以会写入 agent 目录或改变备份去向的基本操作，需要证明"你是主人"，这一级用用户本来就有的 **Valise 口令**，不需要管理钥匙。

- **日常操作**（只要日常钥匙）：`hello`/doctor、状态与实例列表、登记报告（只读）、建立备份、同步到远程备份位置、远程备份位置列表、体检、`seal_log`、拉取与校验、技能状态、定时器状态、管理页隧道（不含令牌）、本地页面转发、只读且不输出机密的管理动作、追加审计记录（`install_audit`：管理操作结束后补记，不能因为管理窗口到期而丢失；它只追加，不改变任何受保护的东西）、**首次给服务器起名**（起好后 porter 拒绝修改），以及**服务器上还没有任何收件人时登记第一把加密公钥**（此前没有任何备份可被泄露）。
- **主人操作**（日常钥匙 + Valise 口令证明）：恢复（含 resume）、安装或卸载技能、接受登记与归档建议、重新接入、设置周期与定时器、添加或修改同步目标与自动同步、增加收件人、登录授权、代取管理页令牌、`manage` 风险的管理动作与输出机密的只读动作、服务启停、**不敏感的删除**（见下）。
- **开发者模式**（管理登录：管理钥匙或服务器密码）：服务器终端、原生界面、harness 安装、工具安装、`config` / `danger` 风险的管理动作、更新 porter、两边一起改端口、移除收件人、**敏感的删除**、创建管理钥匙、迁移到日常钥匙。
- **主人证明**（由 porter 执行，不只是界面）：在日常连接中，客户端调用 `owner_challenge`，porter 生成 32 字节随机数，用标准 age 加密给 `recipients.txt` 中的全部收件人后返回；客户端用 `keystore.age` 中的身份解密（需要 Valise 口令，或在启用本机 PIN 时按 PIN 快捷解开），以 `owner_prove` 回传；porter 以常数时间比较，正确后**本次会话**开放主人操作。服务器还没有收件人时无法证明，提示先登记加密钥匙。只用 age，不涉及自研密码学。未启用快捷解锁时客户端解开的身份在内存中保持与管理钥匙相同的免输时间窗口（默认 **30 分钟**），启用 6 位 PIN 后每次触发主人操作重新验证 PIN，退出 Valise 即清除；CLI 每条命令单独询问。
- **主人操作需要的独立子命令**（`stage-write`、`login-run`）：日常强制命令只在出示一次性许可时放行。许可由已证明的会话调用 `owner_grant` 签发：porter 生成随机令牌，在私有目录记录"子命令 + 参数（如 op_id）+ 5 分钟有效期"，子命令带 `--grant <令牌>` 运行时核对并立即作废。
- **删除分级**（判断依据：删掉以后还能不能找回）：
  - 不敏感（主人操作，加一次确认）：已结束、并且其中每个备份在至少一个远程备份位置上都有副本的服务器周期；已结束、服务器上仍有同一周期的远程备份位置周期；7 天前的"恢复前的样子"（`prev drop`）；7 天前遗留的暂存目录。
  - 敏感（开发者模式，加输入名称确认）：别处没有副本的已结束周期、7 天内的“恢复前的样子”、旧实例清理、移除收件人。正在写入的当前周期禁止删除，不能用更高权限绕过 VAULT_FORMAT.md 10.4 的约束。
  - 是否敏感由 porter 按服务器上的记录判断（同步记录、周期是否结束、文件时间），客户端不能自称"别处有副本"；本机仓库只有客户端知道，不计入服务器的判断。
- 访问级别记入审计（`daily` / `owner` / `admin`）。
- **高级模式**（INSTALL.md 4.1）：在管理操作之上，允许 Valise 代为执行运行时与依赖的安装（含 sudo）。前提是已创建管理钥匙；开启需验证 Valise 口令（并确认该服务器的管理钥匙可解锁；对使用历史独立管理口令的服务器同时校验该口令）并确认免责；管理钥匙窗口到期后暂停，重新验证后才继续。明显有害的命令在任何模式下都不执行。
- 新增 RPC 方法时必须在 `core/rpc` 中显式归入一级；未归类的方法按开发者模式处理。

### 2.3 删除服务器（2026-11-09 用户决定，已实现：N4“服务器设置与删除”段）

两层，界面上二选一：

- **只从这台电脑移除**：删掉这台电脑上的入口（服务器列表中的记录、这台服务器的用户通行证与管理员通行证的本机文件、Valise known_hosts 中的条目），服务器上什么都不动，以后可以重新添加。服务器连不上时只有这一层，并列出服务器上还留着的 Valise 东西（按最后一次读到的情况）。
- **移除并清理服务器上的 Valise 东西**：需要一次管理登录。逐项勾选，默认勾上：服务器 `authorized_keys` 里的用户通行证与管理员通行证、porter、保护计划的定时备份任务（停止后不再自动备份）、工具箱装的工具、云盘授权（服务器上 Valise 的 rclone 配置）。各 Agent 的保护技能（与 MCP 配置片段）单独列出、默认不勾，写明“不建议：Agent 还在用”，勾上即按 AGENT_KIT.md 的卸载规则删除；允许彻底清除，但不推荐。Agent 本身与它的文件一律不动。清理按先停任务、再删工具与技能、最后撤通行证与 porter 的顺序执行，每项结果单独写；中途失败就停下，写明哪些已清、哪些还在。
- **备份库一律保留**：清理时在服务器的 `server.json` 写入 `removed_at`（可选字段，旧版本忽略，VAULT_FORMAT.md 第 10 节），这台电脑的记录里保留服务器名并标为“已删除的服务器”；备份位置、旅程与备份列表照常显示这些备份并带此标记。服务器移除流程不会代用户删除周期。手动删除见第 2.2 节，定时退役见 VAULT_FORMAT.md 10.4。重新添加同一台服务器时清除标记。
- **忘记已删除的服务器**（2026-11-09 用户决定）：“已删除的服务器”里的每条记录可以“忘记”，比如那台服务器已经重装或不存在了。忘记只删这台电脑上的这条记录（`removed-servers.json` 与它在 `server-leftovers.json` 里的那一项），不碰任何备份：服务器上的备份库、备份位置里的副本都还在，只是这台电脑不再在服务器页和备份位置页列出它们；确认框写明这一点。以后再添加同一台服务器，或从备份位置恢复，仍能用这些备份。
- **实现**（2026-11-09）：服务器端的“停定时备份、写 `removed_at`、删 porter”是 porter 的管理方法 `server_leave`（逐步调用，只在管理登录下可用）；工具、云盘授权、保护技能用各自已有的方法，通行证用与添加服务器相同的固定脚本从 `authorized_keys` 删去。这台电脑上的记录：`removed-servers.json`（名字、服务器名、时间、是否已清理、未清理时留下的东西、重新添加用的连接信息，不含秘密）与 `server-leftovers.json`（每次读到的服务器上的 Valise 东西）。

## 3. Keystore

- **身份**：使用 age 原生的 X25519 身份（`AGE-SECRET-KEY-1…`），以 age 口令加密（scrypt）的形式保存为 `keystore.age`。用户随时可以用标准命令 `age -d keystore.age` 解出身份，**不依赖 Valise**。
- **口令**：至少 12 位。scrypt 工作因子使用 age 的默认值，不得调低。
- **收件人**：对应的 `age1…` 公钥登记到服务器的 `recipients.txt`。支持多个收件人，例如再加一把离线纸质备份钥匙。
- **指纹**：收件人公钥字符串（`age1…`）的 SHA-256 十六进制值的前 16 位。`VAULT` 中的 `recipient_fingerprints` 使用同一定义。
- **口令长度**：按 Unicode 字符计数，至少 12 个字符。
- **客户端数据目录**：`os.UserConfigDir()/valise/`（macOS 为 `~/Library/Application Support/valise/`，Linux 为 `~/.config/valise/`），其中包括 `keystore.age`、`config.json`、`servers.json`、`ssh_config`、`known_hosts` 与 `keys/`。ControlMaster 套接字与 Valise 的 ssh-agent 套接字放在 `os.UserCacheDir()/valise/` 下。
- **已记录服务器**：`servers.json` 保存服务器列表，每项为 `{"name": "<别名>", "source": "valise" | "ssh_config"}`。
  - `valise`：手动添加的服务器。`servers.json` 中记录地址、端口、用户名与临时登录方式（`login: password | key`，`key` 时只记私钥文件的路径）；Valise 由它生成自己的 `ssh_config`（`Host <别名>`、`HostName`、`Port`、`User`、`UserKnownHostsFile <客户端数据目录>/known_hosts`、`StrictHostKeyChecking yes`），每次调用 OpenSSH 时用 `-F` 传入；用户的 `~/.ssh/config` 不被修改。钥匙不写进 `ssh_config`，而是按访问级别在命令行上传入（日常：`-i daily -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes`；管理钥匙：`-i admin` 加 Valise 的 ssh-agent；临时登录：`-o PubkeyAuthentication=no` 或用户的私钥文件），这样临时登录不会退回到日常钥匙。从 `~/.ssh/config` 迁移时，如果用户的 `IdentityFile` 是公钥（私钥在 1Password 等密码管理器的 agent 里），同时记下该配置的 `IdentityAgent`（`login_agent`，未配置时为环境中的 `SSH_AUTH_SOCK`），只在这类临时登录中使用；日常钥匙与远程备份位置钥匙一律 `IdentityAgent=none`。不保存任何密码。
  - `ssh_config`：从用户 `~/.ssh/config` 导入的别名（只列具体的 `Host`，跳过通配符），连接参数与密钥交给用户自己的配置。
  - CLI 仍然接受任意别名，不要求先记录；界面只列已记录的服务器。旧版只含别名字符串的 `servers.json` 读作 `ssh_config` 来源。服务器上的实例由 RPC `instance_list` 列出。
- **添加服务器**（2026-11-01 改版）：每一步失败都停在该步并给出原因与建议。
  1. **连接方式**：手动填写（地址、端口，默认 22、用户名、登录方式：密码或已有私钥文件、用户自选的别名），或从 SSH 配置导入。
  2. **确认服务器身份**：首次连接时展示主机密钥指纹（SHA256），说明"第一次连接无法自动验证，请与服务商控制台显示的指纹比对，或确认网络可信"，用户确认后写入 Valise 的 `known_hosts`。之后指纹变化一律停止，说明可能的原因（重装系统、中间人），由用户决定。
  3. **引导登录**（`valise` 来源）：用密码或用户私钥登录**一次**，为这次引导开一个临时 ControlMaster，以下 3–6 步共用，引导结束立即关闭。密码只在 OpenSSH 自己的提示中输入（TUI 把终端交给 ssh；GUI 用 Valise 的 askpass 程序转交，只在内存中经过），不保存。
     - 经标准输入发送 Valise 自带的固定脚本，把日常钥匙的公钥追加到 `~/.ssh/authorized_keys`（目录与文件权限按 OpenSSH 要求设为 0700 / 0600，已存在同注释的旧行先替换）；勾选了“同时创建管理钥匙”时（已设 Valise 口令时默认勾选，并直接用该口令加密），一并安装管理钥匙的公钥。
     - `ssh_config` 来源的服务器可选"迁移到 Valise 日常钥匙"，同样步骤。
  4. **体检服务器**（`doctor`）。
  5. **部署 Valise 服务端**：没有 porter 时提供"一键部署"（第 2 节），在引导登录中完成。日常钥匙的强制命令固定指向部署目标 `$HOME/.local/bin/valise-porter`，所以在部署之前就能写好。
  6. **登记加密公钥**（`key register`，注释写本机名与日期）：加密钥匙已存在时在引导登录中完成；用户在第一次启动时跳过了钥匙时，第一次建立备份前补上（此时服务器上还没有收件人，日常钥匙即可登记第一把，见 2.2 节）。
  引导结束后日常操作一律用日常钥匙；管理操作用管理钥匙或临时登录（2.1 节）。
  7. **确定服务器名**（写入 `server.json`，默认等于别名，用作备份位置里的目录名）。**改名**（2026-11-02 用户决定）：改名前列出会改动的东西——服务器上的 `server.json`、每个本机仓库里的 `<仓库>/<旧名>`、每个远程备份位置上的 `<旧名>`，并说明远程备份位置给这台服务器的证书会重新签发（证书只允许写自己的目录）；用户确认后由客户端逐项改名，中途失败可重试；当时连不上的远程备份位置记下来，下次同步前补做。
  8. **发现 harness**：已有的 agent 可以直接接入 Valise（登记）；没有时引导安装第一个 harness（INSTALL.md）。两条路都可达，不强迫已有用户重装。
  多把钥匙、移除公钥等收件人管理放在设置的"高级"中，并用大白话说明后果。
- **第一次启动**：建议设置 Valise 口令与加密钥匙并备份，但允许暂时跳过，直接去添加服务器。添加服务器本身不需要先设加密钥匙；已设好 Valise 口令后，添加服务器默认用同一口令一并生成管理钥匙。
  - 第一次建立备份前，必须走完"备份钥匙"引导：导出恢复套件，或明确选择"我知道风险，稍后备份"（界面写明：口令或钥匙丢失后，所有备份都无法打开）。
- **离线恢复套件**：导出内容包括 `keystore.age`、收件人公钥、指纹，以及一页恢复说明（指向 `tools/standalone-restore/`）。导出为一个目录，内含 `keystore.age`、`recipient.txt`、`FINGERPRINT`、`RECOVERY.md`。导入时核对指纹：先确认 `FINGERPRINT` 与 `recipient.txt` 一致，解锁后再确认身份对应的公钥与 `recipient.txt` 一致，并把指纹展示给用户，与纸质记录比对。
- **内存处理**：解锁后的身份封装在 `UnlockedKey` 中，`Lock()` 时尽力清零。文档和 UI 中要如实说明：Go 的垃圾回收可能产生副本，无法保证彻底清除。未启用快捷解锁时 UI 空闲默认 **30 分钟**后自动锁定（可在 1–240 分钟间配置）；启用 6 位 PIN 快捷解锁时每次操作后不保留长免输窗口。


### 3.1 导出与导入配置（2026-11-01 用户决定）

换电脑时带走"记录"，不带走任何钥匙。

- **内容**：已记录服务器（`servers.json` 的全部字段：别名、来源、地址、端口、用户名、登录方式、私钥文件路径）、这些手动服务器在 Valise `known_hosts` 中的主机密钥（公开信息，导入后仍能识别冒充者）、设置（目前只有管理窗口时长；`ssh_binary` 等与机器有关的设置不导出）。不包含 `keystore.age`、日常钥匙、管理钥匙、密码或任何秘密；加密钥匙只通过恢复套件（第 3 节）迁移。
- **格式**：一个明文 JSON 文件（默认名 `valise-config.json`，权限 0600），`{"format": "valise-config", "version": 1, "exported_at", "servers": [...], "known_hosts": ["<field> <type> <base64>", ...], "settings": {"admin_window_minutes"}}`。不加密：里面没有秘钥，但有服务器地址和用户名，导出时提醒不要公开分享。导出不覆盖已有文件。
- **导入**：只添加这台电脑上没有的服务器；同名服务器无论内容是否相同都不覆盖，内容不同的跳过并在结束时列出。手动服务器的主机密钥只在这台电脑还没有该地址的密钥时写入。管理窗口时长只在这台电脑未设置时采用。导入的手动服务器没有这台电脑的日常钥匙，需要逐台执行 `valise server rekey <服务器>`（用服务器密码或私钥登录一次，等同于重新走一遍添加服务器的钥匙安装与检查）；来自 `~/.ssh/config` 的服务器要求新电脑的 SSH 配置里有同名 `Host`。
- **CLI**：`valise config export <文件>`、`valise config import <文件>`、`valise server rekey <服务器> [--admin-key]`。

### 3.2 找回 Valise 口令（2026-11-09 用户决定，已实现：N4“钥匙与备份”段）

Valise 口令加密这台电脑的加密钥匙（`keystore.age`）。忘了口令时不能直接“重置”：没有旧口令就打不开钥匙，换新钥匙等于以前的备份全部打不开。所以事先给钥匙留一份**备用锁**，只有“这台电脑上的文件 + 服务器的 root（sudo）”两样同时在手才能打开。默认开启，设置里可以关闭（关闭即删除备用锁文件）。

- **备用锁**（只用标准 age，不自研密码学）：生成一把 age X25519 身份 `R`；加密钥匙的身份用 `R` 再加密一份，存为 `<数据目录>/recovery/key.age`；`R` 本身用 Valise 口令加密保存（`recovery/r.age`），并分别用每台服务器的 SSH 主机公钥（`ssh-ed25519`，age 的标准 SSH 收件人）加密，存为 `recovery/<服务器>.age`。这些文件都只在这台电脑上。主机私钥只有 root 能读，所以只拿到电脑打不开；只有服务器 root 没有这些文件，也打不开。电脑与 root 同时被拿到时能打开，这是开启它的代价，界面如实说明。
- **何时做**：设 Valise 口令时；之后每次输入 Valise 口令时，为还没有备用锁、或主机密钥变了的服务器补做（包装 `R` 需要先用口令解开 `r.age`）。只为有 `ssh-ed25519` 主机密钥的服务器做；没有的写明原因。
- **找回流程**（2026-11-09 用户决定：提前扫描只作提醒，安全靠命令内核对）：
  1. **找回模式**：用户在 Valise 里选“忘记 Valise 口令”，选一台服务器。Valise 进入找回模式：期间不接受 MCP 请求，不运行自动复制与其他后台任务，界面只做这一件事，直到完成或取消。
  2. **提前扫描**（提醒，不是保证）：用用户通行证读服务器上 porter 的版本与 SHA-256，与这台电脑记录的预期值比对；对不上、或这台电脑没有预期值时停下，提示先重新部署 porter（部署是开发者模式，用管理员通行证或服务器密码，与 Valise 口令无关）。说明为什么只是提醒：读取要经过 porter 本身，被替换的 porter 可以谎报；检查与运行之间文件也可能被换。
  3. **请求**：客户端在内存里生成一次性 age 身份 `E`，用用户通行证把 `recovery/<服务器>.age` 与 `E` 的公钥写进服务器上本用户的暂存目录，附请求编号。
  4. **用户自己运行 sudo 命令**（全文展示，Valise 从不代为执行，高级模式也不行，因为它要证明的就是“服务器上的人”）。命令先把 porter 复制到 root 专属的临时文件，核对这份副本的 SHA-256，通过才运行它，结束后删除副本：
     `sudo sh -c 'f=$(mktemp) && cat <porter 路径> > "$f" && echo "<SHA-256>  $f" | sha256sum -c --quiet && chmod 700 "$f" && "$f" recovery-code --for <用户>; r=$?; rm "$f"; exit $r'`
     普通账号改不了 root 的副本，所以检查与运行之间没有可钻的空隙。预期 SHA-256 来自这台电脑：部署 porter 时记下所用文件（Release 中该架构的文件，或本地构建）的 SHA-256，按服务器保存。
  5. **porter 读完主机密钥立即放弃 root**：`recovery-code` 以 root 只做一件事：读 `/etc/ssh/ssh_host_ed25519_key`；随后降为 `--for` 指定的用户（须与 `SUDO_USER` 一致），之后读请求、写结果都以该用户身份进行，打开文件不跟随符号链接。用主机密钥解开 `R`，用 `E` 的公钥重新加密，写回暂存目录（0600），在终端显示 8 位验证码（由请求编号与写回内容算出）。
  6. 用户把验证码填回 Valise（错 3 次这次请求作废，2026-11-09 用户决定）。客户端取回结果并核对验证码，用 `E` 解开 `R`、用 `R` 解开加密钥匙，请用户设新口令，重新加密 `keystore.age`，换一把新的 `R` 重做全部备用锁，删除服务器上的请求与结果文件，退出找回模式。身份不变，服务器上登记的收件人与主人证明照常可用。
- **不能救的**：电脑也丢了（用离线恢复套件）；服务器重装、主机密钥变了（那一份失效，换另一台服务器）；没有 sudo 的服务器。
- **代价（用户已接受）**：任何一台做了备用锁的服务器的 root，加上这台电脑上的文件，就能打开全部备份（包括其他服务器上 Agent 的备份）。用户的判断：服务器 root 被拿到时活数据已经泄露，备份是否防住已无意义；Valise 此时要做的是让用户重装服务器后能从备份恢复 Agent。界面在开启处如实写明。
- **实现**（2026-11-09）：备用锁文件之外，这台电脑记下每台服务器做锁时用的主机公钥（`recovery/state.json`），据此区分“已做 / 主机密钥变了 / 下次输入口令时做 / 不支持”。主机公钥取自 Valise 的 `known_hosts`；来自 `~/.ssh/config` 的服务器取自用户的 `~/.ssh/known_hosts`。请求放在服务器上 `~/.local/state/valise/recovery/<请求编号>.request`，结果写 `<请求编号>.result`（只新建、不覆盖、不跟随符号链接），porter 方法 `recovery_request`、`recovery_result`、`recovery_clear` 属日常级。验证码由请求编号与结果内容算出（`core/recovery`）。找回模式下自动复制暂停；管理方 MCP 尚未实现，所以目前没有要暂停的 MCP 请求。
- **不依赖 Valise**：服务器上有 `age` 时可以不经 porter 手工找回：`sudo age -d -i /etc/ssh/ssh_host_ed25519_key recovery/<服务器>.age` 得到 `R`，再 `age -d -i R recovery/key.age` 得到加密钥匙（RECOVERY.md 写明）。

### 3.3 忘了管理口令 / 统一管理钥匙：重办管理员通行证（2026-11-09 决定，2026-11-16 统一升级）

管理员通行证只管操作权限，不锁任何数据，所以不做恢复，只做重办。新创建的管理员通行证默认直接使用用户的 **Valise 主口令**加密，无需额外独立管理口令；遇到历史独立管理口令遗忘或需把旧服务器钥匙统一为 Valise 口令时，提供“重办管理员通行证”：

1. 使用当前 Valise 口令（尚未设置或希望沿用自定义口令时在重办页明确确认，至少 12 个字符）。
2. 对需要重办的每台服务器，用服务器密码（或用户自己的私钥）临时登录一次，按这台电脑上保留的旧公钥准确删去 `authorized_keys` 里旧的那一行，装上用新口令加密的新通行证；每台结果单独写。
3. 这台电脑上的旧通行证文件删除（已没有口令能打开）。
4. 当时连不上的服务器标为“管理员通行证待重办”，下次连上时提示继续；在此之前，那台服务器的管理操作用服务器密码临时登录。旧公钥保留到那台服务器重办完成，用于删去旧行。

## 4. 登记（全部由代码完成）

1. **探测**：客户端把 profile 集合发给 porter，porter 按每个 profile 的 `detect` 规则（可执行文件、状态目录候选、标记文件）找出候选实例。
2. **解析**：把 profile 的 `paths` 规则展开到真实文件，为每个文件确定类别，并记录未分类的文件。
3. **来源记录**：按 `provenance` 规则读出身体的安装来源与版本，包括 npm 包名、精确版本、registry 和 integrity，git 的 remote、commit 和是否 dirty，uv/pipx 工具的包名与版本，以及二进制的哈希。如果 git 工作树是 dirty 状态，把差异记录为 `body_patch`，随灵魂一起封存。
4. **服务与入口**：确认 service 候选单元是否存在，入口端口是否在监听。
5. **登记报告**：客户端展示各类别的文件数量与大小、未分类文件、凭据文件清单（只列路径）、身体与来源、服务、入口、哪些 profile 条目未核实。用户确认安装事实后写入记录。未知项已在默认备份范围时汇总说明并按敏感内容保存，不要求逐文件分类；不可读内容、目录外引用和实际遗漏单列为覆盖缺口，不把接入成功当作已备份。
6. **agent 补充**（可选）：agent 通过 MCP 提议额外的路径和类别，这些提议以"待确认"状态保存。用户在客户端确认后，才合入实例记录的 `local_overrides`。

实例记录包含：`instance_id`、`profile_id`、`profile_version`、`roots`（解析后的绝对路径）、`provenance`、`service`、`entries`、`local_overrides`、`enrolled_at`，以及被取代时的 `superseded`（见 8.2.1）。harness 升级后再次登记时，展示与上次的差异。实例记录现在是实例档案里一个 agent 的视图（4.1 节）。

### 4.1 实例档案（dossier，2026-11-02 用户决定）

两套资料协作：**通用 profile** 写规则（按官方文档编写、在靶机上核实、随签名资料包分发）；**实例档案**写这台机器上一个 harness 安装的事实（porter 按 profile 的规则检测生成，用户确认后保存，不随任何包分发）。冲突时规则听 profile，事实听档案。

- **文件**：服务器上 `~/.config/valise/dossiers/<install_id>.json`（schema `valise-dossier/1`，0600），旁边 `<install_id>.profile.json` 是登记时通用 profile 的原样副本（不按 agent 改动）。`install_id` 目前等于 profile id（一台服务器上一个 harness 一个安装）。不含任何凭据。
- **内容**：`profile`（id 与版本）、`updated_at`；安装级事实：`provenance`（程序与来源）、`service`、`entries`（以默认 agent 的检测为准）；`agents[]`：每个 agent 的 `instance_id`、`name`、`env`（多实例，PROFILES.md 1.3）、`roots`、`local_overrides`、`entry_ports`、`enrolled_at`、`superseded`，以及之后加入的 `evidence`（在这里成功过的操作，PROFILES.md 1 的核实证据）与读到的审批状态。
- **按 agent 的有效 profile**：由通用 profile 与档案现算（`profile.ForAgent`）：命名 agent 不带 `entries`、`body`、`provenance`，服务只在 `named[].service: shared` 时保留。封存、管理动作、审批检查、登录、恢复都用它。
- **旧记录只读兼容（2026-11-14）**：列表、记录和 profile 查询只读；已有档案优先，没有已提交档案的旧 Agent 仍从 `instances/<id>.json` 及旧 profile 投影，保持未绑定身份，不建立或改写档案。明确的接入/记录写入、改端口等既有写操作才在原互斥内转换其所属安装的旧记录。旧文件改名保留，已有归档不覆盖；显式移除记录时也封存其重复旧记录，避免查询令已移除的 Agent 重新出现。
- **重新检测**：结果与保存的档案不同时，客户端列出差异（版本、新出现的 agent、审批状态等），用户确认后才保存（UI.md 9.x）。
- **显示名**：profile 的 `terms.agent` 是 harness 自己对一个 agent 的叫法（如 Hermes、OpenClaw 都叫 profile）；界面按它显示，内部统一称 agent。

实现细节（M2 确定）：

- **profile 来源**：已安装的签名资料包（PROFILES.md 1.1），另外读取客户端本机的 `os.UserConfigDir()/valise/profiles/*.yaml`（标记为"本地，未经审核"）。porter 自身不携带任何 profile。
- **PATH**：非交互 SSH 的 PATH 通常不包含用户级安装前缀。porter 执行 `detect.binaries`、`version_argv`、`discover_argv` 和来源查询时，使用用户登录 shell 的 PATH（`$SHELL -lc` 读取一次），并补上 `~/.local/bin`。这些命令都设有超时。
- **实例范围**：M2 每种 harness 在每台服务器上只探测默认状态目录（`state_dir_candidates` 中第一个存在且有标记文件的）。harness 自身的多 profile（例如 `~/.hermes/profiles/<name>`、`~/.openclaw-<name>`）推迟处理。
- **instance_id**：默认等于 profile id，可用 `--id` 指定，命名规则与 profile id 相同。
- **嵌套 root**：一个文件只属于包含它的最深的 root。例如工作区位于状态目录内部时，工作区中的文件只按 `workspace` root 的规则分类。
- **分类优先级**：凭据规则（profile 与 `local_overrides` 中的 `secrets`）> `local_overrides` > `body.paths` > `paths` 中第一条命中的规则。
- **SQLite 附属文件**：`consistency.sqlite` 声明的数据库，其 `-wal`、`-shm`、`-journal` 附属文件归入该数据库，不单独分类、不单独计数（封存时由 `VACUUM INTO` 覆盖）。
- **符号链接**：root 内部的符号链接只记录，不跟随。root 自身的路径是（或经过）符号链接时（例如把状态目录软链到另一块磁盘），按解析后的真实目录扫描，报告中同时展示两者。**M4 待定**：这种情况下复活的目录交换应该作用于链接还是目标。
- **确认**：`valise enroll` 默认只展示报告；加 `--accept` 才写入实例记录。未分类文件可用 `--assign <root>:<glob>=<类别>` 归类，写进 `local_overrides`；其余保持未分类并计数。
- **npm 来源**：全局安装没有锁文件。包名与版本取自已安装包的 `package.json`；registry 取自 `npm config get registry`；integrity 用 `npm view <包>@<版本> dist.integrity` 向该 registry 查询。查不到时如实记录缺失，并给出警告。
- **git 来源**：记录 remote、commit、是否 dirty；dirty 时差异（`git diff HEAD --binary`）作为 `body_patch`，未跟踪文件只计数并警告（不进入补丁）。

### 4.2 安装布局与身份的边界（2026-11-05）

profile 负责通用规则，档案记录这台服务器实际探测并经用户接受的安装事实。布局扫描与备份覆盖共用证据，但不将本机路径特例写回官方 profile，也不在 Go 中硬编码 harness 特例。发现、用户接受、操作验证通过必须区分；日常只读扫描不自动扩大授权或改写已接受的档案。

链接只备份链接文本，不隐式跟随未知外部目标。把来源登记进档案不代表允许复制、执行、改写该目标，也不代表管理命令已验证能在暂存环境隔离运行。B03 配置事务中链接的处理（临时指向暂存、程序代码的私有副本与还原）见 INSTALL.md 5.2.1（2026-11-07 用户决定）；它只用于该事务的暂存执行，不改变备份对链接的处理。

首页按 Agent 汇总，但不能用显示名、SSH 别名、可重用的 `instance_id` 或日历周期判断同一生命历程。N1 已确认 `AgentRef = server_uid + install_id + instance_id + generation`；profile 升级或修改显示名不建新世代，新实例、清理后重用 id 或重新接入被取代实例创建新世代。服务器身份仍须结合 SSH 主机信任核对，不能凭 server_uid 合并克隆的系统盘。

身份记录独立保存于 Valise 配置目录的 `identity/`，不扩展现有 dossier 或公开备份库格式；日常只读查询不自动建立身份。旧记录返回 legacy_unbound，用户明确接受接入后才绑定。成功迁移在目标端记录明确接续关系；创建副本拥有独立世代与旅程。失败、回退、仅暂存或仅文件恢复不生成成功迁移关系。

新备份通过备份库外运行记录绑定 AgentRef 与 SnapshotRef；不改写旧快照，不把同名旧历史强行归入新世代。身份/迁移记录丢失时仍可从完整副本重建保存点并导出，世代与关联显示未知。字段、存储和兼容规则见 N1 契约第 2–3、9 节；这些是 N2/N3 实现目标。

匹配规则：

- 一个文件匹配多条规则时，取第一条命中的规则。**但只要有任何一条规则把它判定为 `secrets`，它就是 `secrets`**（凭据优先）。
- **未知即敏感**：没有任何规则命中的文件归为 `unclassified`。它们不进入 `soul` 档，而是和凭据走同一层，进入 `soul-secrets`、`full`、`raw` 档，并在快照中单独标记。这样 profile 写漏不会导致完整备份丢数据，而 `soul` 档始终只含已声明的灵魂。未分类文件的数量会出现在登记报告和每次封存报告中，用户可以随时为它们指定类别。
- **`raw` 档**（全量）：把实例所有 root 下的全部文件原样封存，包括身体、缓存、忽略项和未分类文件，用于在 profile 不完整、或身体无法按来源重建时兜底。规则：
  - 只封存本实例的 root，**不是整机备份**。因此身体位于 root 之外时（例如 npm 全局前缀中的 OpenClaw、DSH），raw 不包含身体，只能按来源重建；身体位于状态目录内部时（例如 Hermes），raw 才能为身体兜底。
  - 整个快照按凭据层对待：恢复时必须显式同意包含凭据（`restore.py --include-secrets`）；声明了 `secret_tables` 的数据库不剥离。
  - SQLite 仍然使用 `VACUUM INTO` 一致性副本；符号链接全部记录、不跟随。
  - 复活时优先按来源重建身体；只有重建失败、并且目标服务器与封存时是同一架构、同一路径时，才允许用 raw 中的身体兜底，并且必须由用户确认。界面必须如实说明：身体中的运行时常含绝对路径，换路径或换架构后不可用。
  - raw 首次封存体积大（身体常达数 GB），后续新增量取决于实际变化与去重边界；读取与一致性处理仍有成本。默认不启用，不自动安排多档位日常任务。

### 5.1 保护计划与迁移（N1 契约）

实例的 `period.keep_auto_periods` 由用户确认，0 关闭，正数是保留的已结束纯自动周期数。定时封存成功后按接受的计划整组退役超期服务器周期，退役与复制结果分开记录。

- 新计划默认 `full`，日常一次保存产生一个快照；每个时间点包含完整恢复清单，复用同叶子/epoch 的数据块，不建立逐次重放的增量链。工作区、凭据及未分类文件按既有类别和加密规则处理，只覆盖已登记 roots。
- 一份用户确认的计划表达默认范围、自动备份安排与复制位置。服务器持有独立执行定时备份所需的权威设置，客户端持有本机路径等客户端侧配置；执行时冻结所用版本，不能在一次任务中途换规则。
- 推荐每天备份，但须用户确认启用；展示时间/时区、空间与读取成本、一致性停服影响，以及用户会话退出或重启后 timer 能否运行。直传证书过期或需客户端中转分别报告，不能保证所有副本永久自动更新。
- 新手动入口、可配置 timer 与未来管理方已允许任务复用同一计划；显式选择旧 tier 保持原含义。旧计划、既有 timer、旧 CLI 默认值与受管方 MCP 的迁移分别设计并展示差异；用户接受前不静默改成 full。当前 timer 与受管方 MCP 固定 soul 的行为是兼容现状，不是新默认保护已实现。
- 已核实管理动作的操作前备份保留既有要求；不能因一天已有一个点而跳过。B03 已确认的标准备份要求在具体迁移规则定稿前维持，不能被未来自定义排除项削弱。
- 备份范围与 `local_overrides` 分类分开。未来自定义须明确 include/exclude 优先级、SQLite 单位、备份时不存在与未读到的区别、范围外携带与范围内恢复删除，以及旧工具拒绝无法解释的新语义；先更新 VAULT_FORMAT/PROFILES 与独立恢复方案，后写代码。首版不自动扩展 roots 或跟随未知链接。
- 计划按 N1 契约第 4 节分别持久化 ServerProtectionPlan 与 ClientProtectionBinding，分别使用单调 revision 和预期版本比较；首次接管须展示差异并由主人确认。服务器以固定提交事务协调计划、timer 与周期兼容投影；失败/崩溃如实报告 pending、已提交或待核实，不伪造跨机器原子回滚。
- 已接管实例的旧无版本 timer/周期/自动同步写入口必须由新版 porter 拒绝；旧显式 seal tier 与受管方 MCP soul 行为保留。新客户端遇旧 porter 不模拟新计划，不能无感降级为 soul。具体 schema、存储位置、方法与错误按 N1 契约实现；本次定稿不提升线级协议版本。保护计划修改仍沿用主人权限，不能由受管 agent 自行修改。

## 6. 封存流水线

定时任务写入自动日期周期；手动与安全备份写入永久 `savepoints/` 叶子。新自动快照记录完整密文块索引；晋升由主人确认后在源服务器把相关密文独立写入存档点，保留原加密头，不需要私钥。发布与退役共用备份库锁。

1. **预检**：确认实例记录与 profile 版本一致，并确认 `~/.local/state/valise/tmp/` 的剩余空间足够容纳 SQLite 副本。
2. **一致性处理**：
   - profile 声明的 SQLite 文件：用 `modernc.org/sqlite`（纯 Go 实现，兼容 `CGO_ENABLED=0`）以只读方式打开，执行 `VACUUM INTO` 生成临时副本，再对副本执行 `PRAGMA integrity_check`，结果必须为 `ok`。封存的是副本的内容，记录的是原文件的路径。
   - **表级凭据剥离**：profile 在 `consistency.sqlite` 条目上用 `secret_tables` 声明哪些表存放凭据。`soul` 档封存时，只在临时副本中清空这些表（`DELETE FROM`）后再 `VACUUM`，绝不修改原文件；`soul-secrets` 与 `full` 档封存未剥离的副本。这仍是"只按声明分类"，代码不扫描表内容。（M3 实现；M2 只在登记报告中展示。）
   - profile 声明 `quiesce: stop_service` 的实例：停止服务，封存，再启动服务并做健康检查。停机时长需要在计划中提前告知用户。默认值为 `none`。
   - 其他文件：读取前后各比较一次 size 和 mtime。发生变化时重读一次；仍然变化就标记为 `unstable` 并写入报告，不视为失败。
3. **分块与去重**：按 `VAULT_FORMAT.md` 的规则执行。
4. **写入**：依次写入新的 pack、index、加密的快照清单、明文元数据，每一步都要 fsync。最后写入审计记录。
5. **报告**：文件数、各类别大小、新增字节数、未分类文件数、`unstable` 列表、耗时。

实现细节（M3 确定）：

- **profile 来源**：`enroll --accept` 时，客户端把当时生效的 profile（已合并子 profile）连同实例记录一起写到服务器的实例档案（`dossiers/<install_id>.profile.json`，4.1 节）。封存一律使用这份 profile，因此定时封存和 MCP 封存不需要客户端在线。profile 升级后需要重新登记。
- **档位**：见第 5 节的表格。`local_overrides` 参与分类。
- **body_patch**：git 来源且工作树 dirty 时，封存当时的 `git diff HEAD --binary` 作为虚拟文件 `valise:body.patch`。
- **互斥**：同一台服务器同一时刻只允许一个封存或同步，用 `~/.local/state/valise/vault.lock`（flock）保证。
- **临时文件**：SQLite 副本写在 `~/.local/state/valise/tmp/`，封存结束后由 Go 代码删除。
- **变动统计**（M4 实现）：每次封存后，porter 更新 `~/.local/state/valise/seen/<instance_id>.json`，记录 identity、config、skills 类文件的路径、SHA-256、连续发生变化的封存次数。它只包含路径和哈希，不含文件内容；服务器本来就持有这些明文文件，因此不新增暴露面。这份统计是给 agent 和用户的归类线索（见 AGENT_KIT.md 第 3.1 节），不会自动修改任何分类。

触发封存的方式有四种：

- CLI 或 UI（包括首次备份教程）；
- agent 通过 MCP 触发，但只能封存 `soul` 档，并且有频率限制；
- 用户开启的定时任务（`systemd --user` timer，见第 7 节"自动同步到远程备份位置"）；
- 复活之前自动封存。

封存由 porter 在服务器上使用收件人公钥加密完成，**不需要客户端在线**。

**教学备份**（2026-11-01 用户决定）：首次备份教程中建立的备份带教学标记。标记不写入备份库格式（VAULT_FORMAT.md 不变），而是由客户端在封存请求中带 `purpose: "tutorial"`，porter 把它写入该次封存的审计记录，经 `seal_log` 返回给界面。界面在备份列表与详情中标"教学"，并说明它只证明当时的流程与内容，不证明之后新增的配置、渠道凭据或工作区已被覆盖；用户完成重要配置后，界面适时建议建立一次实际的备份。备份库只追加，教学备份与其他备份一样保留，随所在周期一起删除。服务器丢失、只剩远程备份位置副本时教学标记随审计记录丢失，界面按普通备份显示。

## 7. 备份库与同步

日期周期与永久存档点都是完整叶子，服务器、本机、Station 和云盘按同样的同步与校验协议处理。服务器退役不传播为异地删除。

- **收件人登记**：`valise key register <服务器>` 把本机密钥的公钥追加到服务器的 `recipients.txt`（每行一个 `age1…`，`#` 开头为注释）。收件人集合变化后，下一次封存新建 epoch。服务器上没有任何收件人时拒绝封存。`--label <说明>` 会在公钥上方写一行注释 `# <说明> (added <日期>)`，用来标明这把钥匙属于谁、用途是什么（例如测试钥匙）；注释不影响收件人集合和指纹。
- **移除收件人**（`valise key unregister`，M4 实现）：从 `recipients.txt` 删除一把公钥，下一次封存会新建 epoch，此后的快照不再加密给它。**必须向用户如实说明**：已经写入备份库的旧快照仍然可以被这把钥匙解开，加密无法追溯撤销；如果钥匙已经泄露，应当把旧快照视为已暴露。拒绝移除最后一把公钥。
- **本机仓库**（现有配置与路径，2026-11-02 用户决定；新界面归入“备份位置”）：用户在客户端选择一个或多个本机文件夹（普通目录、外接硬盘或网盘桌面客户端的同步文件夹），记在客户端 `config.json` 的 `repos`（`[{"name", "path"}]`），所有服务器共用。同步由客户端完成：对服务器上每个未在删除中的周期执行与"拉取"相同的只追加复制，写到 `<仓库>/<服务器名>/<实例>/<周期>/`，`<仓库>/<服务器名>/TREE` 不存在时按 VAULT_FORMAT.md 10 节写入一次；每个周期复制后做不需要私钥的校验。服务器名未设置时先请用户起名。客户端不常驻，需要客户端的复制只在客户端可用时执行，界面写明“这一份只在 Valise 打开时更新”。打开时/备份后的自动补齐由共享服务层按 7.4 节的规则执行，GUI、TUI 与 CLI 共用。不能因新增入口漏掉自动复制，也不能将 CLI 进程退出后的客户端任务描述为继续运行。同步记录（每台服务器每个仓库的最近成功时间与错误）保存在客户端数据目录的 `repo-state.json`。仓库里的目录结构与远程备份位置相同，`tools/standalone-restore/` 可以直接使用。
- **备份库树**：每台服务器的本地备份库按"实例 / 周期"分档，每个周期是一个独立的 `valise-vault/1` 备份库（VAULT_FORMAT.md 第 10 节）。同步到远程备份位置时目标上多一层服务器名：`<dest>/<server_name>/<instance_id>/<周期>/`。
- **远程备份位置**（内部称 station / target，界面曾称云备份、空间站）由 `porter sync --target <name>` 完成，支持 rsync、rclone 和 sftp。目标配置写在 `targets.json` 中；rclone 使用用户自己的 remote 配置，Valise 不保存其中的凭据。
- **移除远程备份目标（`target_remove`，2026-11-16 用户决定）**：porter 提供 `target_remove` 方法（主人操作，经 `WithLegacyTargetsWrite` 锁校验），允许从服务器的 `targets.json` 移除不再使用的远程备份位置记录（不删除远端已保存的备份文件）。若该目标正被当前生效的保护计划引用（`ServerPlan.Desired.ServerCopies`），porter 拒绝移除并提示先在保护计划中取消勾选；仅被已失效旧世代计划引用或无引用的目标允许直接移除。客户端移除 `station` 或 `ssh` 位置时同步对相关服务器调用 `target_remove`，避免失效目标残留导致 `VaultStatus.Targets` 持续将其重新列出并不断触发健康或网关检查。
- 同步按叶子逐个进行，叶子内的顺序固定为：pack → index → 快照 → 元数据 → epochs/keys → PERIOD → VAULT；带 `DELETING` 的叶子跳过。由于叶子内只追加，任何中断都可以安全续传。
- **targets.json**：`{"targets": [{"name": "nas", "kind": "rsync", "dest": "nas-test:/mnt/test/nas/valise-vault/", "auto": {"every": "24h"}}]}`。`kind` 取值 `rsync`、`rclone`、`sftp`；已实现 `rsync`（经服务器自己的 SSH 配置，加 `--ignore-existing`）与 `sftp`。
- **协议回落**（2026-11-02 用户决定）：`kind: rsync` 的目标在服务器或目标上没有 rsync 时（本机找不到 rsync，或远端报 `command not found` 等），这一次操作自动改用 sftp，结果写明所用方式与原因（"rsync 不可用，改用 sftp，速度会慢一些"）；`kind: sftp` 直接用 sftp。sftp 只需要目标上 OpenSSH 自带的 sftp-server：经 `sftp -b -`（服务器自己的 SSH 配置、`BatchMode=yes`）先逐层列出目标上已有的文件，只上传缺少的，每个文件先传为同目录下的 `.part-<名字>` 再 `rename`，因此中断不会留下半个文件、云端只追加；列表跳过 `.part-*`。删除整个周期时先写 `DELETING` 标记，再按列表逐个删除文件、由深到浅删除目录，最后删除标记。界面上未实现的种类不渲染。同步结果写入审计记录，`porter status` 据此报告每个目标的最后同步时间。早期的目标由用户在服务器上自己配置 SSH（"服务器自己配置的远程备份位置"），仍然可用；新的远程备份位置由 Valise 管理（下一条）。
- **Valise 管理的远程备份位置**（2026-11-02 用户决定）：服务器在公网、NAS 在家里内网是常态，远程备份位置的连接信息因此归 Valise 管，不要求用户去改服务器的 SSH 配置。
  - **记录**：客户端数据目录的 `stations.json`（`[{"name", "address", "port", "user", "path"}]`），主机指纹写入 Valise 的 `known_hosts`（与服务器相同的确认流程）。建议用户在 NAS 上为 Valise 开一个**专用用户**并只给它一个目录，界面在添加时说明原因。
  - **钥匙与证书**（2026-11-02 用户决定）：客户端一把 `keys/_stations/<名字>/client`（用于中转、列表与删除），在远程备份位置上以 `restrict` 授权。服务器的钥匙由 porter 用 `ssh-keygen` 在服务器上生成（`~/.config/valise/station-keys/<名字>`，私钥不离开服务器），**本身不被远程备份位置授权**：远程备份位置上只加一行 `cert-authority,restrict,principals="<用户>" <Valise 签发公钥>`，服务器凭客户端签发的 OpenSSH 证书登录。签发私钥（`keys/_stations/_ca.age`）用用户的 age 收件人加密，签发时由已解锁的身份临时解开，因此签证书需要 Valise 口令。证书内容由 Valise 决定，不依赖 NAS 的附加能力：`-O clear`（不能开终端、不能转发）；有效期默认 7 天（`config.json` 的 `station_cert_hours`，1–720），每次打开 Valise 且口令已解锁时自动续期，快到期而未解锁时提示"同步一次即可续期"；`source-address` 为服务器的地址（先用 5 分钟的探测证书执行 `echo $SSH_CLIENT` 得到远程备份位置看到的地址；地址会变的服务器可以选择不限定）；`force-command`：远程备份位置有 rrsync 时为 `rrsync -wo -no-del -no-overwrite <路径>/<服务器名>`（只写、不删、不覆盖，限定在这台服务器的目录，服务器端以该目录为根），否则为 sftp-server 并禁止删除、改名、改权限等请求（仍可能覆盖已有文件，界面建议开启 NAS 快照），两者都没有时不给服务器凭据、一律中转。服务器钥匙不能读也不能删，因此远程备份位置的列表与删除由客户端完成（删除仍按 2.2 节分级：服务器上还有这个周期时为主人操作，否则为开发者模式）。添加远程备份位置时，若它不需要任何凭据就能登录，明确警告；并建议为 Valise 开专用用户、为其目录开启定时快照。
  - **三条路径，依次回落**：① **直传**：服务器 → 远程备份位置（rsync，缺 rsync 时 sftp）。② **经本机仓库中转**：已有本机仓库时，先把服务器上的备份补到仓库，再由客户端从仓库传到远程备份位置。③ **临时中转**：没有仓库时，取回到客户端缓存目录下的临时目录，传到远程备份位置，完成或失败都删除临时目录；开始前检查本机空间。直传因网络或登录原因失败（不认识主机名、连不上、拒绝登录、指纹未确认），或服务器尚未配置这个远程备份位置时，自动改走中转；结果写明用了哪条路径。中转期间 Valise 要保持打开，界面写明。
  - **同步记录**：中转成功后，客户端调用 porter 的 `sync_record`（主人操作）把这些备份记进服务器上该远程备份位置的同步记录，删除分级与"已同步"显示因此一致。
  - 云端列表与删除整个周期同样先直连、失败时由客户端连接。服务器自己配置的远程备份位置在客户端的 SSH 配置里也有同名主机时，同样可以中转。
- **云端列表**：客户端经 porter 列出目标上的备份库树（rsync：`--list-only`，只读目录与文件名、大小），与服务器本地对照，展示每个周期"服务器有 / 云端有 / 两处都有"、备份数量与大小。目标上的元数据文件（`*.meta.json`）可以按需拉取用于展示，不需要私钥。
- **删除周期**：见 VAULT_FORMAT.md 10.4。RPC 只接受"实例 + 周期 + 位置（服务器或某个目标）"，不接受任意路径。
- **自动同步到远程备份位置**（2026-10-31 用户决定，两种方式并存）：
  - **随建立备份顺带同步**（默认方式，不常驻）：每次成功建立备份后（无论由用户、agent 经 MCP、安全网还是定时器触发），porter 检查每个开启了 `auto` 的目标，距上次成功同步超过 `auto.every` 时，启动一个脱离会话的 `valise-porter autosync` 子进程完成同步后退出。它与封存共用 `vault.lock`，拿不到锁就放弃本次，等下一次备份再试。结果写入审计记录。
  - **定时器**（可选，由用户显式开启）：生成 `valise-seal@<instance>.timer` 与对应 service（`--user`，遵守 docs/LAB.md 的 systemd 铁律）。当前固定封存 `soul`；N2 改为执行用户接受的保护计划，新计划默认 full，旧 timer 按 5.1 节显式迁移。启用后不依赖客户端在线完成服务器封存，复制位置仍受网络、证书和客户端条件限制。界面说明留下的单元文件，关闭时删除它们。
- **取回本地**分两种，界面分别说明目的地、是否包含凭据、文件的保护状态：
  - **保存加密备份**：`valise pull`，把备份库（或一个周期）拉取到本机目录。拉取只复制本机没有的文件（备份库只追加），然后做不需要私钥的校验。文件仍是加密的，打开需要加密钥匙与口令。
  - **导出可查看的文件**（M13 实现）：解锁加密钥匙，在内存中解密一个备份，写到用户选择的本机目录。默认不含凭据层，包含时必须单独确认；导出的目录与文件权限设为 0700 / 0600，界面写明"这些文件不再加密，请自行妥善保管或用完删除"。
- **带私钥的校验**只在客户端进行：`valise verify --vault <本机目录> --key` 解锁本机密钥，在内存中解密快照清单与 blob，按文件校验 sha256。
- UI 中"已写入服务器备份库"、"已同步到 <远程备份位置>"与"已取回本地"分开展示；建立成功时写明目前是否只存在于原服务器。

### 7.1 备份位置与验证状态（N3 目标）

共享服务统一读取服务器备份库、本机仓库、已支持远端位置与恢复缓存，保留各自权威配置和访问限制，不强制合成同一磁盘格式。每处结果携带查询时间、错误与验证范围，区分以下事实：

1. 已发现该时间点的元数据。
2. 该时间点所需的加密材料齐全；与整个周期副本齐全分开。
3. 已完成不需要私钥的结构/pack 完整性校验。
4. 已解密并按清单核对文件。
5. 已暂存测试，或已完成实际服务启动验证（两者分开）。

副本齐全必须按快照身份与实际依赖核对，不凭数量相等、某个 `.meta.json` 存在或“上次复制成功”断定。整个周期还须核对快照及 pack/index/epoch/key 等必要集合，规则见 VAULT_FORMAT.md。当前 `LeafCopies.Complete` 等旧聚合与记录不作为新承诺的证据；未完成严格核对时写“尚未验证”。部分缓存保留 `.partial.json` 语义，不计作整个周期副本。位置不可达不等于没有副本，不使用过期结果放宽删除或高级功能门槛。

本轮不改变现有删除分级或将客户端自报的本机副本变成 porter 的放行凭据；相关证据如何用于权限判断须另行定稿。

#### 7.1.1 严格副本的核对方法（N3，2026-11-07 用户决定）

- **材料清单**：一个叶子中除 `DELETING`、临时文件（`tmp-*`、`.part-*`）与 `.partial.json` 外每个文件的相对路径、大小与 SHA-256，按路径排序后取摘要。服务器在线时由 porter 对服务器叶子现算（只读方法 `leaf_materials`，日常钥匙）作为**基准**；已结束的周期这就是最终清单，当前周期只代表“截至核对时刻”，副本只能证明“齐至这一刻”。
- **每一处核对两项**（SERVICE_CONTRACTS.md 5.2）：`period_material`：与基准逐项对比，路径齐全、大小相同，非 pack 的小文件（VAULT、PERIOD、epochs、keys、index、快照 `.age` 与 `.meta.json`）比 SHA-256，列出缺少、多出与不同的路径；`integrity`：VAULT_FORMAT.md 第 7 节的免钥匙校验。
- **完整副本** = 当场重新列出后 `period_material` 通过，且 `integrity` 通过（可按下条复用）。读取失败为“未知”；存在 `DELETING` 或 `.partial.json` 一律不算完整；单快照取回缓存永远不算完整周期副本。
- **各位置在哪里核对**：服务器备份库由 porter 本地核对；本机仓库由客户端直接读；服务器自己配置的 rsync 位置由 porter 用 `rsync -n -c` 对比（目标端计算校验和，不下载，内容与服务器上已校验的文件一致即两项通过）；sftp 位置与 Valise 管理的远程备份位置列出后下载小文件比哈希，pack 内容边下载边计算、不落盘（服务器配置的位置由 porter 做，Valise 管理的由客户端做），开始前显示要下载的总量；云盘见 7.3 节。
- **复用**：已校验的 pack 按“位置 + 路径 + 大小 + 修改时间”记在客户端 `verification-state.json`，大小与修改时间都没变就不重新计算；其他文件每次重新比对。
- **何时核对**：每次复制成功后自动做 `period_material`；pack 内容只在用户点“核对副本”或删除周期前做（只算没核对过或有变化的）。
  - 服务器发起的复制（客户端请求的同步、随备份顺带的自动同步、保护计划的复制）由 porter 在复制后核对（2026-11-07 用户决定）：只核对服务器上清单自上次通过以来有变化的周期（清单摘要不变就沿用上次结果），结果按周期写进该位置的同步记录（`TargetState.checks`：时间、通过/不通过/未知、缺少/不同/多出的数量与第一个路径，不含内容），客户端经 `vault_status` 读取显示。核对失败不让复制失败。Valise 管理的远程备份位置服务器无权列出，复制后由客户端核对。
  - 客户端发起的中转与本机仓库同步由客户端核对，结果记入 `verification-state.json`。服务器记录的结果只用于显示，不作为删除时的完整副本（删除前一律当场核对）。
- **删除周期**：删除前对其他每一处当场核对，逐处显示“完整 / 不完整（列出问题）/ 未知（原因）/ 未核对”与时间。用户可以跳过某一处的核对（例如下载量太大），跳过的按“未核对”处理、不算完整；没有任何一处完整时，走“删除后这些备份将无法恢复”的二次确认。删除权限分级不变，客户端的核对结果不变成 porter 的放行凭据。
- **服务器不可达**：没有基准。某一处 `integrity` 通过且自身快照与材料互相引用齐全时，界面写“能恢复这里列出的 N 个备份；无法确认服务器上是否还有更多备份”，不写“完整副本”，不放宽删除。
- **兼容**：`leaf_materials` 与 `target_verify` 由能力 `copy-verify/1` 声明；旧 porter 没有时，服务器备份库与它配置的位置显示“这个 porter 版本不能核对，更新后再试”，删除时按“未知”处理。备份库格式不变，不向备份库写任何新文件。

### 7.4 这台电脑负责的自动补齐（N3，2026-11-08 用户决定）

本机仓库与“这台电脑登录”的云盘只能由客户端复制。触发、规则与结果由共享服务层统一处理（`AutoCopy`），各前端只负责展示；不新增常驻进程。

- **覆盖的位置**：本机仓库；“这台电脑登录”的云盘（7.3 节，经本机仓库或临时目录中转）。服务器直传连不上的远程备份位置不自动中转，仍在用户手动同步时中转。
- **两个触发**：
  - **打开时**：TUI/GUI 每次运行中第一次载入某台服务器时，对它执行一次；运行 CLI 命令不算打开。同一时机续期快到期的远程备份位置证书（Valise 口令已解锁时）。
  - **备份后**：这台电脑发起的备份成功后。TUI/GUI 在后台执行；CLI 的 `seal` 在前台执行并显示进度，加 `--no-copy` 跳过，此时写明“本机仓库未更新”。CLI 进程退出后不会继续，也不这样描述。服务器定时备份产生的新备份在下一次打开时补齐。
- **规则**（本客户端绑定，SERVICE_CONTRACTS.md 4.1）：
  - 已采用保护计划且本客户端为该 Agent 保存了绑定的实例，按绑定决定：仓库 R 在“备份后”触发时补齐，当且仅当该 Agent 的绑定列出 R 且 `after_backup` 为开；“打开时”同理看 `on_client_open`。绑定未列出的仓库视为关。
  - 没有绑定的实例（未采用保护计划、没设置过、或绑定的世代与当前不符）沿用原规则：两个触发都补到所有仓库。
  - 仓库按整台服务器复制（内容不变，7 节）：打开时，只要这台服务器上有一个实例需要 R 就补 R；备份后只看发起备份的实例。没有任何实例的服务器按原规则。
  - “这台电脑登录”的云盘没有绑定，两个触发都补。
- **并发**：每个位置里每台服务器的文件夹一把本机锁（客户端数据目录 `locks/`；不同服务器写各自的文件夹，可以同时复制到同一个仓库）。自动触发遇到锁被占用就跳过，结果写“另一个 Valise 正在同步这个位置”；用户手动发起的同步等待它结束。
- **重试与断连**：自动触发不在本次运行内反复重试；本机仓库的结果写入同步记录（`repo-state.json`，写入时加锁），下一次触发再试。复制只追加，中断后再次补齐从已有内容继续。
- **结果**：每个位置一项：已补齐（新下载的备份数）、已是最新、按设置未补、未挂载（仓库路径不存在，如外接硬盘没插）、正在被另一个 Valise 同步、失败（原因与下一步）。TUI 在有新内容或失败时提示，没变化时不打扰；CLI 逐项打印。界面照旧写明这些位置“只在 Valise 打开时更新”。
- **设置入口**：CLI `valise protection copies <服务器> <实例>` 显示或修改本客户端绑定（`--repo <名> --after-backup on|off --on-open on|off`，可重复）；要求该实例已采用保护计划，按版本比较写入。第一次保存时先把每个已登记仓库设为两项都开（与原规则一致），再应用这次修改。TUI/GUI 的设置页在 N4。

### 7.2 旅程读取与可重建索引（N2 / N3 目标）

- Agent 页面按显式连接范围读取：当前服务器及已有明确迁移关系关联的服务器，加上本机和可访问备份位置；不逐台探测无关服务器来查找关联，不按同名或创建副本关系扩张。全位置表示查找这条旅程的副本；位置错误、缓存与重试同样受范围约束。全局备份库查询保留为显式能力，首页启动只建立本机索引。
- 快照头、明文元数据及完整恢复清单是保存事实的依据；审计、恢复验证与迁移记录提供附加信息。时间点按实际保存时间排列，标明当时 tier 和覆盖，不按当前保护计划解释旧快照。
- 成功保存才成为恢复点。失败/取消/部分完成的任务作为独立操作记录展示；复制失败不抹去已成功保存的时间点，备份失败不创建虚假节点。
- 索引是可丢弃并重建的客户端查询缓存；从备份库副本重建时间点不能依赖原服务器在线、原 dossier 或原客户端状态。缺少原因、教学标记或关联时如实留空；不从对话内容或 LLM 补写故事。
- 多处读取到同一快照须核对备份库与快照身份、发现冲突时停止将其作为同一副本；离线列表的明文元数据不等于解密验证通过。身份关联、查询分页/过滤、验证记录存储与失效条件采用 N1 契约第 2–5 节；不为新视图直接变更公开格式。
- 原服务器不可达时，已有副本仍可列举与导出；历史中的服务器状态只能显示为历史值，不能假装在线。

### 7.3 云盘（N3，2026-11-07 用户决定）

备份位置新增“云盘”，全部经 rclone 完成，Valise 不实现任何云盘协议。首批 Google Drive、OneDrive、Dropbox；坚果云（WebDAV）与自定义云在后。

- **表单登录**（2026-11-10 用户决定）：桌面版把 rclone 的提问画成表单（rclone 的非交互配置，LOGIN_RELAY.md 第 7 节第 5 步）；无浏览器授权、不支持回环授权的云盘与旧 porter 仍用窗口里的终端。
- **rclone 保持独立程序**（2026-11-10 用户决定）：不把 rclone 作为库集成进 porter 或桌面版。理由：porter 要保持小（每次部署都上传，服务器直传依赖服务器上的 rclone）；网盘接口变化时只换 rclone，不必等 Valise 发版；授权文件仍是 rclone 的标准配置，Valise 不在时用户可直接用 rclone 访问。

- **云盘清单**：签名资料包 `kit-tools.yaml` 中 rclone 条目的 `clouds`（AGENT_KIT.md 8.4）列出每家的 `rclone_type`、固定参数、授权范围（`folder` 只能访问 rclone 自己建的文件 / `account` 能访问整个网盘）与说明。Go 代码不写任何云盘名称或参数；`verify: pending` 的条目只展示、不能添加。Google Drive 固定 `scope: drive.file`；rclone 内置的 Dropbox 与 OneDrive 应用是整盘权限。
- **自己的应用**（2026-11-08 用户决定；2026-11-10 起桌面版的表单登录里由用户在表单中填写 client_id 与 client_secret，只交给 rclone 一次，Valise 不保存、不记录，见 LOGIN_RELAY.md 第 7 节第 5 步；终端登录仍按下文）：rclone 1.75.2 提示它共享的 Google Drive 应用“将在 2026 年内停止工作”。条目可声明 `ask_app: true`（Google Drive），登录时 rclone 的配置命令加 `--all`，由 rclone 自己在终端里依次询问 client_id、client_secret、service_account_file 与是否编辑高级设置（默认否）；client_id 留空时 rclone 会问是否继续用共享应用。用户在 rclone 的提问里自己填写，Valise 只转发终端字节，不解析、不保存、不记录（与原生界面同一规则）。登录前界面说明这几步，并给出 rclone 文档“自建 client_id”页面的地址；不用自己的应用时写明“rclone 的共享应用可能随时停用，之后需要重新登录”。Valise 自己不提供任何应用密钥输入框。
- **两种登录**，界面分别说明同步级别，可以都登录：
  - **服务器登录**：rclone 由 Kit 安装（`~/.local/bin/rclone`，版本与 SHA-256 已核实），配置在 Valise 自己的文件 `~/.config/valise/rclone/rclone.conf`（0600），每次调用都显式 `--config`，不碰用户自己的 rclone 配置。remote 名为 `valise-<位置名>`。备份后由服务器直传，定时与自动复制依赖它，不需要 Valise 打开。
  - **这台电脑登录**：rclone 用 PATH 里已有的（显示 `rclone version` 第一行），没有时经确认按 `kit-tools.yaml` 锁定版本下载（展示地址、大小与 SHA-256），核对后放在 `<配置目录>/tools/rclone`；配置在 `<配置目录>/rclone/rclone.conf`（0600），同样显式 `--config`。复制经本机仓库或临时目录中转，只在 Valise 打开时更新。
  - 两种都登录时先服务器直传，失败再经这台电脑中转，结果写明路径；只有服务器登录的云盘能被保护计划的自动复制使用。
- **授权内容**只在上述 rclone 配置文件里。Valise 不读取、不解析、不保存、不记录它；登录过程的终端字节经 Valise 转发（LOGIN_RELAY.md 第 7 节），只显示给用户，不写日志与审计。
- **服务器登录确认页**写明：“授权保存在服务器上。服务器被攻破时，这个授权会一起暴露（备份内容本身是加密的）。” `account` 级的云盘另写“这个授权能访问整个网盘”，并建议只用这台电脑登录或改用 Google Drive；用户确认后可以继续。
- **保存位置**：授权完成后用 `rclone lsjson --max-depth 1 valise-<名>:` 做只读连通测试，再经 `target_check`（N2 G 节）保存；`targets.json` 记 `{"name", "kind": "rclone", "dest": "valise-<名>:valise-vault/"}`，不含授权内容。
- **同步只追加**：先 `rclone lsf -R --files-only` 列出目标已有文件，只上传缺少的，按叶子顺序（pack → index → 快照 → 元数据 → epochs/keys → PERIOD → VAULT）分批 `rclone copy --files-from … --ignore-existing --immutable`，不使用 `sync`。中断后续传。删除整个周期与 sftp 相同：先写 `DELETING`，逐个删除文件，最后删标记（VAULT_FORMAT.md 10.4）。副本校验适用 7.1 节。
- **云端可见的明文**：目录名（服务器名、实例名、周期）与文件大小；文件内容是 age 加密的。不加 rclone crypt，保持备份库公开格式：从网盘网页下载整个目录即可用 `tools/standalone-restore/` 恢复。添加时写明哪些名字云端可见。
- **移除位置**：`rclone config delete valise-<名>`（服务器或本机各自的配置文件），界面写明“这里的授权已删除；网盘账户里的授权需要你在账户设置里撤销”。云端已有的备份不自动删除。
- **诚实状态**：已登录（服务器 / 这台电脑）、连通测试通过、最近一次同步结果与路径分开显示；“已登录”不等于“已同步”。
- **访问级别**：添加、登录、移除是主人操作；同步与列表沿用远程备份位置现有级别。

## 8. 复活

### 8.1 三种模式

| 模式 | 场景 | 目标 |
| :--- | :--- | :--- |
| 回滚 | 同一个实例退回到更早的封存 | 原服务器、原状态目录 |
| 迁移 | 把实例搬到另一台服务器，可以跨架构 | 新服务器。启动目标前核实停用原实例，目标检查通过后自动标记迁出，旧目录与备份保留 |
| 克隆 | 生成一个新实例 | 当前或另一服务器的新 `instance_id`，默认不带独占凭据；先准备、用户确认后启用（目标规则，待实现） |

### 8.2 流水线

> **2026-11-15 架构收敛**：已撤销 2026-11-12 试探的 A/B 双槽位并行环境及三档模式方案（归档见 `docs/history/RESTORE_ENVIRONMENTS_DEPRECATED_2026-11-15.md`），统一回归本节流水线。

恢复当前实例默认绑定当前登记目录，保留交换前目录（`.valise-prev-<op>`）；额外“先备份当前状态”为用户可选项，不作为所有恢复的强制前置，普通路径的 GUI 选择已实现、默认不勾选，使用一次完整备份，失败就不暂存。来源不明时仍独立确认来源，已选择先备份的不重复建立。迁移/副本的目录由已核实布局安排，CLI 显式 root 覆盖保留，普通 GUI 不要求用户写内部参数；迁移/副本的新位置流程仍待实现。

1. **计划**：由代码计算并展示以下内容，用户确认后才继续（`--dry-run` 只输出计划）：
   - 源快照；
   - 目标服务器与状态目录；
   - 身体的处理方式：保持不变、按来源记录安装同一版本，或版本不同需要用户确认；
   - 是否恢复凭据，以及独占凭据冲突的处理方案；
   - 预计停机时间；
   - 所需磁盘空间（暂存空间加上旧状态的保留空间）；
   - 暂存目录与状态目录是否在同一个文件系统（用 `stat` 比较设备号，不在同一文件系统就拒绝执行）。
2. **身体**：
   - 目标服务器上已有同一来源、同一版本的身体时，保持不变。
   - 否则按来源记录安装：npm 使用记录中的 registry 和精确版本，安装到用户级前缀，并比对 integrity；git 克隆记录中的 remote，检出记录中的 commit，再应用 `body_patch`；然后执行 profile 中的 `bootstrap_argv`；uv 和 pipx 同样使用精确版本。
   - **来源校验失败时立即停止**，例如 remote 或 registry 不一致、包已下架、哈希不符。此时向用户展示差异，由用户决定是否改用 profile 文档中的全新安装方式，手动安装后重试。
   - 全局安装的身体（例如 npm 用户级前缀）无法预先放进暂存区，安装动作推迟到交换窗口内执行，并在交换日志中记录原版本，以便回退时重装。
3. **暂存**：客户端在内存中解密 blob，组装成 tar 流，交给 `porter stage-write` 写入 `.valise-stage-<op>/`。之后逐个文件校验 sha256，对 SQLite 执行 `integrity_check`，并恢复文件权限；`secrets` 类文件一律设为 0600。
4. **确认**：展示暂存校验的结果，请用户做第二次确认。
5. **交换**：交换日志的状态依次为 `PLANNED → STOPPED → LIVE_MOVED → STAGE_MOVED → BODY_SWITCHED → STARTED → HEALTHY`；失败时进入 `ROLLING_BACK → ROLLED_BACK`。
   - 正常路径：写日志 → 停止服务并确认已停止 → 把活动目录重命名为 `.valise-prev-<op>` → 把暂存目录重命名为活动目录 → 按需切换身体 → 启动服务 → 健康检查。
   - 健康检查：先等待宽限期（profile 定义，默认 20 秒），然后每 5 秒检查一次，连续 3 次通过即为健康，总超时 120 秒。
   - 失败路径：停止服务 → 把活动目录重命名为 `.valise-failed-<op>` → 把 prev 目录改回活动目录 → 恢复身体 → 启动服务并做健康检查 → 向用户返回 `rolled_back` 和最近的服务日志。这些日志只展示给用户，不写入审计记录。
   - 回退证据独立记录目录、程序版本、服务启动和健康结果。停服失败不交换目录；程序恢复或启动失败保留未完成日志，可在处理原因后继续退回；目录退回完成但健康未通过时明确保留失败结果。日志归档失败可单独收尾，不重做目录交换。新字段为可选，旧 porter 没有证据的分项保持未知。
6. **收尾**：`.valise-prev-<op>` 默认保留 7 天，UI 中提供"立即退回到交换前"的操作。清理只能由用户执行 `valise prev drop`，由 porter 在 Go 代码中调用 `os.RemoveAll` 完成。
   - **恢复测试**（UI.md 9.5）走第 1～3 步（暂存与校验），不进入交换；随后以 `revive_resume` 的 `discard` 结束：只允许状态仍为 planned 的操作，暂存目录当场由 porter 在 Go 代码中删除（用户发起测试即视为显式命令；暂存只是副本，活动目录从未被触碰），访问级别与 `stage_begin` 相同（主人）。
   - 文件测试的内部计划不包含程序重建、服务安装/控制、目录携带或身份恢复步骤，不因缺少运行时或资料未核实而伪装成运行测试；仍检查实例、目录、空间和未完成操作。测试索引在开始前保存原操作与时间点，并分别记录本机核对、服务器校验和收尾。本机解密暂存按操作放在私有缓存中，正常收尾清理；强退后由用户发起对原操作的核实与两端暂存清理，不重发测试，也不把收尾完成当成测试通过。连接身份变化或日志已进入交换时拒绝按测试清理。

### 8.2.1 实现细节（M4 确定）

- **快照来源**：客户端从快照所在服务器只取回这个备份需要的部分（2026-11-03 用户同意，检测报告 F03）：先取回周期里的小文件（VAULT、epochs、keys、index、快照头与 meta），用加密钥匙解开快照头，按文件清单与各文件引用的 blob 查 index 得到用到的 pack，只下载本机缺的 pack（下载时核对 SHA-256；本机已有的重新核对后复用，损坏的重新下载）；之后每个文件仍按 SHA-256 核对。这样的本机缓存只是这个备份的恢复材料，旁边以 `<备份库目录>.partial.json` 标明，不能当作完整周期副本校验或使用。标记必须在写入任何取回文件前原子落盘，写入失败则停止；失败或断线后保留标记，只有成功取回的快照才列入标记的恢复材料清单。重新进入时复用已核对的数据包；只有取回整个周期并通过整体校验后才删除标记，删除失败也必须报告；本机仓库、远程备份位置与"保存加密备份"仍复制整个周期，`tools/standalone-restore/` 的承诺不变。计划与恢复测试的结果写明周期总大小、备份大小、用到的 pack 大小、本次下载量与复用量。然后在内存中解密快照与 blob；明文以 tar 流经 `porter stage-write --op <id>` 写入目标服务器的暂存目录。profile 优先取已安装资料包（或本地）的同 id、同 `profile_version` 的 profile；没有时，改用快照头中的 `profile_doc`（封存时使用的完整 profile），计划中标明"来自快照，未经当前客户端审核"，并且必须显式传入 `--allow-snapshot-profile`（其中的服务安装命令等仍逐字展示）。两者都没有时停止。恢复能力未核实（`capabilities.restore` 不是 `tested`，或 `status: draft`）的 profile 必须显式传入 `--allow-draft-profile`（PROFILES.md 1.2）。
- **目标路径**：目标的状态目录由目标服务器按 profile 的 `detect.state_dir_candidates` 解析（使用目标用户的 HOME）。其余 root：原路径在原状态目录下的，映射到新状态目录下的同一相对路径；在原 HOME 下的，映射到新 HOME 下；都不是时停止，由用户用 `--root <id>=<路径>` 指定。
- **符号链接**：目标的 root 本身是符号链接时，v0.1 拒绝复活并说明原因（链接常由其他工具管理；交换时被改名的会是链接而不是数据）；封存不受影响。root 的上级路径中有符号链接（例如 macOS 的 `/var`、把 `/home` 软链到数据盘）不影响原子交换，允许。
- **交换单位**：只交换没有嵌套在其他 root 内的 root（例如工作区在状态目录内时，只交换状态目录，工作区随之移动）。暂存目录为 `<root 的父目录>/.valise-stage-<op>-<root>`，必须与 root 在同一文件系统。
- **回滚的携带语义**：回滚只替换快照档位内的类别；当前活目录中档位以外的内容（例如用 `soul` 档回滚时的凭据、未分类文件、工作区、缓存）在服务停止后**复制**进暂存目录；位于 `body.paths` 的身体目录（形如 `<目录>/**`）在交换窗口内整体改名搬入新活目录，并记入交换日志。迁移与克隆不携带任何内容：目标目录整体替换（已有目录按流程保留为 prev）。
- **嵌在状态目录里的身体**（2026-11-08 用户决定）：身体目录在被替换的 root 里（例如 OpenClaw 的私有 Node 与程序包在 `~/.openclaw/tools/`），而计划是“身体保持不变”或“按来源安装另一版本”时，回滚、迁移与克隆都把目标原有的身体目录在交换窗口内**原样改名搬入**新活目录，与命名实例的 `keep` 同一套交换日志，失败时搬回；不复制、不替换。备份自带同名目录（raw 档）时以备份为准；目标上没有这个目录时跳过（新目录、首次恢复）。需要安装另一版本时，先搬入原身体，再用它安装记录的版本；退回时先把原目录放回原位，再装回原版本。目标搬运工不支持这项能力（`revive-body-dirs/1`）时计划停止，要求先更新搬运工。
- **不含凭据的档位替换已有实例**（2026-11-08 用户决定）：迁移或克隆用不含凭据的备份（如 `soul`）替换目标上已存在的目录时，“不携带”的规则不变，但计划必须写明：目标原有的配置与凭据会随旧目录一起换下（保留在 prev），harness 可能因缺少配置起不来并自动退回；建议改用含凭据的备份，或恢复后在原生界面重新登录。
- **运行时前提**：按来源重建身体所需的工具（npm、git、uv、pipx）必须已在目标服务器的登录 PATH 中；计划阶段检查，缺少时停止，并给出 profile 中的 `fresh_install_doc`。恢复流程不安装运行时；需要时由用户经 INSTALL.md 的安装流程（官方方案或原生界面）先行准备。
- **来源校验**：npm 身体在计划阶段向记录中的 registry 查询该精确版本的 integrity，与登记时记录的值不一致就停止。git 身体检查 remote 一致、commit 可取得。v0.1 中 git 身体只支持"目标已有同一 commit 的身体，保持不变"；需要重建而 `bootstrap_argv` 尚未核实时，计划停止并说明（raw 档兜底见第 5 节）。
- **服务单元**：目标服务器上没有 profile 声明的服务单元时，执行 profile 的 `service.install_argv`（harness 自带的安装命令）。计划中逐字展示这条命令，用户确认后才执行。Valise 不自己写单元文件。
- **副本范围（2026-11-11 问卷确认，待实现）**：目标允许原服务器或另一服务器，默认原服务器；原 Agent 保留，分身有独立身份、名称与状态位置。先准备并展示登录/共享服务影响，再由用户亲自启用。目录安排、名称、服务/端口及独占凭据隔离必须依据已核实的 profile 与目标事实，不靠简单解除 From == Target 限制。当前执行器仍只支持另一台服务器，准备与启用尚未分离；不能把这条目标规范当作现有能力。
- **独占凭据**：迁移默认在目标启动前停止原实例的服务（原实例的文件不动）；克隆默认不暂存匹配 `exclusive_secrets` 的文件。复活失败回退后，客户端重新启动原实例的服务。
- **其他进程**：服务单元之外仍在使用状态目录的进程（工作目录或打开的文件位于 root 内，Linux 上通过 `/proc` 判断），会在交换期间按路径重新创建活动目录。计划阶段发现就列为阻断项；服务停止后、移走活动目录之前再检查一次，仍有就停止并退回。Valise 不会替用户结束这些进程。（M4 在靶机上发现：Hermes 的 dashboard 进程独立于网关服务运行。）
- **路径被重新创建**：交换或退回时，如果目标路径已被其他进程重新创建，先把它改名挪到 `.valise-intruder-<op>-<root>` 保留（不删除），再完成改名，并在改名后核实；结果中提示用户检查。`valise prev drop` 一并清理。
- **健康检查**：按 profile 的 `health.checks` 执行（`systemd_active`、`tcp`、`http`、`argv`）。没有服务单元的实例（前台运行）不由 Valise 启动：计划中说明，交换完成后结果为"已恢复、未启动"，不做健康检查。
- **新实例的记录**：迁移与克隆成功后，在目标服务器写入实例记录和 profile 副本。`roots` 取目标路径；`provenance`、`service`、`entries` 在目标上重新探测（快照里的记录描述的是原服务器，例如 npm 前缀、二进制路径）；目标上的身体与快照的来源种类不同时，保留快照的来源记录。`local_overrides` 沿用快照头中记录的封存时规则（迁移和克隆都沿用；规则使用相对 root 的路径，跨服务器仍然成立；不依赖原服务器还活着）。
- **被取代的实例**：迁移或克隆的目标路径与目标服务器上另一个已登记实例的 root 相同，或那个实例的 root 位于目标路径之内（交换会把它的文件换走）时，计划中列出该实例并说明后果（警告，不阻断）。目标路径位于另一个已登记实例的 root 之内时（2026-11-07 用户决定）：如果目标 state 目录是本 profile 声明的命名实例位置（`detect.named` 的 glob，例如 Hermes 的 `profiles/*`），这是正常的命名实例布局，不取代、不阻断，按嵌套规则处理；其他情况一律阻断（不能把一个实例放进另一个实例的目录里），计划写明冲突的实例与办法（换一个目标目录）。交换成功后不删除它的记录，而是标记为"已被取代"（`superseded`：取代它的实例、op_id、时间）；它原来的目录按流程保留为 prev。被取代的实例不能再封存，也不能作为回滚目标；用同一 id 重新登记会清除标记。实例 id 不改名，因为备份库中的快照按 id 关联。
- **旧实例清理**：`valise old list <服务器>` 列出被取代的实例、取代它的操作，以及那次操作保留的旧目录和大小。`valise old cleanup <服务器> <实例>` 在用户再次确认后删除这个实例的记录、profile 副本，以及取代它的那次操作保留的旧目录（与 `prev drop` 相同）。只能由用户显式执行，porter 在 Go 代码中删除。备份库中该实例的备份不受影响（按周期删除见 VAULT_FORMAT.md 10.4）。
- **交换日志**：`~/.local/state/valise/journal/<op_id>.json`，每次状态变化原子写入并 fsync，内容包括模式、实例、各 root 的 live / stage / prev 路径、已搬动的身体目录、npm 身体的原版本、当前状态与时间。结束（`HEALTHY` 或 `ROLLED_BACK`）后移到 `journal/done/`，`hello` 只报告未完成的日志。
- **故障注入**（仅用于演练与测试）：客户端隐藏参数 `--inject-fault health|crash-at=<状态>` 通过环境变量传给本次 porter：`health` 让健康检查一律失败；`crash-at` 在写入该状态后立即退出进程。
- **prev**：`valise prev list <服务器>` 列出保留的旧状态及其天数；`valise prev drop <服务器> <op_id>` 由用户显式执行，porter 在 Go 代码中调用 `os.RemoveAll` 删除。

- **N4 桌面适配（2026-11-11）**：原生界面见 UI.md 7.10。新目标能力 `restore-review/1` 在服务器空闲锁内查询原 journal，返回已完成标记、实际保留目录、允许的固定恢复分支和现场摘要；恢复分支执行前再次核对摘要。中断迁移在尚未完成目标交换时只给退回，不凭旧停服证据继续。暂存清单作为 journal 的可选字段保留，继续前重新校验；不改变公开备份库。准备计划与两次确认有独立有效期，目录设备/inode、身份、资料、共享影响与连接信任变化使确认失效。
- **管理登录仍分离**：恢复中按来源重建程序或安装服务也要独立管理登录；在停止源服务前先建立这次操作自己的管理连接。porter 的代码同样拒绝日常连接在 swap/resume 中安装程序或服务。拒绝尚未交换的暂存不要求管理登录。取消准备使用独立的有界收尾 context，核实退回后才报告停止；无法核实则保留原 op_id 待查询。

### 8.2.2 恢复来源独立于原服务器（N3）

现有 8.2.1 的取回流程依赖源服务器查询和拉取，保留为在线路径。新流程先选择快照与可读取的备份来源，再选择恢复目标；本机仓库或已支持远端位置的完整副本可以独立提供材料，不能把源服务器不可达作为读取已保存快照的前置阻断。

- 材料按备份库/快照身份、快照头、index 与实际 pack 依赖检查；数据来源切换必须核对身份和内容，不以同名目录混拼。缺失、损坏或版本不支持必须停止相应恢复步骤并列出缺口。
- 从快照取得当时的 profile、来源、roots 和分类；保留已有快照 profile 的审核提示、显式允许条件与命令展示，不因原服务器失联自动信任可执行内容。
- 目标服务器仍须核对来源与精确版本、架构、空间、目录归属、共享服务影响和所需权限，再走原有暂存—校验—确认—日志交换。无法重建身体时可导出数据，不报告已运行。
- 源服务器不可达不证明源实例停止。独占身份无法核实隔离时，首版只提供排除 profile 声明的独占凭据后恢复，或导出/暂存等待处理；不接受仅凭用户声明已关机/已撤销身份就带独占身份完整启动，不提供风险确认绕过。独占凭据内联于共享配置时说明被排除的整个文件及影响，不扫描内容猜 token、不私自改写配置。具体流程采用 N1 契约第 6 节；克隆默认不带独占凭据的规则不变。
- 不因恢复来源离线放宽主人证明、管理登录、目标路径或目录交换限制。来源适配和权限采用 N1 契约第 6–8 节，不能直接给旧 PlanRevive 增加一个未经校验的任意目录参数。

#### 8.2.3 首版做法（2026-11-08 用户决定）

- **副本来源**：本机仓库（`repo:<名>`，在 `<仓库>/<服务器名>/` 下找；服务器名默认等于连接名，找不到时列出仓库里的服务器文件夹，用 `repo:<名>/<服务器名>` 指定）；用户选择的本机文件夹（`dir:<路径>`，指向含 `TREE` 的服务器文件夹，例如从 NAS 或网盘手动下载下来的）；这台电脑登录的云盘（`cloud:<名>`，读 `valise-vault/<服务器名>/`）。服务器自己配置的 rsync/sftp 位置和 Valise 管理的远程备份位置不直接读，用户可先把它们复制到本机再按文件夹选择。
- **什么时候改走副本**：源服务器连不上时停下，按快照 id 列出这台电脑知道的副本里哪些有这个备份（本机仓库与文件夹只看本机文件；云盘需要联网列目录），用户用 `--source` 选一个；不自动切换。源服务器连得上时也可以显式指定副本。`valise vault status <服务器> --source <来源>` 不需要服务器即可按周期列出副本里的备份（只读元数据，不需要私钥）。
- **读取规则**：本机仓库与文件夹原地只读打开，不写入；用到的数据包逐个核对 SHA-256 与名字一致，缺失或损坏就停止并列出。云盘按 8.2.1 的恢复缓存规则只取回这个备份需要的部分（`.partial.json` 标记、复用已核对的数据包）。不同来源不混拼：一次恢复只用一个来源，备份库 id 不符即停止。
- **失联迁移**：源服务器连不上时，`--mode migrate` 到另一台服务器沿用原实例名，规则为：不停止、不读取、不写入源服务器；profile 声明的独占凭据一律排除（与克隆相同，计划列出被排除的文件及影响，交换后需在新服务器上重新登录）；来源世代无法读取，按 SERVICE_CONTRACTS.md 6.3 由用户确认“来源无法核实”；交换时的处置为 `exclusive_omitted`，目标记一条迁移关系，来源身份记为未知。客户端在本机记下这次失联迁移（`lost-migrations.json`：源连接、实例、目标、时间、操作 id）；以后源服务器又连上时，如果那里仍有这个已接入的实例，就提醒“两边可能都在运行，独占凭据不要两边同时使用”，处理方式由用户决定，Valise 不自动停止任何一边。回滚（目标就是源）在源失联时不可用；克隆照旧。
- **导出**：`valise export <服务器> <备份 id> --to <本机空文件夹> [--source <来源>] [--include-secrets]` 把备份解密成普通文件，不启动 Agent。来源可以是服务器（在线）或任一副本。按 `<根 id>/<相对路径>` 写出，文件 0600、目录 0700；路径逐项校验，不越出导出文件夹；符号链接只在目标是导出文件夹内的相对路径时重建，其余记入导出说明 `VALISE-EXPORT.txt`；凭据类文件默认不导出，`--include-secrets` 时导出并在说明里列出。每个文件写完后按快照记录的 SHA-256 核对。导出到目标服务器暂存不在首版。

### 8.3 崩溃恢复

porter 每次被唤起时都会检查 `journal/` 目录，`hello` 会报告所有未完成的操作。客户端必须立即提示用户，让用户选择"继续完成"或"退回"（`valise revive resume <服务器> <op_id> --continue|--back`）。porter 绝不在没有客户端确认的情况下自动推进。

### 8.4 独占凭据与迁移

profile 可以把某些凭据声明为 `exclusive_secrets`，例如社交平台的 Bot Token，两个实例同时使用会互相冲突。迁移或克隆时，如果两个实例会同时运行，计划中必须二选一：

- **(a) 先停止原实例，再启动目标实例**（迁移的默认方案）；
- **(b) 目标实例不带独占凭据启动**（克隆的默认方案）。

原服务器失联时不把用户口头声明当作 (a) 的已核实停止；独占身份无法核实隔离时按 8.2.2 的首版分支处理。

### 8.5 跨架构

灵魂数据与架构无关，身体在目标服务器上按来源记录重建。工作区中如果有架构相关的二进制文件，只在报告中列出，不做修复。

### 8.6 B03 配置事务（2026-11-05 用户确认）

配置事务不执行完整 revive，不重建身体；只复用同文件系统暂存/目录交换的机制。独立记录在 `~/.local/state/valise/action-journal/`（`valise-action-operation/1`，0700/0600），终态移入 done；每次副作用前 intent、完成后结果均原子写入并 fsync。保存冻结计划、原服务状态、步骤进度和目录身份，不保存文件内容、命令输出、登录环境或凭据。备份库格式不变。

协议 1.3 增加事务能力与 pending_actions，客户端先核实服务器能力才登记或执行事务；action_plan/status 日常只读，run/resume 按冻结风险分级（B03 config 为管理登录），cleanup 按现有删除分级。与封存/交换共用修改互斥，未完成记录阻止冲突操作；重连提示用户，未知步骤不重跑。现场不符或记录损坏时停止。详细阶段、恢复分支与兼容要求见 [已确认 B03 设计](history/B03_DESIGN_PROPOSAL_2026-11-05.md) 第 4–6 节。

## 9. 体检（代码部分）

`porter checkup` 按 profile 的 `checkup` 声明计算以下指标：

- 每个会话的大小与 token 量。有 usage 字段时直接求和；没有时按字节数除以 4 估算，并标注为"估算"。
- 会话持续的天数，以及每日 token 增长率。
- 记忆文件的行数与 profile 阈值的比较。
- 冷会话占比（90 天前的会话所占的体积比例）。
- 是否启用了任何记忆机制（依据 profile 中声明的标记文件判断）。

计算结果以固定的 finding id 输出：`long_session`、`cost_growth`、`memory_bloat`、`session_pileup`、`no_memory_mechanism`。解读文案由 agent-kit 和 UI 提供，体检的计算过程不涉及 LLM。

## 10. 审计

`audit.jsonl` 每行记录：时间、操作、实例、发起者（`client` / `agent-mcp` / `timer`）、结果、快照 id、字节数、可选的原因与用途（如 `tutorial`），以及访问级别（`daily` / `owner` / `admin`）。审计记录绝不包含文件内容或凭据内容。

## 11. 统一任务、授权与生命周期（N1 已定稿，按 N2–N5 分场景落地）

统一的是面向入口的任务信息：操作目标、所用计划与版本/摘要、授权要求、阶段、进度、是否允许取消、已产生的副作用、分项结果、待恢复入口及最后核实时间。准确字段、状态机、持久化和事件接口采用已定稿 N1 契约第 7–11 节，不将设计接口宣称为已发布 RPC。

- 恢复 journal 和 B03 action-journal 仍是各自执行与恢复的权威记录；统一层适配它们，不用一个新状态枚举替换安全状态机，不自动重放结果不明的命令。
- 区分等待用户确认、等待解锁、执行中、等待重连、部分完成和终态；超时或 SSH 断开不自动等于成功、失败或已撤销。备份、复制、命令退出、配置发布、服务启动及复核各有结果。
- 用户确认须绑定具体目标与冻结计划；目标、来源、范围或命令变化时旧确认不可继续使用。复用现有主人证明、独立管理连接和操作前备份，不增加 AI 可取得的口令或通用授权票据。
- 切换页面、显式取消、关闭窗口、退出进程与远端断连分别处理。具体取消条件由相应操作决定；恢复进入交换后不因前端关闭而中断，B03 中断后按其日志要求用户选择。没有服务进程存活或已有定时器/有限子任务承接时，不承诺退出客户端后任务仍运行。
- 进度订阅断开后重新查询实际任务/远端日志，不凭前端计时器恢复状态。取消与清理不是同义词，残留资源仍按显式命令和既有删除权限处理。
- 资源互斥、submission_key 去重、结果不明时先核实、错误脱敏、授权到期和计划变化失效采用 N1 契约；冻结计划首次执行和恢复第二次确认的有效期均为 10 分钟，正在执行的任务不因该期限中断。结构化 CLI 是同一服务的适配，不另写业务分支。
- 管理方跨进程只提交允许的类型化请求到客户端私有待办箱；用户打开 GUI/TUI 后重新准备计划并确认，由该人类进程执行。没有人类会话则等待；不跨进程传递解锁身份、ssh-agent 凭据或通用确认票据，不凭磁盘 approved 字段恢复执行授权。执行者崩溃先核实，不因认领超时自动重跑。MCP 的恢复/删除等禁区不因请求箱而放宽；工具清单及实现按 N5a.2 单独交付。

## 12. 错误与文案

所有错误统一为 `{code, reason, suggestion, detail}` 结构。UI 默认展示 `reason` 和 `suggestion`，`detail` 默认折叠。
