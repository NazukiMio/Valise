# CLI/TUI 产品整改实施提案

日期：2026-11-04。代码基线：`701cdb6` 加当前工作区规范调整。交付对象：开发 agent。
配套验收：[QA_REVIEW_PROPOSAL_2026-11-04.md](QA_REVIEW_PROPOSAL_2026-11-04.md)。本文给出代码审查结果与实施方案；没有修改实现代码。代码位置以文件和函数定位，行号仅作辅助。

## 1. 本轮交付

按 A → B → C 执行，每批独立验收，不把所有功能堆进一个改动。

- **A：统一健康入口与状态。** 清除失效导航和旧文案；概览与健康使用同一套发现与忽略结果；刷新失败不冒充正常。
- **B：把已核实的修复接到健康发现。** 首项复用服务重启动作；审批修复补齐执行编排后接入。普通用户不必复制命令完成已有可靠方案。
- **C：自定义备份内容。** 实现目录/文件选择、保存、再编辑和恢复；先限现有 roots。它涉及新范围模型，不能只增加菜单。

用户已决定：面向普通用户，撤销“agent 相关问题不代修复”的限制；保留有趣命名但降低理解成本；支持可保存和修改的自定义范围。额外目录、陌生 harness、GUI 聊天、本轮未列出的新能力不在 A/B 的完成范围内。

## 2. A：直接整改的代码问题

### A01 概览仍写“体检”，而且重复统计未过滤的提醒

**位置**：`client/ui/tui/instance.go`，`overviewTab.view`，当前约 348 行；`health.go` 的 `rows`、`topHealth`；`instance.go` 的 `needsView`。

**现状**：备份行追加 `体检有 N 个提醒（见体检）`，N 直接取 `len(p.check.Findings)`。健康页已改名“健康”，且 `rows` 会把这些 finding 转成 `finding:<id>` 并应用忽略记录。顶部 `needsView` 已使用 `topHealth`，因此同一发现可能重复显示，忽略后备份行仍继续提醒。这是代码逻辑差异，不只是一处措辞错误；忽略场景仍需执行测试确认。

**修改**：删除备份行的整个 finding 追加块，不替换成“健康有 N 个提醒”。备份行只写备份信息；发现统一在 `needsView` 展示。保留实际健康分栏编号的动态查找，不硬编码“见 4 健康”。已忽略数量也从合并后的 health rows 统计，当前仅遍历 `p.health.Items` 会漏掉 finding。

**验收**：一个会话发现只出现一次；忽略后顶部不继续报该项，显示正确忽略数量；开关对话分栏、单 agent/多 agent 布局时导航编号正确。

### A02 健康中的会话检查失败被丢弃，页面可能继续显示旧结果

**位置**：`instance.go` 的 `checkLoaded` 分支与 `loadCheckup`；`health.go` 的 `view`、`rows`；`service/health.go` 的 `Health`。

**现状**：`checkLoaded.err != nil` 不更新任何状态，第一次失败没有说明，刷新失败则继续保留旧 `p.check`。`Health` 还将 Instances、TimerStatus、KitStatus 等子检查失败直接略过，审批 RPC 失败退为空结果。`healthTab.view` 仅根据已返回项数量显示“一切正常”。因此“检查未完成”和“没有问题”可能混淆。

**修改**：

1. `instancePage` 为 checkup 单独保存 loading/error/最后成功时间；失败可保留旧值，但标“上次结果，刷新失败”，不得当成最新结论。
2. `HealthReport` 增加明确的子检查失败信息（向后兼容的可选字段）；各子调用出错必须记录检查名与脱敏错误，不能无声丢弃。没有 profile 能力属于“不适用/未支持”，与 RPC 失败分开。
3. 健康页存在失败或尚未完成的检查时写“部分检查未完成”，不能“一切正常”。概览同时提示无法完整判断；已有真实问题照常显示。
4. 刷新完成后同时重算合并发现、忽略和摘要。不要把旧数据清空后短暂显示绿色。
5. “发现了什么”和“检查是否完整”独立表达；例如“已完成的检查未发现问题，但有 2 项未完成”。每次读取携带页面/实例归属与递增请求代号，延迟旧响应不能覆盖后一次刷新，切页后返回同样适用。

**验收**：首次失败、成功后失败、失败后恢复分别有可辨状态；已完成项不丢失；错误不露出凭据；无能力的项目不伪装为 RPC 失败。

### A04 保留品牌词，直接说明用户要选什么

**位置**：`tui/pods.go` 的 `tierChoices`、`pickSeal`；`tui/iset.go` 的 `periodText`。

## 3. B：健康页修复的实施路径

### B01 现有能力与缺口

- `core/profile/model.go` 的 `Action` 已有固定 argv、risk、undo、terminal；`service/actions.go:RunAction` 已处理授权、默认备份和运行状态检查。
- `tui/action.go:startAction` 已有确认与结果页，可复用，不能从健康页直接绕过调用。
- `HealthItem` 只有 `Key`，没有可执行动作引用；`healthTab.update` 只处理 t/u/s/k/y/i/r，确实没有修复分支。
- `actionResult.update(actionDone)` 仅 `m.loadServer`；父 `instancePage.health/check` 未被明确刷新，新增修复后不能沿用这个结果更新方式。
- `profiles/openclaw.yaml` 已有 restart；审批 remedy 为 stop → preset cautious → start 三步。`Action.Argv` 只能一条命令，不能把三步文字直接当成一个动作。

### B02 首批落地：服务重启

1. 在 profile 的服务声明中新增可选 `repair_action` 动作 ID（先写 schema 与 lint）；指向本 profile `actions`，lint 校验引用存在。具体名称如有既有等价字段则复用，不重复建模。
2. `HealthItem` 增加可选 `action_id`；服务项异常且关联有效动作时填入。Go 不判断 harness 名称，也不猜动作 ID 一定为 restart。
3. 健康页选中该项时显示 `f 修复` 及动作的真实名称；按键先重新读取动作清单，资料版本不一致先完成既有重新接入流程，再调用 `startAction`。
4. 修复结果携带 host/instance/item 标识；完成后重跑 Health、Checkup 和服务器状态，并让返回后的父页面消费结果。可新增范围明确的刷新消息，不能假设后台页面一定收到栈顶消息。
5. 结果分别写“命令退出码”和“该问题复核结果”；服务仍未启动必须保留原问题。CLI 复用已有 action 命令，在 health 人类输出列出准确的执行方式；不为便捷另建随意执行接口。

### B03 第二项：审批改为执行前询问

**可行性**：已有核实的读法和手动三步；缺固定步骤执行与失败补偿。不能直接拼 `sh -c`，不能把 `remedy` 文本解析成代码。

**建议实现**：为管理动作增加固定顺序的 argv 列表，与单 argv 互斥；仅顺序执行和遇错停止，不加入条件表达式/循环。停止前记录服务是否在运行；配置步骤失败后按明确的清理步骤尝试恢复原运行状态，分别报告原错误与清理错误。原本已停止的服务不擅自启动。审批动作与 `approval_check` 通过动作 ID 关联，成功后重新读取审批状态。

**开工闸门**：多步骤与清理 schema、原运行状态表达方式属于现行规范未覆盖部分。先提交上述具体设计供用户决定并更新 PROFILES/INSTALL，再写执行代码；B02 不受此阻塞。实际 cautious 不能只显示“需要批准”，还应说明白名单命令可能直接执行，其他命令询问。未经当前版本靶机核实不展示执行按钮。

设计还必须覆盖停服后客户端退出、SSH 断开、porter 中断：执行前保存各服务的原运行状态与操作进度，明确重新连接后的识别、继续或恢复办法，不能只依赖内存中的清理回调。配置是否已改变、服务是否恢复分别报告；恢复运行状态不等于撤销配置。健康入口优先显示“启动服务”“重启服务”“改为执行前询问”等实际动作名，避免笼统“修复”掩盖影响。

不做“修复全部”、自动记忆整理、自动恢复逃生舱、自动修改服务器时钟。不能自动修复的项目仍给明确下一步，不再以“Valise 一律不替你改”为理由拒绝。

## 4. C：自定义备份——现有代码不能只套 local_overrides

### C01 可行性结论

| 实际代码 | 能复用的部分 | 不能直接做到的部分 |
| --- | --- | --- |
| `tui/rules.go` | 展示分类与来源 | 只有滚动，无选择/保存/修改 |
| `service/enroll.go:Enroll`、`core/profile/classify.go` | ParseOverride、已声明 roots 校验、凭据优先 | Assign 每次从输入构建；分类不是独立的包含/排除，凭据不能通过 ignore 排除 |
| `porter/internal/enroll/scan.go:classify` | 遍历、大小、分类、SQLite/嵌套 root | Report 主要是分类汇总、凭据路径和未分类分组，不是通用分页文件树 |
| `porter/internal/seal/seal.go` | 分类、一致性、副本、加密与去重 | 多处用 InTier 过滤；SealParams 只有实例、tier、reason，无方案 |
| `porter/internal/timer/timer.go:Seal` | 服务器自主定时调用 | 固定 Tier soul，不读取用户方案 |
| `porter/internal/revive/swap.go:carry` | 活动目录以外复制到暂存 | 仅按类别是否在 tier 内决定携带，不能表达同类文件部分排除 |
| `core/vault/types.go:Snapshot` | 保存 profile、local_overrides、roots | 没有独立的选择范围；仅有 files 清单无法知道未出现的路径是排除还是备份时不存在 |

**结论**：不要增加 `TierCustom` 后继续调用旧 InTier；不要把所有选择伪装成归类修改。这会改变敏感层或使回滚误删未选择文件。

### C02 选定的实施建议

首版一个实例保存一份“自定义方案”，仅作用于已有 roots；四个预设保持现状。新增独立范围对象，包含基础预设、root 相对路径的 include/exclude 规则、版本；分类仍由 classifier 决定，范围只决定是否收录。

建议匹配语义：先取基础预设允许的内容，include 可显式补入其他分类，exclude 最后排除；目录选择递归并覆盖未来新增子文件；精确文件只匹配该文件。选入 secrets 或未知项仍用敏感加密层。SQLite 主库与附属文件为一个选择单位。raw 预设保持原本全量语义，不因自定义排除被悄悄改变。

回滚用快照时保存的范围对当前文件判定：范围内由快照替换（备份时不存在、现在新增的文件按回滚语义移除）；范围外保留并携带至暂存。迁移/克隆只还原备份内文件，不声称补齐排除内容。不能按当前方案解释旧快照。

**开工闸门**：上述范围对象、匹配语义及回滚删除语义是具体候选设计，尚未得到用户对每一细节的批准；先确认并更新 ARCHITECTURE/PROFILES/VAULT_FORMAT。公开格式扩展还要解决旧客户端忽略新范围后错误回滚的能力检查/拒绝策略，不能仅声称“增加可选字段即兼容”。若不扩格式，应证明现有字段可无歧义表达同样语义，否则不走替代捷径。

定稿前还须明确：

- 父目录包含、子目录排除、孙文件重新包含的优先级；首版建议排除最终优先，编辑器展示生效原因。路径改名和文件/目录/链接类型变化也要有例子。
- 区分“备份时不存在”和“扫描未读到”。权限、I/O 或不稳定文件导致遗漏时，不得把遗漏当作不存在，在回滚时删除当前文件；应阻止成功封存，或保存明确不完整状态并限制恢复。
- 用实际旧客户端验证其会在交换前拒绝新范围快照。若旧解析器忽略未知字段，必须选它不能误执行的版本或格式边界；不能只测试新客户端的版本判断。

### C03 开发步骤

1. **核心**：新增范围模型、有效范围求值与版本校验；以一个 shared predicate 供预览、seal、carry 使用，避免三套规则。
2. **持久化**：方案权威放服务器实例档案，客户端只缓存。新增读取/预览/保存服务与 RPC，保存需要主人授权；按版本比较更新防止两个客户端静默覆盖。不要通过重新 Enroll 整体重写档案保存方案，避免丢掉已有归类及其他事实。
3. **扫描**：复用 Walk/Classifier，新增限 root、按目录分页的路径/大小/类别/规则原因列表；不返回文件内容，不全盘扫描，不跟随链接越界；取消不保存。
4. **封存**：SealParams 可显式选择自定义；手动默认选择必须显示。快照记录实际生效范围；一次请求开始时固定版本，不在封存中途切规则。
5. **定时与动作前备份**：首版定时任务可选择跟随该方案，服务器每次运行读取已保存版本；默认不改现有定时 soul 行为。动作前自动备份仍显式用标准预设并显示该内容，不因为用户排除了配置而失去修复前退路。MCP 自动备份保持现有预设，后续再单独讨论。
6. **恢复**：范围随计划与日志传到 carry；旧快照走原逻辑；新快照在不支持的工具上明确拒绝，独立恢复工具同步验证所选文件可导出。
7. **TUI**：`pickSeal` 增加“自定义”；进入编辑器展示选择状态、大小、敏感项及排除原因；保存方案与立即备份分开；设置页可再次编辑。未改动取消不写；保存后回原入口。
8. **CLI**：复用同一服务与文件格式，提供导出/导入方案与预览入口；具体命令在实现前列入帮助规范，不改变原 seal 参数含义。

完成标准：选中自定义目录、排除同类另一个文件，重开仍保持；手动和选择跟随方案的定时任务真实按此封存；旧/新快照回滚逐文件正确；独立恢复成功。额外目录和陌生 harness 另开任务，首版不能宣称已覆盖。

## 5. 开发执行顺序与交付证据

1. A01/A02：先统一合并发现、忽略、加载、失败与旧结果状态，概览和健康页共用结论，按 QA 场景做回归。
2. A03/A04：更新 PRODUCT/UI 用语，再整改输出、导航、备份说明与 CLI 帮助。
3. B02：服务修复闭环，先 schema/lint，再服务/TUI/CLI，最后靶机。
4. B03 与 C 各自先提交具体闸门设计；得到决定后落规范再实现，不让这两项阻塞 A。

每批报告写：修改文件、对应任务 ID、自动测试结果、实际 UI 状态、真实靶机覆盖及未覆盖。不要用“原则已落地”代替入口可用，也不要用计划页验收替代真实恢复。

以后机会仅保留为待办：失去原电脑恢复引导、分项恢复准备摘要、覆盖变化提醒。它们不参与本轮完成判定。项目免费开源，不增加遥测或商业化任务。
