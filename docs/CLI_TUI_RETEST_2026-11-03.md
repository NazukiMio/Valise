## F07：可以拆成正常忽略行为与固有汇总冲突

### 配置对照

A 为上一轮独立测试配置。复测前检查，A **不存在** `health-dismissed.json`，并非带着旧的忽略记录启动。

B 是本次另建的配置目录：仅复制连接记录、已知主机、测试加密钥匙、收件人、资料和空间站定义；不复制 config.json、health-dismissed.json、restore-tests.json、体检忽略记录、金库和客户端缓存。B 没有配置本机仓库，因此“最近异地副本”的说明与 A 可以不同，这是预期的客户端配置差别。

两者连接同一实例，不修改服务器上的审批设置或记忆机制，不通过重置服务器制造所谓干净状态。

### 触发一：没有忽略记录也会出现矛盾文字

1. 用 A 启动 TUI，进入服务器、OpenClaw、健康页。
2. 等待读取结束：健康页有审批 Bypass 红色提醒，以及没有长期记忆的黄色提醒。
3. 切到概览。
4. 同一屏顶部显示审批、记忆两条问题，下面仍写“需要处理：无”。
5. 用 B 重复进入健康页，等待异步读取完成再切概览。B 还有“还没有测试过恢复”的黄色提醒，这是因为没有复制恢复测试记录。
6. B 的概览顶部显示“审批”和“恢复测试”问题，下面同样写“需要处理：无”。

**结论：这部分可以在无忽略记录的新配置中复现，不需要旧缓存或服务端忽略状态。** 它不是“健康数据没读到”：概览顶部已经拿到了当前健康结果。

### 触发二：忽略红色项后健康页仍显示，是规则本身

1. A 的健康页，从备份行向下移动两次，选中审批。
2. 按 `i`。
3. 提示为“主页不再提醒审批，30 天后恢复；红色的项在健康页里照常显示”。
4. 再按 `i`，提示“已恢复提醒审批”。
5. 核对本地文件，取消后为 `{}`。

因此，“健康页还红着，而概览不再列出这条红色提醒”本身不能判定为 bug。红色项保留在健康详情并继续计数、但被忽略后不进入概览，是当前代码明确规定的行为。

本轮通过界面实际切换了 A 的忽略状态并取消；没有等待 30 天或测试真实到期。没有修改服务器的审批策略。当前代码的忽略文件保存在客户端 Data 目录，按服务器、实例、finding 分组；不能据此声称不同客户端的忽略状态会自动共享。

### 代码归因

- `client/ui/tui/instance.go`：概览先调用 `topHealth` 显示健康问题，随后单独调用 `attention` 决定是否写“需要处理：无”。
- `client/ui/tui/health.go`：`topHealth` 从健康结果取 warn/bad，并排除 `Quiet()` 项。
- `client/ui/tui/cards.go`：`attention` 只考虑服务停止、管理页未监听、没有快照、超过七天未备份，不包含审批、恢复测试、记忆 findings。
- `client/ui/service/dismiss.go`：`Quiet()` 与 `Counts()` 的语义不同；已忽略的红色项仍计入健康页。

所以存在两条独立的汇总口径。服务和近期备份正常时，即使健康页有未忽略的问题，`attention` 仍可为空。这是固有界面汇总逻辑冲突，不是服务器残留配置的必要结果。

### 建议验收

统一“需要处理”的范围，或将 `attention` 区块改成明确的“运行与备份”状态，不让“无”覆盖上方健康问题。验收至少覆盖：无忽略、红色忽略、取消忽略、黄色忽略、新客户端无恢复测试记录、健康尚在加载六种情况。加载未结束时不能先宣称一切无需处理。

附带发现：110×34 的概览仍写“详见 3 健康”，而当前健康分栏是 4。它是旧快捷键说明，与 F07 的状态归因分开处理。

## F03：进度已修复，按快照取数尚未实现

### 精确触发步骤

1. 使用 B，确保金库缓存为空。
2. 执行 `restore-test <服务器> openclaw --snapshot s_01M6GMVKSS3HDH5MFRRHGS09PY`。
3. 该快照为上一轮 30 个文件、约 2.9 MiB 的 full 快照，同周期还有旧 raw 备份。
4. CLI 明确显示“取回逃生舱所在的整个周期……只要一个也要先取回这个周期”，总量 **247.8 MiB**。
5. 实际进度依次出现 32.4、83.6、137.1、184.4、239.9 MiB，随后进入本机解密并询问口令。
6. 本轮未进入暂存和交换；传输现象已充分观察，在口令阶段退出。不能把它记为本轮恢复测试再次通过。

### 结论与实现线索

第一部分的阶段和数据量提示已真实验证通过。第二部分依旧按周期取回，具有明确、可重复的触发条件：**冷缓存 + 小目标快照 + 同周期大历史备份**。

`client/ui/service/revive_plan.go` 先通过 `LeafOf(snapshot)` 找到周期，再调用 `s.Pull(ctx, from, leaf, "")`。当前入口没有将目标 snapshot 的依赖集合传给取回流程。

### 改进边界

不能把“仅需下载 2.9 MiB”或“仅需下载本次新增 238.6 KiB”直接作为指标：目标快照可能引用历史 blob，传输粒度也可能是整个 pack。

建议读取目标快照头、文件清单与必要索引，计算实际引用的 blob / pack；只拉取缺少的必要 pack，已有且校验通过的内容复用。局部缓存应明确为某一快照的恢复材料，不能伪装成完整且已经全库校验的周期；完整金库导出与独立恢复承诺仍需保留。

验收记录应同时包含：周期总大小、目标逻辑大小、引用 pack 大小、实际传输量、冷热缓存差别，以及中途断线后恢复。不能通过跳过完整性检查来减少传输量。

### 完整触发路径

1. 临时移开服务器 `dossiers/openclaw.json`，保留恢复副本，TUI 服务器页按 `r` 后确认显示“这台服务器上还没有接入 Valise 的 agent”。这是为复现起始空态进行的准备操作，不是产品正常退出接入的方法。
2. 按 `i`，选择 OpenClaw。安装器识别已有数据，选择“2 直接安装，新程序接管这份数据”。确认方案，跳过可选 PATH 修改。
3. 实际执行官方脚本、基础设置、目录权限与服务步骤；包管理器报告 changed 354 packages，基础设置显示 Config OK / Workspace OK。
4. 安装完成后回答“现在接入 Valise”为 y；报告显示后，再回答“接受接入报告”为 y。
5. 等待第二次登记完成，终端明确打印“已写入实例记录”，停在“按回车返回 Valise”。必须经过这一步，不能把尚未接受接入的安装记作本问题。
6. 按回车，之后不按 `r`，不切页，不执行外部刷新。

### 实际观察

- 返回后的第一次采样约在按回车后 1 秒，仍显示旧的“没有接入”空态与“正在确认仓库或空间站里有能独立恢复的备份……”提示。
- 第二次采样在按回车后约 11.2 秒时结束，输出已经包含“在线 · 1 个 agent”、main 的卡片、运行中和管理页可打开。**没有手动刷新，卡片确实自动更新。** 两次采样不能确定卡片变化的准确时刻，不把 11.2 秒当成固定刷新耗时。
- 卡片出现后，旧的“正在确认仓库或空间站……”提示仍显示在下方。本次没有另做长时间采样，不能断言它永不消失。

**结论：这条保留数据重装、重新接入的真实路径未复现持续空态或必须手动刷新的问题；仍复现刷新中的旧空态和残留进度文案。** 不能据单次重装结果宣称全新空服务器安装的所有返回路径均已通过。

### 代码与验收建议

当前 `serverPage.install` 已通过 `cliThen(m.loadServer(host), ...)` 在子命令结束后运行刷新，`execDone` 会返回后续命令；`srvLoaded` 替换实例缓存。这与此次自动出现卡片的结果一致。

`loadServer` 会将旧数据标为 loading，但服务器页空态仍可根据旧 instances 渲染。建议返回时明确显示“安装已完成，正在读取接入结果”，避免短暂空态诱导再次安装；操作结束时清理 gate 留下的进度提示。

后续验收应分别覆盖：空服务器全新安装、保留数据重装、拒绝接入、接受接入、安装中断，以及服务器刷新失败。对拒绝接入的情况应保留可解释的未接入状态；不要为了消除空态而自动接受登记。
