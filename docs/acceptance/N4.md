## 2026-11-15 架构减负：撤销 A/B 双槽位并行环境，收敛直通恢复闭环

- **背景与决定**：2026-11-12 至 2026-11-15 期间（见下文 6.8–6.39 历史工作记录），工作树尝试构建了 A/B 双运行槽位（`linux-bwrap` 容器接管、三档恢复模式、独立程序树采集与父子切换状态机）。经 2026-11-15 Prompt Audit 与架构评估，确认该链路过度复杂且与“不接管原生 systemd 服务”原则冲突，用户决定**正式撤销** A/B 双槽位设计并分阶段从工作树剥离。
- **保留的非 A/B 有效成果**：本轮 N4 新增的以下功能完整保留并纳入标准主线：
  1. 旅程按实例连接与迁移关系做范围化、增量读取与分位置重试（6.1–6.2）；
  2. 一次性备份与实时进度跟随、部分失败清晰展示（6.3）；
  3. 恢复历史记录、基础直通恢复/失联恢复与导出向导、恢复前可选备份（6.5–6.6）；
  4. 健康页选择具体备份时间点与副本执行文件/暂存恢复测试（6.7，移除隔离网关重建与 A/B 模式切换）；
  5. 按实例打开原生界面终端 `native --instance <id>`（6.29 通用部分，移除受管槽位绑定）；
  6. `core/vault` 与 `tools/standalone-restore/restore.py` 对 `valise-snapshot/1` 与 `valise-snapshot/2` 的永久读取兼容。
- 以下 6.8–6.39 仅作为 2026-11-12–15 A/B 并行环境开发阶段的历史记录保留（只读）。相关 A/B 槽位源码已于 2026-11-15/16 在分支 `refactor/revoke-ab-slots-and-doc-audit` 上分三阶段完成剥离（Stage 1 文档归档 `bc3d917`、Stage 2 `core`/`profiles`/`porter` `c9de8b9`、Stage 3 `client/ui`），并通过 `AGENTS.md` 第 6 节全部五模块自检（含 `profilelint`、Linux `arm64`/`amd64` 交叉编译、`go tool mygo vet` 及 `gui`/`tui` `<= 400` 行检查）。

### 1.2 发现并已修复

1. **本机备份按连接名匹配**：仓库里服务器目录用的是金库自己的名字（`debian-vm` 存在 `debian/` 下），界面按连接名找，`debian-vm` 上的 Agent 都显示“本机没有备份”并被算进“超过 7 天”的提醒。改为读 Agent 时顺带用日常钥匙读各服务器的金库名（`VaultStatus`），按它匹配；提醒从 6 个降到 4 个。
2. **自绘卡片没有按钮角色**：Agent 卡片、列表行、视图切换、导航窄栏、旅程节点在无障碍树里只有文字，读屏无法按下。加上按钮角色；名字带上 harness 与服务器，同名 Agent 可以区分。
3. **桌面版没接 Valise 口令框**：管理页令牌一步要确认是本人，服务层报“这里没法询问 Valise 口令”。已接上 `OwnerAuth`，与管理口令共用一个弹框，文案分开。
4. **健康页“定时备份：每 一次”**：保护计划按日历时间运行，没有固定间隔，文案拼空。改为“按保护计划的时间运行”。服务层文字，TUI 同样受益。
5. **未来时间说成“1 分钟前”**：模拟夏令时期间（时钟调到 2027 年）留下的备份，健康页说成“1 分钟前”。改为写出记录的日期并说明“晚于现在（备份时服务器时钟可能不准）”。
6. **搜索时计数不变**：改为“找到 N 个 · 共 M 个在用”。
7. **“超过 7 天”提醒不分原因**：补齐后仍有 4 个 Agent 报“没有新备份到这台电脑”，其实服务器上也没有新备份，“现在补到本机”解决不了。按用户决定（UI.md 7.2、7.3）分成两张卡片：服务器有更新的备份 →“有新备份还没复制到这台电脑”，去备份位置；服务器也没有 →“超过 7 天没有新备份”，去第一个 Agent 的“健康”看定时备份。服务器每个 Agent 的最新备份时间随读 Agent 时的金库状态一起读。实机复核：4 个都归到后者，进入 `debian-vm` 的 drill-synthetic 健康页签，显示“定时备份：没有开启”“备份：还没有备份”。

### 5.5 备份进度与结果核实（2026-11-11）

- “现在备份”显示开始时间、总耗时、进行中的位置与各部分耗时；忙时每秒请求重绘，切页后继续显示原任务，完成后保留用时。旧记录缺分项时间就不显示该项用时，不画没有真实字节数支持的进度条。部分失败保留服务器已保存的结果，逐项说明复制失败的原因与下一步。
- 默认连接内执行也在等待 Start 返回期间按同一 plan/run 查询任务；重开页面或客户端后从本机任务索引找回同一实例世代的未完成任务。“核实结果”只查原任务；结果仍未知时可以另行确认发起新的独立备份，旧任务保留，不重发。取消未能受理时显示原因，不把停止查询冒充服务器已经取消。
