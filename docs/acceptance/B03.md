## 2. 自动化证据

- `actionjournal`：分类（相对内部链接不列出、绝对内部链接、程序代码链接）；没有程序目录记录时拒绝并说明来源无法核实；指向其他位置与悬空链接拒绝并写明链接；暂存期间两类链接都只指向私有区域，还原后暂存摘要与活动目录一致；命令经链接写入私有副本时指出 `skills/program/cache.json`，原程序未被写入。
- `actiontxn`：含两类链接的完整事务发布，活动目录中链接为原文本；旧客户端（未声明 `link_handling`）在停服前被拒绝；步骤写入私有程序副本时不发布、恢复原服务，失败原因含“程序代码”。
- 全仓 `testbed/selfcheck.sh` 通过（SELFCHECK_PASS）。

## 3. 隔离真实网关验收（`ubuntu-vm`，OpenClaw 2026.10.9 (8b18b55)）

环境：独立 HOME `~/.cache/valise-b03-gw`，状态目录在其中；最小本地配置，没有渠道或模型凭据；用户单元 `valise-b03-gw.service` 运行真实 `openclaw gateway run --port 19864 --bind loopback --auth none`。网关首次启动后生成 `plugin-skills/browser-automation`、`plugin-skills/canvas` 两个绝对链接，指向用户 npm 前缀 `~/.openclaw/tools/node-v24.22.1/lib/node_modules/openclaw/dist/extensions/...`（与 2026-11-05 阻塞时相同）。

驱动：本轮验收程序在靶机上直接调用 porter 的 `Plan` 与 `Runner.Run`（不入库）；验收 profile 由官方 `profiles/openclaw.yaml` 派生，只改服务单元、入口端口，并加入事务动作：步骤 `exec-policy preset cautious`、`exec-policy show --json`（吸收首次读取对 SQLite 共享内存的改动）；环境 `OPENCLAW_STATE_DIR`、`OPENCLAW_CONFIG_PATH`、`OPENCLAW_HOME` 指向暂存；写入范围 `openclaw.json`、`openclaw.json.bak`、`state/openclaw.sqlite`（含 `-wal`、`-shm`），由事先在副本中运行比对得出。CLI/RPC/确认层沿用 2026-11-05 的实测，本轮只新增已有单元测试覆盖的 `link_handling` 参数。

第一次启动失败的原因（观察）：OpenClaw 在 `state/openclaw.sqlite` 的 `config_health_entries` 与 `diagnostic_events` 中按配置文件路径记录配置摘要；暂存中运行的命令记下的是暂存路径 `.valise-action-…/stage/openclaw.json`。交换后活动路径的记录与新配置不一致，第一次启动被配置守卫拒绝，此后自行补齐。真实安装的服务单元自动重启，第二次运行未再出现。这些记录里残留暂存路径不影响运行，但属于 harness 内部状态，记为已知现象。

另做只读扫描：用户真实的 `~/.openclaw`（npm 前缀在状态目录内）共有 10 个绝对链接（`plugin-skills/*`、`tools/node`、codex 工具链等），全部归为“内部绝对链接”，不再阻塞。

清理：测试单元已停止并删除；`~/.cache/valise-b03-gw`（约 206 MB，含两次事务的 prev 与私有副本）保留，待显式清理。
