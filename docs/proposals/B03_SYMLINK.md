# B03 链接与安装布局适配方案（修订稿，2026-11-05）

> 原 `docs/B03_SYMLINK_PROPOSAL_2026-11-05.md`（2026-11-07 改名移入 `docs/proposals/`）。待定设计提案，尚未经用户确认；B03 状态见 `docs/DEV_PLAN.md` 的未完成项。

状态：设计讨论中，执行代码与正式支持入口未改变。

用户反馈：安装布局的具体情况应记在服务器的安装档案中；通用代码不应按 harness 写特例，官方 profile 也不应逐项维护每次安装的链接名称。此前“在 profile 枚举两个 materialized_links”的提案由本稿替代。

## 1. 什么情况、会发生什么、为什么

同一种 harness 用不同方式安装、升级或新增功能后，数据目录里的链接也可能不同。当前 porter 对外部链接统一拒绝，因此遇到已安装程序自己的代码引用时，也无法执行配置事务。

如果逐项把今天的两个名称放进官方 profile，每出现新链接就需要改资料包。这把某次安装的实际布局当成整个 harness 的固定规则，无法适应不同服务器。

现有服务器已有安装档案：`~/.config/valise/dossiers/<install_id>.json`，旁边是登记时的通用 profile 副本。应扩展该档案，让它记录这次安装实际存在什么。

## 2. 三层职责

| 位置 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 通用引擎 | 探测文件结构、核对来源、生成暂存计划、复制、目录交换、中断恢复 | 不出现具体 harness 名称或特殊链接名称，不根据名称猜文件用途 |
| harness profile | 如何发现安装和实例、读取来源、区分身体/状态/凭据、调用已核实动作，以及该动作已验证的隔离与适配条件 | 不枚举每台服务器的全部链接，不固定本次安装的绝对路径 |
| 服务器安装档案 | 本次安装的真实目录、实际链接、目标归属、选择的通用处理办法及其核实证据 | 发现一个路径不等于授权它；不成为任意命令或脚本执行器 |

官方 profile 提供 harness 级知识；实际安装的适配明细由扫描结果生成并记录。用户本地 profile 仍可提供相同接口，不要求每次适配都发布官方资料包。

## 3. 安装档案增加什么

建议增加“安装布局”记录，字段名和 schema 版本在后续规范中定稿。需要记录以下事实：

- 安装来源和实际身体位置，以及来源所属的版本或摘要。
- 每个 agent 的扫描范围和相应状态目录。
- 实际链接的所在位置、原始链接文本、解析后的真实目标、完整解析链和目录/文件类型。
- 目标归属：本实例内部、已登记的身体、其他已登记实例、已明确登记的数据位置，或来源未知。
- 归属证据：来自哪条已有身体声明、包管理器文件归属或安装来源记录；不能仅因为目标在 HOME 或某个 npm/uv 前缀中就认定为代码。
- 已选择的通用处理方式、核实状态、对应的动作定义摘要及最近一次核实证据。
- 结构修订号和探测时间，供确认、执行及恢复核对。

安装级身体信息只存一份；链接属于哪个 agent 的状态目录，在 agent 对应的布局中记录。命名 agent 可引用安装级身体信息，不因其有效 profile 去掉 provenance 就丢失安装归属。

凭据分类沿用 profile 声明，优先于身体归属；没有声明清楚的内容保持未知或敏感。只扫描已登记范围及相关链接的元数据，不遍历整机找数据，不读取文件正文猜 API Key，不自动把外部目录加进备份。

## 4. 如何自适应

### 登记时

1. 使用已有 profile 发现安装、状态目录和安装来源。
2. 通用扫描器读取这些范围内的目录与链接结构，解析目标。
3. 根据已有身体声明和可核对的安装归属，生成每个链接的事实记录。
4. 将布局和适配建议加入既有登记报告，确认后写入安装档案，不增加独立口令或逐链接确认流程。

不需要用户填写两个技能目录，也不根据目录名套某个 harness 的特例。

### 日常计划时

1. 重新读取当前结构，不盲信旧档案。
2. 同一来源、同一规则能够解释的新代码引用，可以自动生成新的观察和候选计划。不能直接继承“此前成功过”的核实证据。
3. 纯探测结果与已接受布局分开：日常只读请求可以返回观察和差异，不能悄悄更新权限、来源或已接受的适配决定。
4. 如果来源、布局或适配影响变化，在现有计划/确认流程展示；按现有接入和操作权限接受相应变化后，再固定本次执行计划。不能扩大权限。
5. 停服后再次核对，确认后发生变化则停止。计划中冻结本次实际路径和处理办法，运行中不重新猜测。

升级、新增链接或路径移动因此成为“重新发现并核对结构”，通常不需要添加 Go 分支或给官方 profile 追加一个链接名称。若程序的行为规则发生变化，仍须更新或补充对应的 harness 规则及证据。

### 迁移与恢复时

原服务器的绝对目标只作为来源证据。目标服务器按相同来源重新定位并生成自己的布局，不能照抄原机器路径。无法重新定位时停止，不猜目标路径，也不自动安装未知来源。

## 5. 通用处理方式

| 识别出的情况 | 处理建议 |
| --- | --- |
| 相对链接完整留在当前 state 内 | 保留现有安全复制规则 |
| 绝对链接指向同一 state 内部 | 采用明确的内部映射规则，在 stage 中映射到副本；最终链接形式须在规范中确定，并单独验收 |
| 链接指向可核实的已登记身体代码目录 | 若当前动作已满足临时展开的隔离条件，可在 stage 中临时展开，验证后恢复原引用 |
| 链接指向其他实例、外部用户数据或凭据位置 | 不按代码处理，不自动复制或跟随；需要对应的明确数据范围和处理规则 |
| 悬空、循环、来源不明或发生冲突 | 标明具体原因并停止相关事务 |

“临时展开再恢复”仍是可复用的机制：完整复制目标代码到私有副本，暂存路径使用该副本，执行后核对内容未变并恢复原链接；转换过程写日志，失败可放弃 stage，残留由明确 cleanup 处理。

原先的两个 OpenClaw 名称只作为验收案例，不进入通用引擎或官方 profile 的必备路径表。

## 6. 能自动发现什么，不能自动推断什么

可以通过代码发现：链接在哪里、指向哪里、属于哪个已登记安装、类型和内容摘要是否变化。

不能仅靠这些信息推断：某个配置命令是否会保留临时实体目录、是否会先删除目录再创建链接、是否会另外写绝对路径。

因此，自动发现解决“这台机器是什么样”；harness 的已核实动作规则和本机核实证据解决“这次可以怎么操作”。档案中的 evidence 必须绑定 profile/动作定义、harness 版本、安装来源和适用布局条件。未知行为保持未知，不能因为登记了就自动放行，也不能让 LLM 的判断直接成为执行许可。

登记时允许 LLM 按既有范围补充说明或提出适配建议，但扫描、归属核对、计划、执行、校验和恢复都由确定性代码完成。只读发现不运行配置命令；任何首次实际试验仍须满足已授权动作的隔离、确认和风险规则。

如果某种 harness 已有可核实的机器可读安装信息，profile 可以通过受限的声明式读法补充发现结果；不能把 harness 输出当作授权或可执行脚本。首版可仅使用文件元数据和现有来源探测，不为此引入插件解释器。

## 7. 针对当前阻塞如何落地

1. 先定义安装布局记录、来源归属和观察/接受/核实三种状态，更新 ARCHITECTURE、PROFILES 及 B03 设计。
2. 增加通用扫描与归属分析，读取当前隔离安装，自动生成两个链接的事实。现有档案没有该字段时重新探测，不伪造为已核实。
3. 把 OpenClaw 当前版本“Linux 下保留同名实体目录”的源码观察作为待实测的行为依据；不预先填写这台机器的具体链接清单。
4. 完成临时展开机制及日志，使用自动生成的本次计划执行隔离验收。只有完整实测通过后才写成功证据。
5. 再用另一种安装来源/布局验证同一引擎：测试中换身体位置、增加不同名称的代码链接，确认无需改 Go 或官方链接清单；尚未测试的 Hermes/DSH 行为不声称已支持。
6. 验证升级、链接增删、来源不明、其他实例、凭据目录、确认后变化、命名实例、迁移及各个崩溃窗口。

## 8. 与自定义备份范围共用识别及覆盖报告（补充讨论）

关联设计：`docs/history/PRODUCT_REVIEW_PROPOSAL_2026-11-04.md` 第 4 节 C 自定义备份。两者应共用实例扫描、安装事实和路径归属，不能各自扫描后给出相互矛盾的结果；这不代表 B03 事务执行必须等待整个 C 编辑器完成。

用户提出的产品流程是：先用官方或本地 profile 识别，再结合服务器档案补足本机事实，剩余内容由自定义范围兜底。这里是识别与交互顺序，不改动现行凭据优先和 local_overrides 的分类优先级。

需要分别回答三个问题：

- 认识它吗：类别、来源、归属是否确定。
- 备份它吗：当前预设或自定义方案是否覆盖它。
- 能安全操作它吗：链接解析、来源和事务适配是否满足执行条件。

未知不等于不备份，选入备份也不等于已经知道如何安全运行它。当前规范已经让未分类文件进入标准、完整、原样档，并按敏感内容处理；轻装不包含它们。自定义范围应当补足用户选择，不能取代这个默认兜底。

### 降低用户负担的交互建议

1. 正常情况自动完成识别和归属核对，在备份摘要说明覆盖结果，不要求逐文件归类。
2. 未知文件已经包含在当前范围内时，汇总为“有 N 项尚未识别，已按敏感内容备份”，详情可展开，不为此逐项弹确认。
3. 当前选择遗漏未知内容时，按目录汇总并说明大小及影响，提供一次选择更广预设或进入自定义的入口。用户仍可明确保留轻装；不能暗中改变预设含义。
4. 自定义以目录为选择单位，允许保存并再次编辑；分类仍可保持未知，不要求用户判断文件是否属于记忆或配置。只有需要缩小范围时才展开到文件。
5. 已保存的范围继续使用；后续报告新增遗漏或范围变化，不反复询问已作出的相同选择。提醒时机和状态保存须在 C/UI 具体设计中确定，尚未实现。
6. 已明确覆盖的内容不反复打断。未读到、来源不明的外部目标、未登记目录和类型变化不能伪装成“已覆盖”；需要单独解释实际缺口。

例如：实例目录中多出一个 profile 不认识的目录，档案也没有声明其用途。若使用标准备份，应自动按敏感内容收录并汇总；若使用轻装，则说明它未包含，用户可以切换标准，或用基于轻装的自定义方案补入整个目录，无须先给它起类别名称。

自定义首版仍限已有 roots。外部链接目标不会因勾选链接就被自动遍历；备份链接本身不等于备份目标数据。未知外部目录需要后续明确的范围登记机制，不能声称 C 首版已兜底。B03 的事务隔离也不能靠用户勾选备份来放宽。

以上是共享模型和交互方向的补充提案，具体界面仍遵守先确认草图再实现的约定。

## 9. 兼容与保护

本方案涉及安装档案 schema、事务日志和能力声明的扩展。旧档案可读取，缺布局时重新探测；旧客户端或 porter 不认识新执行条件时，应在产生副作用前拒绝，不忽略新字段继续执行。

每次操作的日志保存冻结布局及处理计划，恢复不按后来重新扫描的结果改写旧计划。清理继续核对目录身份和当前登记 roots，不能删除安装来源或用户数据。

本稿没有改变现行规范或开放入口。此前方案中的逐路径 profile 声明和 npm 专用入口不再作为推荐实现；具体 schema 与通用处理策略须按本稿职责划分进一步定稿。
